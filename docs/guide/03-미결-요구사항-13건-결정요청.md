# 미결 요구사항 13건 — 결정 요청서

`python -m registry.check --all` 이 지금 13건으로 빨간불이다. 검사기 `CI-07`이 내는 것이고,
문장은 이렇다: **"이 레코드는 논쟁 중인 요구사항인데 어느 해석을 골랐는지 기록이 없다."**

## 먼저 — 제가 앞서 잘못 말한 것

"13건 전부 당신이 판단해야 한다"고 말했는데 **정확하지 않다.** 실제로는 셋으로 갈린다.

| 분류 | 건수 | 무엇을 하면 되나 |
|---|---|---|
| **A. 코드가 이미 골랐다 — 확인만** | 6 | "맞다/아니다" 한 마디 |
| **B. 실측이 나와야 숫자가 나온다** | 5 | "측정 전까지 값을 못 박지 않는다"를 기록으로 확정 |
| **C. 진짜 열린 판단** | 2 | 실제로 정해야 함 |

그리고 `CI-07`이 요구하는 건 **최종 숫자가 아니라 "어느 해석을 채택했는지"** 다. 그래서 B도
"측정에 위임한다"는 형태로 기록하면 닫힌다.

## 답하는 방법

각 항목의 **"당신이 답할 것"** 에만 답해주면 된다. 나머지(원장 기록·해시 재발행·재파종)는 제가 한다.

# B. 실측이 나와야 숫자가 나온다 (5건)

**전부 한 뿌리다.** 명세가 `U-0` 이라 부르는 것:

> **LeRobot Python 제어 루프의 실측 사이클 타임이 [미측정]이다 — 모든 주파수 요구사항의 뿌리.**

알려진 것: `openarm_teleop`(C++) 바이래터럴 스레드는 500 Hz로 돈다
(`openarm_bilateral_control.cpp:42,72,103`). **Python이 그걸 낼 수 있는지 아무도 모른다.**
같은 프로세스에 GIL·카메라 grab·이미지 라이터가 같이 있다.

또 하나 확정된 제약: LeRobot 한 사이클 = `get_observation()`(refresh 라운드) + `send_action()`(MIT
라운드) = **32 프레임/사이클**. CAN-FD 이론 상한이 **625 Hz**다. **500 Hz면 버스 부하 80%,
1000 Hz는 물리적으로 불가.**

| 요구사항 | 무엇을 정해야 하나 | 코드 상태 |
|---|---|---|
| `NFR-SAF-001` | 충돌 감지 루프 1 kHz + 지터 p99 ≤ 200 µs — **1 kHz는 CAN 예산상 불가**, 그럼 얼마로? | `backend/rtbench/` 가 상한을 하드코딩하지 않고 `enforce_target_hz(target, fmax)` 로 **측정값에 종속**시켜 뒀다 |
| `NFR-PRF-004` | `f_max = min(f_max_can, f_max_python)` 셀프테스트, 목표는 `f_max × 0.8` 이하 강제 | `backend/rtbench/fmax.py:72 max_target_hz()` 로 구현. **측정 대기** |
| `NFR-PRF-054` | Python 루프 실측 사이클 타임 자체 | 하네스 있음. **측정 대기** |
| `NFR-PRF-055` | M-8 하네스가 조건 1~7(순수 루프 / 패턴 A / 전체 텔레옵 / GIL 부하 / 프로세스 분리 / RT 승격 실효성 / candump 프레임 수)을 전부 자동 실행 | 하네스 있음. **측정 대기** |
| `NFR-GUI-004` | 관절 상태 지연(백엔드 → 브라우저 3D) **p95 상한** 숫자 | `backend/loadtest/constants.py:3` 에 *"여기 아무것도 합격선이 아니다"* 라고 명시. **측정 대기** |

**당신이 답할 것 (5건 공통, 한 번에)**:

> **"이 다섯은 M-8 실측(`NFR-PRF-054/055`) 결과에 위임한다. 측정 전에는 어떤 목표 주파수도
> 합격 기준으로 쓰지 않는다."**

이렇게 답하면 원장에 그 취지로 기록하고 닫는다. **숫자를 지금 지어낼 필요 없다** — 오히려 지어내면
안 된다. 실측 후 값이 나오면 그때 다시 기록한다.

다만 하나만 확인해달라: **`NFR-SAF-001`의 1 kHz 목표를 625 Hz 상한 아래로 내리는 것에 동의하나?**
(명세 본문이 이미 *"1 kHz는 물리적으로 불가"* 로 개정돼 있다. 형식상 확인만 필요)

# C. 진짜 열린 판단 (2건)

## C-1. `NFR-REC-001` — 녹화 루프 레이트의 하한 비율

**갈린 것**: 녹화 중 실측 사이클 레이트가 목표 fps(기본 30) 대비 **몇 % 밑으로 떨어지면 실패로 볼
것인가.**

**인용 가능한 유일한 선례**: ALOHA의 **84%** — 50 Hz 목표에 42 Hz 실측
(`aloha_scripts/record_episodes.py:109-111`). **다른 하드웨어의 값이다.**

**코드**: 하한 비율 상수가 **아직 없다**(`backend/recorder` 에 검색 결과 0건). 즉 지금은 아무 하한도
강제하지 않는다.

**선택지**:
- ① ALOHA의 84%를 잠정 채택하고, 우리 실측 후 재조정
- ② 우리 실측이 나올 때까지 하한을 두지 않되 **p50/p95/p99와 목표 미달 프레임 비율은 항상 보고**
- ③ 다른 숫자

**제 의견**: ②. 남의 하드웨어 숫자를 합격선으로 박으면 그게 나중에 "검증된 값"으로 인용된다.
보고는 이미 요구사항에 있으니 측정은 계속 쌓인다.

**당신이 답할 것**: ①/②/③ 중 하나.

## C-2. `NFR-GUI-008` — 제어 루프를 실시간 우선순위로 올릴 것인가

**갈린 것**: 제어 루프가 백엔드 프로세스 **안에** 있다(`GROUND §0`, CLI 스폰 금지 — `FR-GUI-083`).
그 상태에서 WS 서빙과 카메라 JPEG 인코딩이 같이 돈다.

명세가 요구하는 네 가지:
1. 제어 루프와 WS 서빙·인코딩을 **별도 스레드/워커로 분리**
2. WS 서빙/인코딩이 제어 루프를 블로킹하지 않을 것
3. 제어 루프 스레드를 **RT 승격(SCHED_FIFO) + `mlockall`** 대상으로
4. 제어 루프 사이클 타임 상시 계측

**갈리는 지점은 ③**이다. RT 승격은 root 권한이 필요하고, 잘못 쓰면 우선순위 역전으로 시스템 전체를
멈출 수 있다.

**코드**: `backend/rtbench/judge.py:120` 에 판단 근거가 이미 적혀 있다 —
*"`chrt -f` + `mlockall` 은 마지막에 적용하라, RT 승격은 GIL 문제가 해결된 뒤에야 도움이 된다."*
즉 **"GIL이 병목이면 RT 승격은 소용없다"** 는 순서 판단이 코드에 들어가 있다. 실제 승격 코드는
아직 없다(`SCHED_FIFO`/`sched_setscheduler` 검색 0건).

**선택지**:
- ① 명세대로 RT 승격을 구현 대상으로 확정 (root 권한 전제, 실측 후 적용)
- ② M-8 조건 6("RT 승격 실효성")의 **측정 결과를 보고 결정**한다 — 효과 없으면 안 넣는다
- ③ RT 승격을 아예 범위에서 제외

**제 의견**: ②. 코드에 이미 "GIL 먼저"라는 순서가 박혀 있고, M-8 하네스가 그 실효성을 측정하도록
설계돼 있다. 측정 없이 ①로 확정하면 효과 없는 root 권한 요구가 남는다.

**당신이 답할 것**: ①/②/③ 중 하나.
