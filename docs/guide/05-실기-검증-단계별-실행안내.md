# 실기 검증 — 처음부터 끝까지, 한 단계씩

이 문서는 **당신이 실제로 손으로 무엇을 하는지**만 적는다. 왜 그렇게 설계했는지는
`docs/guide/02-실기-검증-무엇을-해야-하나.md`에 있고, 여기는 **순서와 명령과 판정**이다.

읽는 법: 위에서 아래로 그대로 따라간다. 각 단계는 세 부분이다.

- **당신이 하는 일** — 손으로 하는 것
- **명령** — 그대로 복사해서 붙여넣는 것
- **다음으로 넘어가는 조건** — 이게 안 되면 다음 단계로 가지 않는다

---

## 이 문서에서 쓰는 말

몇 개만 먼저 정한다. 나머지는 나올 때마다 그 자리에서 풀어 쓴다.

| 말 | 뜻 |
|---|---|
| **토크 OFF** | 모터에 전기는 들어가 있지만 **힘을 안 내는 상태**. 손으로 팔을 움직일 수 있다 |
| **토크 ON** | 모터가 자기 자리를 지키려고 **힘을 내는 상태**. 손으로 밀면 저항한다 |
| **영점(zero)** | "이 자세가 0도다"라고 모터에게 알려주는 것. 이게 틀리면 **모든 각도가 다 틀린다** |
| **캡처** | 로봇이 내놓은 데이터를 파일로 받아 적는 것. 이 프로젝트는 캡처 파일을 받아서 판정한다 |
| **게이트** | 통과 못 하면 다음으로 못 가는 관문. 이름이 `PG-`로 시작한다 |
| **E-Stop** | 비상 정지 버튼. 누르면 전원이 끊긴다 |
| **CAN** | 모터와 컴퓨터를 잇는 통신선. 자동차에서 쓰는 것과 같은 방식 |
| **잔차** | 실제 토크에서 "중력·마찰·관성으로 설명되는 몫"을 뺀 나머지. **충돌 감지는 이 값을 본다** |

## 0. 시작 전 — 5분

### 0-1. 소프트웨어가 준비됐는지 확인

```bash
cd ~/workspace/bh_open_arm
./scripts/gates.sh
```

맨 아래에 `ALL GATES GREEN`이 나와야 한다. 안 나오면 **로봇을 만지기 전에 그것부터 해결한다** —
그 상태로 실기에 들어가면 나중에 나온 이상한 값이 로봇 탓인지 코드 탓인지 구분이 안 된다.

처음 받은 컴퓨터라면 그 전에:

```bash
uv sync --extra dev --extra robot
cd frontend && npm ci && cd ..
```

### 0-2. 기록할 폴더 만들기

캡처 파일을 한 곳에 모은다. 나중에 "이 수치 어디서 나왔냐"에 답해야 하기 때문이다.

```bash
mkdir -p ~/openarm_captures/{s1_power,s2_restraint,s3_clearance,s4_payload,s5_estop}
mkdir -p ~/openarm_captures/{usb,udev,link,lock,rid,bind,calib,torque,stop,friction,camera}
```

**규칙 하나**: 리그(로봇·구속물·카메라 배치)를 바꾸면 **이전 캡처는 못 쓴다.** 폴더를 새로 만들고
처음부터 다시 한다. 이건 규정이라기보다 물리다 — 다른 배치에서 잰 값은 지금 배치의 증거가 아니다.

| 물건 | 왜 |

`! ` 를 앞에 붙여 치면 결과가 대화에 그대로 들어오니 그게 편하다.

## 2. 1부 — 물리 안전 게이트 (`PG-SAFE-001`)

**이게 첫 관문이다.** 여기를 통과해야 나머지 물리 게이트 12개가 열린다. 그리고 이 게이트를
통과하기 전에는 **토크를 절대 켜지 않는다.**

순서는 **바꿀 수 없다.** S-5(E-Stop 시험)가 실제로 전원을 끊기 때문에, 그 전에 팔이 지지되고
(S-2) 아래가 비어 있고(S-3) 아무것도 안 매달려 있어야(S-4) 한다.

```
S-1 전원 도메인  →  S-2 구속물  →  S-3 낙하영역  →  S-4 무부하  →  S-5 E-Stop 리셋
```

---

### S-1 · 전원을 끊으면 CAN도 같이 끊기는가

**무엇을 알아내려는 건가.** E-Stop을 눌렀을 때 **모터 전원만 끊기는지, CAN 통신까지 같이 끊기는지**를
확인한다. 설계는 "둘 다 끊긴다"를 전제로 만들어져 있는데, **이 리그에서 실제로 그런지는 아무도 확인한
적이 없다.** 둘 중 어느 쪽이냐에 따라 전원 복구 절차가 달라진다.

#### 당신이 하는 일

1. 팔을 **전원 없는 상태**에서 손으로 rest 자세 근처에 두고 **잡고 있는다**
2. 그리퍼는 비운다. 팔 위에 아무것도 없어야 한다
3. 도달 범위 안에 사람이 없어야 한다
4. 아래 명령을 띄운 뒤, **E-Stop 버튼을 누른다**
5. 잠시 뒤 **리셋한다**
6. **끝날 때까지 팔에서 손을 떼지 않는다**

#### 명령

`[당신이 직접]` 터미널 두 개를 띄운다.

터미널 A — CAN 프레임을 계속 받아 적는다:
```bash
candump -ta -x any > ~/openarm_captures/s1_power/candump.txt
```

터미널 B — 링크 상태를 1초마다 찍는다:
```bash
while true; do
  echo "=== $(date -Ins)"
  ip -details link show
  sleep 1
done > ~/openarm_captures/s1_power/linkshow.txt
```

이 두 개가 도는 동안 E-Stop을 누르고, 5초 기다리고, 리셋한다. 그 다음 두 터미널을 `Ctrl+C`로 멈춘다.

#### 판정

두 파일을 저에게 주시면 제가 봅니다. 판정은 셋 중 하나다:

| 결과 | 뜻 | 다음 |
|---|---|---|
| **T-B** | 전원과 CAN이 **같이** 끊겼다 | 설계 전제와 일치. **S-2로** |
| **T-A** | 모터 전원만 끊기고 CAN은 살아 있다 | 복구 절차를 다시 정의해야 한다. 제가 처리 후 S-2로 |
| **그 외** | 부분 차단, 또는 아무 반응 없음 | **중단.** 회로가 제대로 연결 안 됐을 가능성 |

#### 즉시 멈춰야 하는 경우

- 버튼을 눌렀는데 **CAN 프레임이 계속 들어온다** → 차단 범위가 불명확하다
- 버튼을 눌렀는데 **컴퓨터가 재부팅된다** → 로직 전원까지 끊겼다는 뜻이고, 복구 절차가 성립 안 한다
- 버튼을 눌렀는데 **아무 반응이 없다** → 회로가 안 붙어 있다

### S-2 · 팔이 어디서 떨어져도 받아주는 구속물

**이 단계는 시뮬레이션으로 통과할 수 없다.** 어떤 시뮬레이션 결과도 여기서는 증거가 아니다.

**왜 그런가.** "이 자세에서 떨어지면 여기 떨어진다"를 계산하려면 마찰과 접촉을 알아야 하는데,
이 시점에 **마찰 모델이 없다**(그건 나중 단계의 산출물이다). 그리고 자세 100개를 확인해도
101번째에서 떨어지는 건 못 막는다 — 관절이 16개니까 가능한 자세는 연속이고 무한하다.

**그래서 다른 방식을 쓴다.** 떨어지는 **지점**은 모르지만, 팔이 **닿을 수 있는 범위**는 안다 —
베이스가 고정돼 있고 링크 길이가 정해져 있고 관절 한계가 정해져 있으니까. 그리고 **떨어진 자세가
무엇이든 그건 반드시 닿을 수 있는 범위 안**이다. 마찰이 얼마든 상관없이 참이다.

**그러니 구속물을 "떨어질 곳"이 아니라 "닿을 수 있는 범위 전체의 경계"에 세운다.**

#### 제가 먼저 하는 일

관절 한계와 링크 모양만으로 **도달 범위**를 계산해서 3D로 그려 드립니다. 마찰·접촉·동역학은
입력으로 쓰지 않습니다(쓰면 위 논증이 무너집니다). 그림은 **눈으로 보시라고 드리는 것**이지
판정 근거가 아닙니다.

#### 당신이 하는 일

1. 구속물을 **물리적으로 설치**한다
2. 구속물이 도달 범위 경계를 **끊김 없이** 둘러싸는지 실물에서 확인한다
   — 자세를 하나씩 시험하는 게 아니라, **틈·구멍·안 이어진 구간이 있는지**를 본다
3. **틈이 있으면 보고한다.** 틈은 "그 자세는 안 나오겠지"라고 기대하는 자리이고, 기대는 증거가 아니다
4. 구속물이 **얼마나 버티는지 근거를 말로 적는다**: 어떻게 고정했나(볼트/클램프/자중), 하중이
   어느 방향으로 걸리나, 왜 그 정도가 버틴다고 보나. 최악 조건은 **최대 높이에서 자유낙하 +
   최대 속도로 밀어붙이는 경우**다
5. 구속물이 **하중을 받는 방향**인지 판단한다 — 스치듯 닿거나, 옆으로 휘어 부러지면 안 된다
6. 사진을 찍는다 (경계가 이어져 있는 게 보이는 각도로)

#### 즉시 멈춰야 하는 경우

- 도달 범위 경계에 **구속물이 없는 구간**이 있다
- 구속물이 **팔의 정상 작업 경로를 방해**한다 (구속물이 충돌원이 되면 안 된다)
- **얼마나 버티는지 근거를 말할 수 없다**
- 손으로 움직이는 중 **딱딱한 끝(하드스톱)에 부딪힌다** → 관절 한계 설정이 의심된다
- 누군가 **"시뮬레이션 돌려보니 안 떨어진다"를 근거로 내민다** → 그건 이 단계가 요구하는 증거가 아니다

#### 통과 못 할 때의 정당한 해결책

**구속물로 도달 범위를 다 못 덮으면, 관절 한계를 좁혀서 도달 범위를 줄이는 게 정답이다.**
이건 패배가 아니라 설계된 출구다. 도달 범위는 관절 한계의 함수라서, 한계를 좁히면 **모델 없이도
확실하게** 범위가 줄어든다.

대가: 작업 공간이 줄고, 그 좁힌 한계가 이후 모든 것(IK·텔레옵·학습 데이터)의 경계가 된다.

### S-3 · 팔 밑을 비운다

S-2가 "경계에 무엇이 서 있는가"라면, S-3은 **"경계에 닿기까지 무엇을 지나가는가"**다.

비워야 할 공간 = **S-2에서 계산한 도달 범위 그대로**다. 낙하 궤적을 시뮬레이션해서 좁히지 않는다
(이유는 S-2와 같다).

#### 당신이 하는 일

1. 그 공간 안의 **움직일 수 있는 물건 전부 치운다** — 공구, 부품, 케이블, 의자, 모니터
2. 못 치우는 고정물(테이블 등)은 **부딪히면 부서지거나 튕기는지** 판단한다
3. **사람이 들어오면 안 되는 경계를 테이프나 펜스로 표시**한다
4. 치우기 전/후 사진을 찍는다

#### 즉시 멈춰야 하는 경우

- 못 치우는 물건이 남았는데 그게 **튕기거나 부서질** 수 있다
- 그 공간이 **사람 통행로를 침범**한다
- **케이블(CAN·USB·전원)이 그 공간을 지나간다** → 팔이 떨어지면서 케이블을 당기면
  어댑터가 빠지고, 그게 2차 사고가 된다

---

### S-4 · 아무것도 매달지 않았는지 확인

공식 안전 가이드가 낙하 위험으로 지목한 게 정확히 **"들고 있는 물건"**이다. 매달린 물건은
낙하 에너지를 키우고, 그리퍼에서 빠지면 **날아간다.**

#### 당신이 하는 일

1. 그리퍼에서 **모든 물체를 뺀다**
2. 팔·손목·그리퍼 케이스에 붙인 **임시 부착물 전부 뗀다** — 지그, 마커, 테스트 추
3. 무부하 상태를 촬영한다 (그리퍼 근접 + 전신)
4. **손안 카메라는 페이로드가 아니다** — v2 그리퍼 케이스에 내장된 것이고, 손목 카메라와 같은
   물건 하나다

#### 이 통과의 범위

**이 통과는 아무것도 안 매단 구성에만 유효하다.** 나중에 페이로드를 매다는 순간 이 게이트는
무효가 되고 **그 구성으로 다시 해야 한다.** 이유 두 가지, 둘 다 모델과 무관하다:

- 페이로드가 그리퍼 너머로 **길이를 늘리니까 도달 범위가 커진다** (S-2를 다시 해야 한다)
- 페이로드가 **낙하 하중을 키우니까 구속물의 버티는 근거가 무효**가 된다

---

### S-5 · E-Stop을 풀면 어떻게 되는가

**무엇을 알아내려는 건가.** E-Stop을 해제했을 때 로봇이 **저절로 다시 움직이기 시작하는지**를 본다.
회로가 자동 복전이면, 소프트웨어가 아무리 조심해도 **회로가 먼저 재개시켜 버린다.**

#### 당신이 하는 일

이 단계에 오기 전에 S-2·S-3·S-4가 **전부 끝나 있어야 한다.** 실제로 전원을 끊는 시험이라,
팔이 지지돼 있지 않으면 그냥 떨어진다.

1. 팔을 구속물 위에 두거나 손으로 지지한다
2. E-Stop을 누른다
3. **리셋한다**
4. 리셋 직후 팔이 **저절로 움직이는지** 본다 — 움직이면 안 된다
5. 촬영한다 (리셋 순간이 보이게)

#### 판정

| 결과 | 다음 |
|---|---|
| 리셋해도 팔이 **가만히 있다** | **`PG-SAFE-001` 통과.** 3부로 |
| 리셋하면 **저절로 움직인다** | **중단.** 회로가 자동 복전이라 소프트웨어로 못 막는다 |

### `PG-SAFE-001` 통과 후

### 3-2. 인터페이스 이름이 고정돼 있는가


#### 검증


환경변수가 없으면 그 테스트들은 "건너뜀"이 됩니다. **건너뜀은 통과가 아닙니다.**

### 3-5. 모터 16개를 읽는다 (`PG-RID-001`)

모터마다 설정값(레지스터)이 들어 있습니다. **토크를 켜기 전에** 그 값들이 우리가 기대하는
것과 맞는지 확인합니다. 특히 **RID 9(통신 끊김 감지 시간)**가 중요합니다 — 이게 잘못돼 있으면
통신이 끊겨도 모터가 계속 마지막 명령을 유지합니다.

#### 명령 `[당신이 직접]`

`openarm-can-cli`로 각 모터의 레지스터를 읽고, 아래 형식의 JSON을 인터페이스마다 하나씩 만듭니다:

```json
{
  "iface": "oa_fl",
  "motors": {
    "0x07": {
      "expected_type": "DM4310",
      "registers": {"9": "00002041", "23": "0000A040"},
      "declared_kinds": {"9": "f32"}
    }
  }
}
```

- `registers` 값은 **4바이트 리틀엔디언 16진수 그대로** — 해석하지 말고 읽은 그대로 적습니다
- `declared_kinds`는 `openarm-can-cli show_param`이 찍어주는 `Type` 칸입니다.
  이게 있어야 **타입 오독**을 잡을 수 있습니다

파일을 `~/openarm_captures/rid/` 에 인터페이스 하나당 하나씩 둡니다.

#### 검증

```bash
OPENARM_RID_REAL_FIXTURE=~/openarm_captures/rid pytest tests/wp0b07 tests/wp2a09 -q
```

#### 이 단계에서 열리는 것

모터 16개 관련 검증 6가지가 여기서 처음 실제로 돕니다 — RID 9 전수 읽기, 그 값의 판정,
J7의 RID 23, DM4340의 RID 22, 그리고 8개 모터의 과전압·과열·과전류 기록.

## 4. 3부 — 영점 잡기 (토크는 계속 OFF)

🔴 **이 프로젝트에서 가장 중요한 제약이 여기 있습니다.**

**`connect()`를 호출하면 영점이 파괴됩니다.** 상류 라이브러리의 `connect()`가 내부에서
`set_zero_position`을 부르기 때문입니다. 그래서 우리 코드는 `connect_readonly()`만 씁니다.

즉 **모드를 바꾼다고 다시 연결하면 안 됩니다.** 그러면 지금 자세가 새 영점이 되고, 그 뒤의
모든 각도가 조용히 틀립니다 — 오류 메시지 없이.

### 4-1. 영점 잡기

#### 당신이 하는 일

1. 팔을 영점 자세로 손으로 맞춘다 (토크 OFF라 손으로 움직여집니다)
2. 영점을 저장한다
3. 저장된 파일을 캡처 폴더에 복사한다

#### 검증

```bash

```

이 검증은 **저장된 영점 파일의 체크섬을 다시 계산해서 대조**합니다. 이번 세션에 고친 결함이
여기 있었습니다 — 체크섬이 비어 있으면 **검증을 건너뛰고 "검증됨" 도장을 찍고 있었습니다.**
지금은 빈 체크섬을 거부합니다.

### 4-2. 그리퍼 열림/닫힘 끝점 잡기

## 10. 9부 — 실시간성 측정 (`PG-RT-001`)

```bash
OPENARM_RTBENCH_REAL_FIXTURE=~/openarm_captures/rtbench pytest tests/wp104 -q
```

🔴 **주파수는 통과/실패 기준이 아닙니다.** 측정해서 보여줄 뿐입니다 — 이건 이번 세션에
사용자 판정으로 정해졌고, 코드가 그렇게 되어 있는지 정적 검사가 지킵니다.

**다만 예외가 하나 있습니다.** 충돌 감지 루프는 `K·dt < 2`를 만족해야 합니다. 이건 성능
기준이 아니라 **기능이 성립하는 조건**입니다 — 관측기가 전진 오일러라서, 이걸 어기면
잔차가 느려지는 게 아니라 **발산합니다.**

K = 90 기준으로:

| 루프 속도 | K·dt | 결과 |
|---|---|---|
| 1000 Hz | 0.09 | 수렴 |
| 100 Hz | 0.90 | 수렴 (**채택된 값**) |
| 50 Hz | 1.80 | 겨우 수렴 |
| 20 Hz | 4.50 | **발산** |
| 10 Hz | 9.00 | **발산** (45 → −315 → 2565 → −20475) |

즉 **감지 루프는 45 Hz를 넘어야 합니다** (K/2). 그래서 100 Hz로 정했습니다.

## 12. 🔴 절대 하면 안 되는 것

### 12-1. 페이로드를 매단 채 E-Stop을 시험하지 마라

`PG-SAFE-001`은 **무부하 구성에만** 유효합니다. 매단 순간 무효가 되고 다시 해야 합니다.

### 12-2. 복구 절차 없이 시작하지 마라

전원이 끊긴 뒤 어떻게 되살릴지가 **먼저** 정해져 있어야 합니다. E-Stop을 누르고 나서
"이제 어떻게 켜지?"를 고민하면 안 됩니다.

### 12-3. 시뮬레이션 결과를 물리 안전의 증거로 내지 마라

특히 S-2에서. 마찰 모델이 없는 상태의 시뮬레이션 출력은 **예측이 아니라 미검증 코드의 출력**입니다.

### 12-4. 리그를 바꾸고 이전 통과를 재활용하지 마라

구속물 하나만 옮겨도 S-2부터 다시입니다. 카메라 마운트를 옮겨도 마찬가지입니다.

### 12-5. "건너뜀"을 통과로 읽지 마라

```
5 passed, 12 skipped
```

이 12개는 **아직 확인 안 된 것**입니다. 환경변수를 안 줬으니 검사가 안 돈 겁니다.
초록색이라고 통과가 아닙니다.

### 12-6. 모드를 바꾼다고 다시 연결하지 마라

`connect()`가 영점을 파괴합니다. 오류 없이, 조용히.

## 13. 통과했는지 어떻게 아나

### 한 단계씩

```bash
pytest tests/<해당-패키지> -q
```

- **초록 (`passed`)** = 통과
- **빨강 (`failed`)** = 실패. 메시지에 어느 값이 얼마나 벗어났는지 나옵니다
- **건너뜀 (`skipped`)** = **아직 확인 안 됨.** 통과가 아닙니다

### 전체

```bash
./scripts/gates.sh
```

13가지 검사를 전부 돌리고 마지막에 `ALL GATES GREEN` 또는 `FAILED: <이름>`을 찍습니다.
**판정은 종료 코드로 합니다** — 출력 꼬리를 눈으로 보고 판단하지 않습니다.

호스팅 CI는 없습니다(연구개발 단계라 제거했습니다). 그래서 **`scripts/gates.sh`에 없는
검사는 아무도 돌리지 않습니다.**

### 기록

각 단계의 캡처·사진·판정은 남깁니다. 나중에 "이 수치 어디서 나왔냐"에 답해야 하고,
리그를 바꾸면 이전 증거를 못 쓴다는 규칙이 있기 때문입니다.

## 14. 요약 — 순서만

```
0.  ./scripts/gates.sh 로 소프트웨어 확인          ← 지금 바로 가능
1.  준비물 확보 (E-Stop 실물 · 구속물 필수)
2.  PG-SAFE-001:  S-1 전원 → S-2 구속 → S-3 낙하영역 → S-4 무부하 → S-5 E-Stop
    ↑ 여기 통과해야 아래가 열린다. 토크는 여기까지 계속 OFF
3.  통신 확인:    USB → udev 이름고정 → CAN 링크 → 잠금 → RID 16모터 읽기
4.  영점:         영점 잡기 → 그리퍼 끝점 → 홈 확인
5.  첫 토크 ON:   선행조건 검사 → 정지 성능 → 데드맨
6.  움직임 안전:  속도 한계 도출 → 자산 점검 → 충돌 임계값 보정
7.  마찰 식별:    여기 통과해야 충돌 감지가 켜진다
8.  카메라·시간 동기
9.  텔레오퍼레이션
10. 실시간성 측정
11. 데이터 수집 → 학습 → 평가
```

**당신이 하는 건 손으로 하는 일과 캡처입니다. 판정·분석·기록은 제가 합니다.**
