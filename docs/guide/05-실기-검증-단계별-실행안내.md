# 실기 검증 — 처음부터 끝까지, 한 단계씩

이 문서는 **당신이 실제로 손으로 무엇을 하는지**만 적는다. 왜 그렇게 설계했는지는
`docs/guide/02-실기-검증-무엇을-해야-하나.md`에 있고, 여기는 **순서와 명령과 판정**이다.

읽는 법: 위에서 아래로 그대로 따라간다. 각 단계는 세 부분이다.

- **당신이 하는 일** — 손으로 하는 것
- **명령** — 그대로 복사해서 붙여넣는 것
- **다음으로 넘어가는 조건** — 이게 안 되면 다음 단계로 가지 않는다

---

## 🔴 이 문서 전체를 지배하는 규칙 하나

**터미널은 명령이 끝나야 출력을 보여준다.** 명령이 도는 *중간에* 찍은 글자는 당신이 그것을 보고
행동해야 할 바로 그 순간에 화면에 없다. 카운트다운도, "지금 누르세요"도 마찬가지다.

이 함정으로 이 벤치에서 **E-Stop 측정을 세 번 날렸다.** 도구는 조용했고, 사람은 신호를 못 봐서
안 눌렀고, 도구는 그걸 "눌렀는데 반응 없음"으로 기록했다 — 하마터면 "E-Stop 회로 미연결"로 잘못
판정할 뻔했다. 회로는 멀쩡했다.

**그래서 사람이 손을 대야 하는 모든 단계는 이 모양이어야 한다:**

1. **벽시계 시각표를 먼저 찍는다** — "21:04:30에 비상정지를 누르세요"
2. **그다음에** 계측을 백그라운드로 띄우고 즉시 프롬프트를 돌려준다
3. 사람은 시계를 보고 그 시각에 행동한다
4. 판정은 나중에 별도 명령(`--status`)으로 읽는다

```
계측 시작됨 — 지금 돌고 있습니다
  현재 시각    19:44:20
  ▶ E-Stop     19:44:40  에 누르기
  ▶ 리셋       19:44:52  에 리셋
```

**상대 시간("15초쯤 뒤")은 쓰지 않는다. 절대 시각만 쓴다.** 상대 시간은 언제부터 세는지가 화면에
안 나오면 아무 뜻이 없다.

토크 ON 단계는 이 규칙이 도구로 구현돼 있다 — `./scripts/torque_session.sh --run`이 시각표를 먼저
찍고 워커를 떼어 보낸다(§5). E-Stop 단계는 아직 손으로 맞춰야 한다(§2).

## 이 문서에서 쓰는 말

몇 개만 먼저 정한다. 나머지는 나올 때마다 그 자리에서 풀어 쓴다.

| 말 | 뜻 |
|---|---|
| **토크 OFF** | 모터에 전기는 들어가 있지만 **힘을 안 내는 상태**. 손으로 팔을 움직일 수 있다 |
| **토크 ON** | 모터가 자기 자리를 지키려고 **힘을 내는 상태**. 손으로 밀면 저항한다 |
| **영점(zero)** | "이 자세가 0도다"라고 모터에게 알려주는 것. 이게 틀리면 **모든 각도가 다 틀린다** |
| **캡처** | 로봇이 내놓은 데이터를 파일로 받아 적는 것. 이 프로젝트는 캡처 파일을 받아서 판정한다 |
| **게이트** | 통과 못 하면 다음으로 못 가는 관문. 이름이 `PG-`로 시작한다 |
| **E-Stop** | 비상 정지 버튼. 누르면 전원이 끊긴다 |
| **CAN** | 모터와 컴퓨터를 잇는 통신선. 자동차에서 쓰는 것과 같은 방식 |
| **잔차** | 실제 토크에서 "중력·마찰·관성으로 설명되는 몫"을 뺀 나머지. **충돌 감지는 이 값을 본다** |

## 0. 시작 전 — 5분

### 0-1. 소프트웨어가 준비됐는지 확인

```bash
cd ~/workspace/bh_open_arm
./scripts/gates.sh
```

맨 아래에 `ALL GATES GREEN`이 나와야 한다. 안 나오면 **로봇을 만지기 전에 그것부터 해결한다** —
그 상태로 실기에 들어가면 나중에 나온 이상한 값이 로봇 탓인지 코드 탓인지 구분이 안 된다.

**이 개발 PC는 이미 설치가 끝나 있다.** 아래는 *새 컴퓨터*에서 이 저장소를 처음 받았을 때만
필요하다.

```bash
uv sync --extra dev --extra robot     # 파이썬 쪽 (로봇을 움직이는 부분)
cd frontend && npm ci && cd ..        # 웹 화면 쪽
uv run oa-index                       # 계획 색인 생성 — 새 클론에는 없다
```

앞의 두 줄은 **남이 만든 패키지를 받는 것**이고, 셋째 줄은 **이 저장소가 자기 계획서에서 만들어내는
색인**이다. 성격이 달라서 도구도 다르다.

앞 두 줄이 나뉘어 있는 이유: 이 저장소는 **파이썬 덩어리와 웹 화면 덩어리**로 나뉘어 있고 패키지
관리 도구가 다르다. 파이썬은 `uv`가 `uv.lock`을 그대로 따르고, 웹 화면은 `npm`이
`frontend/package-lock.json`을 그대로 따른다(`npm install`이 아니라 `npm ci`인 이유가 이것이다 —
`install`은 잠금 파일을 고쳐 쓸 수 있고 `ci`는 그대로 따르거나 실패한다).

🔴 **셋째 줄을 빼면 위의 `./scripts/gates.sh`가 반드시 빨간불이 된다.** `registry indexes`가
"182 generated file(s) diverge"로, `pytest`가 `registry/build/gate_index.json` 없음으로 3건
실패한다. `registry/build/**`는 계획서에서 **생성되는 물건**이라 git에 넣지 않고(`.gitignore`의
`build/`) 각 기계에서 만든다. 로봇하고는 아무 상관이 없는데 게이트가 빨간불이면 실기에 들어갈
수 없으니, **클론 직후 한 번은 반드시 돌린다.** `uv sync` 뒤여야 한다 — `oa-index`가 그때 설치된다.

`frontend/node_modules/`는 git에 들어가지 않으므로 새 컴퓨터에서는 반드시 한 번 받아야 한다.
이미 있으면 다시 칠 필요 없다. `npm ci`는 `added 297 packages`라고 찍는다 — 최상위 디렉터리는
216개고 나머지는 그 안에 중첩된다. 두 숫자가 달라도 정상이다.

#### `npm ci`가 내는 경고 세 종류는 정상이다

새 컴퓨터에서 위 명령을 치면 경고가 쏟아진다. **오류가 아니다.** 무엇인지 미리 적어둔다.

| 출력 | 무엇 | 대응 |
|---|---|---|
| `EBADENGINE` | 그 기계의 Node가 요구 버전보다 낮다. 요구는 `^22.13.0 \|\| >=24` — 근거는 README §런타임 버전. 루트 패키지 1건 + eslint 계열 전이 의존 3건이 뜬다 | Node를 24로 올린다. 경고만 나고 설치는 성공하므로 급하지는 않다. Node 24면 **0건**이 된다 |
| `deprecated whatwg-encoding` | 테스트 환경(`jsdom`)의 전이 의존. 상류가 갈아끼울 일 | 없음 |
| `12 vulnerabilities` | 9건은 개발 도구 전용(eslint·vite·vitest 계열), 3건은 `react-router` | 아래 참조 |

🔴 **`npm audit fix`를 돌리지 마라.** 12건 중 **한 건도 줄지 않는다**(실측: 12 → 12). 잠금 파일
한 줄만 바뀌어서 `npm ci`가 재현하던 트리가 의미 없이 흔들린다. `--force`는 eslint 10 · vite 8 ·
vitest 4로 끌어올려 게이트를 통째로 깨뜨린다.

`react-router` 3건이 유일하게 프로덕션 번들에 들어가는 것이라 코드를 확인해 뒀다. 셋 다 이
저장소에서는 **도달 경로가 없다**: SSR 하이드레이션 취약점은 SSR을 안 쓰고(`BrowserRouter`
하나뿐, `renderToString`·`StaticRouter` 0건), 열린 리다이렉트 2건은 이동 대상이 전부
컴파일타임 상수다(`NotFound.tsx`의 `to="/"`, `Layout.tsx`의 `screen.paths[0]`·`VIEWPORT_PATH`).
그리고 6.x 라인에는 **패치 버전이 아예 없다** — 6.30.4가 6.x 마지막 릴리스이면서 취약 범위의
상한이고, 수정은 7.18.0부터라 메이저 상승이다.

> **이 개발 PC의 Node는 v22.22.2**라 요구 범위(`^22.13.0 || >=24`) 안에 있다. `EBADENGINE`을
> 봤다면 그건 다른 기계다. 어느 쪽이든 경고이지 오류가 아니고, 게이트를 막지 않는다 —
> **`scripts/gates.sh`는 eslint를 돌리지 않고**, 경고를 내던 패키지들이 전부 eslint 계열이었다.

## 2. 1부 — 물리 안전 게이트 (`PG-SAFE-001`) — **통과**

**이게 첫 관문이고, 이 리그에서는 이미 통과했다.** 여기를 통과해야 나머지 물리 게이트가 열리고,
통과 전에는 **토크를 절대 켜지 않는다.**

| 단계 | 결과 |
|---|---|
| **S-1** 전원 도메인 | **T-B** — 모터 전원과 CAN이 같이 끊긴다 |
| **S-5** E-Stop 리셋 | 리셋해도 팔이 스스로 움직이지 않는다 (`FR-SAF-057`) |

S-2·S-3·S-4는 **게이트에서 뺐다**(사용자 결정). 남은 것은 S-1과 S-5 둘이고, S-1이 먼저다 —
S-1이 "E-Stop을 누르면 무엇이 끊기는가"를 확정해야 S-5가 무엇을 보는지 정해진다.

```
S-1 전원 도메인  →  S-5 E-Stop 리셋
(S-2 구속물 · S-3 낙하영역 · S-4 무부하 = 게이트에서 제외, 30초 눈확인으로 남음)
```

아래 절차 전체는 **리그를 다시 만졌을 때 다시 돌리기 위해** 남긴다 — 마운트·페이로드·E-Stop
배선·작업대 위치 중 하나라도 바뀌면 위 결과는 무효다.

---

### S-1 · 전원을 끊으면 CAN도 같이 끊기는가 — **끝남 (T-B)**

**무엇을 알아내려는 건가.** E-Stop을 눌렀을 때 **모터 전원만 끊기는지, CAN 통신까지 같이 끊기는지**를
확인한다. 설계는 "둘 다 끊긴다"를 전제로 만들어져 있고, 둘 중 어느 쪽이냐에 따라 전원 복구 절차가
달라진다.

#### 이 리그의 답: **T-B — 같이 끊긴다**

| 잰 것 | 값 |
|---|---|
| 모터 응답률 | **147/s → 0**, 0이 된 시각은 시작 후 **11.26초** |
| 버스 상태 | 양 채널이 `ERROR-ACTIVE` → `ERROR-PASSIVE` |
| 호스트 | **35초 연속 생존.** 재부팅되지 않았다 — 로직 전원은 별개다 |
| 리셋 후 | **7/7 모터 복귀** |
| 리셋 순간 자기 움직임 | **없음** — `FR-SAF-057` 성립 |

즉 설계 전제가 맞다. **복구 절차는 T-B 기준으로 그대로 간다.**

아래 절차는 리그를 다시 만졌을 때(마운트·배선·전원 구성 변경) 다시 돌리기 위해 남긴다.

#### 🔴 이 시험은 CAN이 살아 있어야 성립한다

첫 시도가 판정 불가로 끝났던 이유가 이것이다. `candump.txt`가 0바이트였는데, E-Stop이 CAN을 끊었기
때문이 **아니라 CAN 링크가 한 번도 올라간 적이 없었기 때문**이었다. 링크가 내려가 있으면 아래 T-A와
T-B가 **구별되지 않는다.** 그래서 링크 기동(0단계)이 **이 게이트 앞에** 있다 — 링크를 올리는 것은
토크와 무관하고 모터를 움직이지 않으므로 안전 게이트 앞에 두어도 된다.

링크 상태를 먼저 확인하지 않고 진행하면 같은 판정 불가가 그대로 재현된다.

#### 어댑터 사실

PEAK PCAN-USB Pro FD(`0c72:0011`), `peak_usb` 드라이버, 2채널이 한 USB 부모에 붙은 **1개 듀얼채널
장치**, `clock 80000000`. 이 80 MHz는 프로젝트 기준 코퍼스
(`tests/wp0b02/fixtures/corpus/normal.txt`)가 가정하는 것과 같아서 1M/5M 이 달성 가능하다.
어댑터는 **호스트 전원**을 쓴다 — 모터 전원 도메인에 물려 있지 않다.

#### 판별자는 프레임 유무가 아니라 오류 카운터다

T-A와 T-B는 **둘 다 모터 응답이 멈춘다.** 응답 침묵만으로는 구분이 안 된다. 갈리는 곳은 버스 상태다:

| | 팔쪽 트랜시버 | 호스트 송신 ACK | `can state` 귀결 |
|---|---|---|---|
| **T-B** 둘 다 끊김 | 전원 상실 | ACK 없음 → 오류 누적 | ERROR-ACTIVE → PASSIVE → **BUS-OFF** |
| **T-A** 전원만 끊김 | 별도 전원으로 생존 | 정상 ACK | **ERROR-ACTIVE 유지**, 카운터 0 |

그래서 **호스트가 계속 송신하고 있어야** 이 판별이 작동한다. 아무도 폴링하지 않으면 DM 모터는 먼저
송신하지 않으므로(`docs/v1/spec/03-모터-설정.md:167`) 누르기 전 침묵과 누른 뒤 침묵이 똑같아진다.
아래 터미널 C가 그것이다. `linkshow`가 두 번째 계측기로 있는 이유도 이것이다 — 판정은 거기서 나온다.

#### 당신이 하는 일

1. 팔을 **전원 없는 상태**에서 손으로 rest 자세 근처에 두고 **잡고 있는다**
2. 팔 위에 아무것도 없어야 한다
3. 도달 범위 안에 사람이 없어야 한다
4. **0단계로 CAN 링크를 올리고, 기동을 확인한다**
5. **모터 전원을 인가한다 — 토크는 OFF다.** 전기는 들어가지만 힘은 안 낸다
6. 계측기 3개를 띄우고, **기준 트래픽에 응답이 오는지 먼저 확인한다**
7. **누를 시각을 먼저 정해 놓고** 그 시각에 E-Stop 버튼을 누른다. 5초 기다리고, **리셋한다**
   — 위 "이 문서 전체를 지배하는 규칙"이 여기 적용된다. 계측 명령이 도는 중에는 화면에 아무것도
   안 나온다
8. **끝날 때까지 팔에서 손을 떼지 않는다**

#### 0단계 — CAN 링크 기동 `[당신이 직접]`

```bash
sudo ip link set can0 up type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can1 up type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can0 txqueuelen 1000
sudo ip link set can1 txqueuelen 1000
```

값은 발명한 게 아니다 — `backend/can/link/constants.py`의 `REQUIRED_BITRATE` ·
`REQUIRED_DBITRATE` · `RECOMMENDED_TXQUEUELEN`이고, 명령 형태는 `ops/systemd/can_link.py:42`가
렌더하는 것과 같다. **`restart-ms`는 0(커널 기본)으로 둔다** — 자동 재시작이 BUS-OFF 전이를
튕겨내며 지워버려서 T-B 신호를 가린다.

기동 확인:

```bash
ip -details link show can0
```

`mtu 72` · `state UP` · `can <FD,…> state ERROR-ACTIVE` · `bitrate 1000000 sample-point 0.750` ·
`dbitrate 5000000`이 다 보여야 한다. 🔴 **`mtu 16`이거나 `bitrate` 줄이 없으면 여기서 멈춘다** —
그대로 진행하면 1차 시도와 같은 판정 불가가 나온다.

#### 🔴 누를 시각은 계측을 시작하기 **전에** 정한다

이 문서 맨 앞의 규칙이 여기서 처음 걸린다. 아래 계측기 3개는 `Ctrl+C`로 멈출 때까지 화면에
아무것도 안 찍는다. 그러니 **터미널을 띄우기 전에 시계를 보고 "몇 시 몇 분 몇 초에 누른다"를
정해 두고**, 그 시각에 누른다. 상대 시간은 쓰지 않는다.

E-Stop 측정 세 번이 이 순서를 뒤집었다가 날아갔다. 회로 문제가 아니라 도구가 조용했던 것이다.

---

#### 명령 — 계측기 3개 `[당신이 직접]`

터미널 A — CAN 프레임과 **오류 프레임**을 받아 적는다:
```bash
candump -ta -x -e any > ~/openarm_captures/s1_power/candump.txt
```

`-e`가 있어야 오류 프레임이 사람이 읽을 수 있게 찍힌다. 버스 상태 전이는 ms 단위라 **여기에만**
잡힌다. 시각은 `-ta`(시스템 시계)로 둔다 — 터미널 B의 `date -Ins`와 같은 시계라서 대조가 된다.

터미널 B — can 인터페이스만, **통계 포함**, 0.2초 간격:
```bash
while true; do
  echo "=== $(date -Ins)"
  ip -details -statistics link show can0
  ip -details -statistics link show can1
  sleep 0.2
done > ~/openarm_captures/s1_power/linkshow.txt
```

`-statistics`가 RX/TX 패킷·오류 수를 준다. 인터페이스를 2개로 좁히는 이유는 1차 시도에서 39초
캡처가 106KB였기 때문이다 — `lo`·`wlan`·`tailscale`을 매초 덤프한 잡음이었다.

터미널 C — **기준 트래픽.** 1차 시도에 없었던 것이고, 없으면 시험이 성립하지 않는다:
```bash
while true; do cansend can0 7FF#0100CC0000000000; sleep 0.05; done
```

`0x7FF` + 3번째 바이트 `CC` = **Refresh(상태 요청)**, J1(send ID 0x01) 대상이다
(`docs/v1/spec/03-모터-설정.md:167`). **읽기 전용이다** — 플래시를 소모하는 파라미터 쓰기(`0x55`)도,
토크 인가(`0xFC`)도, 영점(`0xFE`)도 아니다. `NFR-MOT-003`의 감사 대상 목록에 `CC`가 없는 것이 그
확인이다.

🔴 **`0x08`(그리퍼)에는 이 프레임을 보내지 마라.** 이 리그에는 그 모터가 없고, 없는 모터는 오류가
아니라 침묵으로 답한다. 송신 오류 카운터가 올라가 **16프레임이면 양 채널이 `ERROR-PASSIVE`로
떨어진다** — 실측이다. 그러면 지금 재려는 T-A/T-B 판별 자체가 오염된다.

#### 누르기 전 확인 — 이걸 안 하면 또 판정 불가가 된다

`candump`에 **J1 master ID(`0x11`) 응답 프레임이 돌아오는지** 본다.

🔴 **응답이 없으면 E-Stop을 누르지 않는다.** 누르기 전 침묵과 누른 뒤 침묵이 구별되지 않아
1차 시도와 같은 결과가 된다. 응답이 없으면 전원·배선·종단저항·모터 ID를 먼저 확인한다.

응답이 확인되면 E-Stop을 누르고, 5초 기다리고, 리셋한다. 그 다음 세 터미널을 `Ctrl+C`로 멈춘다.

#### 판정

세 파일을 저에게 주시면 제가 봅니다. 판정은 셋 중 하나다:

| 결과 | 뜻 | 다음 |
|---|---|---|
| **T-B** | 전원과 CAN이 **같이** 끊겼다. `can state`가 BUS-OFF 또는 ERROR-PASSIVE로 간다 | 설계 전제와 일치. **S-5로** |
| **T-A** | 모터 전원만 끊기고 CAN은 살아 있다. `can state`가 ERROR-ACTIVE에 머물고 오류 카운터가 0이다 | 복구 절차를 다시 정의해야 한다. 제가 처리 후 S-5로 |
| **그 외** | 부분 차단, 또는 아무 반응 없음 | **중단.** 회로가 제대로 연결 안 됐을 가능성 |

#### 즉시 멈춰야 하는 경우

- 버튼을 눌렀는데 **모터 응답 프레임이 계속 들어온다** → 차단이 아예 안 걸렸다
- 버튼을 눌렀는데 **컴퓨터가 재부팅된다** → 로직 전원까지 끊겼다는 뜻이고, 복구 절차가 성립 안 한다
  (이 리그에서는 **해당 없음** — 35초 연속 생존)
- 버튼을 눌렀는데 **아무 것도 변하지 않는다**(응답도 계속 오고 오류 카운터도 0) → 회로가 안 붙어 있다

#### 판정 불가로 끝난 캡처는 치운다

판정 불가 캡처는 증거가 아니다. 폴더에 남겨 두면 다음 사람이 증거로 오인한다. **이름에 사유를
박아서 옮기고** 새로 만든다:

```bash
mv ~/openarm_captures/s1_power ~/openarm_captures/s1_power_VOID_<사유>
mkdir -p ~/openarm_captures/s1_power
```

### S-2 ~ S-4 — **연구개발 단계에서는 생략**

원래 여기에 세 단계가 있었다: 도달 포락 전체를 경계하는 하중등급 구속물 설치(S-2),
그 공간 비우기(S-3), 무부하 확인(S-4). **사용자 결정으로 게이트에서 제외했다.**

근거: 하중 정격 근거를 문서로 진술하는 공학적 구속물은 **연구개발 단계에 비해 무겁다.**
얻는 것보다 드는 품이 크다는 판단이다.

#### 다만 물리는 그대로다 — 30초짜리 확인

브레이크가 **없다.** 명세 `docs/v1/spec/04-수동-동작.md:38`: *"각 관절에 기계적 스토퍼 존재.
**기계식 브레이크는 없다** — 토크를 끊으면 중력으로 낙하한다."* 그리고 바로 다음 단계인
**S-5는 전원을 끊는 시험**이다. 페이로드 정격은 4.1 kg(피크 6.0 kg)이고, 그 무게가
엔드이펙터 위치에서 떨어진다.

게이트로 두지 않되, S-5 버튼을 누르기 직전 이것만 보면 된다:

- [ ] 팔을 **손으로 잡고 있다** (S-1에서 이미 하고 있는 것과 같다)
- [ ] 팔 **바로 아래**에 노트북·모니터·공구가 없다
- [ ] 팔 끝에 **매달린 것이 없다**

이건 절차가 아니라 눈으로 한 번 보는 것이다. 30초면 된다.

### S-5 · E-Stop을 풀면 어떻게 되는가 — **끝남 (자동 복전 아님)**

**무엇을 알아내려는 건가.** E-Stop을 해제했을 때 로봇이 **저절로 다시 움직이기 시작하는지**를 본다.
회로가 자동 복전이면, 소프트웨어가 아무리 조심해도 **회로가 먼저 재개시켜 버린다.**

**이 리그의 답: 리셋해도 팔은 가만히 있다.** 자기 움직임 없음 — `FR-SAF-057` 성립. 리셋 후
7/7 모터가 복귀했다. **`PG-SAFE-001` 통과.**

절차는 리그를 다시 만졌을 때를 위해 남긴다.

#### 당신이 하는 일

실제로 전원을 끊는 시험이라 **팔을 잡고 있어야 한다.** 브레이크가 없어서 놓으면 떨어진다.

1. 팔을 **손으로 잡는다** (브레이크가 없어서 놓으면 떨어진다)
2. E-Stop을 누른다
3. **리셋한다**
4. 리셋 직후 팔이 **저절로 움직이는지** 본다 — 움직이면 안 된다
5. 촬영한다 (리셋 순간이 보이게)

#### 판정

| 결과 | 다음 |
|---|---|
| 리셋해도 팔이 **가만히 있다** | **`PG-SAFE-001` 통과.** 3부로 |
| 리셋하면 **저절로 움직인다** | **중단.** 회로가 자동 복전이라 소프트웨어로 못 막는다 |

---

### `PG-SAFE-001` 통과 후

제가 통과 기록을 만들어 저장소에 남깁니다. 그 기록의 해시가 없으면 **토크 ON 경로가 시작 자체를
거부합니다** — 확인용:

```bash
python -m backend.torque_bringup.cli --manifest <시작-매니페스트.json>
```

이 명령은 `PG-SAFE-001` 통과 해시가 선언 안 돼 있으면 **0이 아닌 코드로 죽습니다.** 즉
"안전 게이트 없이는 토크를 못 켠다"가 말이 아니라 코드로 강제돼 있습니다.

## 3. 2부 — 통신·모터 확인 (토크는 계속 OFF)

여기부터는 로봇에 전원이 들어가 있지만 **모터는 힘을 안 냅니다.**

### 3-1. USB 어댑터가 보이는가

#### 명령 `[당신이 직접]`

```bash
lsusb -t > ~/openarm_captures/usb/lsusb_t.txt
```

각 CAN 인터페이스마다:
```bash
ip -s -d link show can0 > ~/openarm_captures/usb/ip_s_d_can0.txt
```

#### 넘어가는 조건
어댑터가 목록에 보이고, 인터페이스가 존재한다.

---

### 3-2. 인터페이스 이름이 고정돼 있는가

CAN 어댑터를 뽑았다 꽂으면 이름이 `can0`↔`can1`로 **바뀔 수 있다.** 그러면 왼팔 명령이
오른팔로 간다. **지금 대응은 `can0` = 왼팔, `can1` = 오른팔**이고, 이건 이름을 믿은 게 아니라
실제로 움직여서 확인한 값이다. udev 규칙으로 이 대응을 고정한다.

🔴 **규칙의 어댑터 축을 USB 경로로 쓰면 안 된다.** 두 채널이 한 몸이라 `ID_PATH`가 같다
(`pci-0000:80:14.0-usb-0:10.3.1.2:1.0`). 둘을 가르는 값은 **`dev_id`(`0x0` / `0x1`)**다.
경로로 쓰면 두 채널에 같은 이름이 붙는다. 아래 `udevadm info -a` 출력에서 그 속성을 확인한다.

#### 명령 `[당신이 직접]`

```bash
mkdir -p ~/openarm_captures/udev/udevadm
for i in can0 can1; do
  udevadm info -a -p /sys/class/net/$i > ~/openarm_captures/udev/udevadm/$i.txt
done
```

#### 검증

```bash
OPENARM_UDEV_REAL_FIXTURE=~/openarm_captures/udev pytest tests/wp0b05 -q
```

환경변수가 없으면 그 테스트들은 "건너뜀"이 됩니다. **건너뜀은 통과가 아닙니다.**

---

### 3-3. CAN 링크가 제대로 올라왔는가

링크를 **올리는** 명령은 §2의 S-1 0단계에 있다 — 안전 게이트가 그것 없이는 성립하지 않기
때문이다. 여기서는 올라간 상태를 **캡처해서 판정**한다.

#### 명령 `[당신이 직접]`

```bash
mkdir -p ~/openarm_captures/link
for i in can0 can1; do
  ip -details link show $i > ~/openarm_captures/link/$i.txt
done
```

그리고 기대값 파일을 만든다 — 각 인터페이스가 어떤 상태여야 하는지:

```bash
cat > ~/openarm_captures/link/expected.json <<'EOF'
{
  "can0": {"ok": true, "state": "ERROR-ACTIVE", "fd": true, "bitrate": 1000000, "dbitrate": 5000000},
  "can1": {"ok": true, "state": "ERROR-ACTIVE", "fd": true, "bitrate": 1000000, "dbitrate": 5000000}
}
EOF
```

숫자는 **당신 리그의 실제 설정값**으로 바꾸세요. 저 값은 자리 표시입니다.

#### 검증

```bash
OPENARM_LINK_REAL_FIXTURE=~/openarm_captures/link pytest tests/wp0b02 -q
```

### 3-4. CAN을 다른 프로그램이 같이 쓰고 있지 않은가

**이게 조용한 실패의 대표 사례입니다.** 두 프로그램이 같은 CAN에 붙으면 오류가 안 나고 그냥
명령이 섞입니다. 그래서 파일 잠금으로 막습니다.

#### 명령 `[당신이 직접]`

```bash
mkdir -p ~/openarm_captures/lock
cp /var/lock/openarm-can0.lock ~/openarm_captures/lock/ 2>/dev/null
cat > ~/openarm_captures/lock/expected.json <<'EOF'
{"can0": {"holder_pid": 1234}}
EOF
```

`holder_pid`는 실제 잠금을 쥔 프로세스 번호로 바꿉니다.

#### 검증

```bash
OPENARM_LOCK_REAL_FIXTURE=~/openarm_captures/lock pytest tests/wp0b01 -q
```

또 침입자 탐지도 있습니다:

```bash
mkdir -p ~/openarm_captures/intruder
cat /proc/net/can/rcvlist_all > ~/openarm_captures/intruder/rcvlist_all.txt
ip -s link show can0 > ~/openarm_captures/intruder/ip_s_link.txt
OPENARM_INTRUDER_REAL_FIXTURE=~/openarm_captures/intruder pytest tests/wp0b03 -q
```

그리고 같은 버스에 두 번 붙는 상황:

```bash
OPENARM_BIND_REAL_FIXTURE=~/openarm_captures/bind pytest tests/wp0b04 -q
```

### 3-5. 장착된 모터를 전부 읽는다 (`PG-RID-001`)

모터마다 설정값(레지스터)이 들어 있습니다. **토크를 켜기 전에** 그 값들이 우리가 기대하는
것과 맞는지 확인합니다. 특히 **RID 9(통신 끊김 감지 시간)**가 중요합니다 — 이게 잘못돼 있으면
통신이 끊겨도 모터가 계속 마지막 명령을 유지합니다.

🔴 **이 리그에서 읽을 모터는 팔당 7개, 합쳐서 14개입니다.** send id `0x01`~`0x07`.
**`0x08`은 읽지 않습니다** — 그리퍼가 없습니다. 없는 모터를 부르면 오류가 아니라 침묵이 돌아오고,
송신 오류 카운터가 올라가 **16프레임이면 양 채널이 `ERROR-PASSIVE`로 떨어집니다**(실측).
그러면 멀쩡한 7관절까지 같이 열화됩니다. 폴링 대상의 정본은 장착된 도구
(`backend/endeffector/tools.py`의 `EndEffectorProfile.motor_send_ids`)이지, 등록부
(`backend/can/rid/layout.py`의 `ARM_SEND_IDS` — 여기엔 여덟 개가 다 들어 있습니다)가 아닙니다.

#### 명령 `[당신이 직접]`

`openarm-can-cli`로 각 모터의 레지스터를 읽고, 아래 형식의 JSON을 인터페이스마다 하나씩 만듭니다:

```json
{
  "iface": "oa_fl",
  "motors": {
    "0x07": {
      "expected_type": "DM4310",
      "registers": {"9": "00002041", "23": "0000A040"},
      "declared_kinds": {"9": "f32"}
    }
  }
}
```

- `registers` 값은 **4바이트 리틀엔디언 16진수 그대로** — 해석하지 말고 읽은 그대로 적습니다
- `declared_kinds`는 `openarm-can-cli show_param`이 찍어주는 `Type` 칸입니다.
  이게 있어야 **타입 오독**을 잡을 수 있습니다

파일을 `~/openarm_captures/rid/` 에 인터페이스 하나당 하나씩 둡니다.

#### 검증

```bash
OPENARM_RID_REAL_FIXTURE=~/openarm_captures/rid pytest tests/wp0b07 tests/wp2a09 -q
```

🔴 **7모터 캡처를 8모터 기준으로 판정하면 `0x08`이 "응답 안 한 모터"로 잡힙니다.** 판정기
(`backend.can.rid.evaluate.evaluate_dump`)는 기대 id 목록을 인자로 받고, 안 주면 **여덟 개**를
기본으로 씁니다. 없는 그리퍼가 고장 난 모터로 둔갑하는 것이지 실제 결함이 아닙니다 — 이 결과가
나오면 저에게 알려 주세요. 판정 쪽에서 기대 id를 장착 도구에 맞추면 됩니다.

#### 이 단계에서 열리는 것

모터 레지스터 검증 6가지가 여기서 처음 실제로 돕니다 — RID 9 전수 읽기, 그 값의 판정,
J7의 RID 23, DM4340의 RID 22, 그리고 관절별 과전압·과열·과전류 기록.

## 4. 3부 — 영점 잡기 (토크는 계속 OFF) — **끝남**

**14개 모터 전부 raw 32767에 영점이 잡혀 있고, 전원을 껐다 켜도 살아남았습니다.** 잔차는
**0.0109°**입니다.

🔴 **0.0109°를 "고쳐야 할 오차"로 보지 마세요. 바닥값입니다.** 모터는 각도를 16비트로, ±12.5 rad
범위에 걸쳐 담습니다 — 한 눈금이 0.0219°입니다. 0.0109°는 정확히 **반 눈금**이고, 이보다 작은
값은 표현 자체가 안 됩니다. 다시 잡아도 이 숫자보다 아래로 못 내려갑니다.

**늘어뜨린 자세가 그대로 URDF 0도입니다.** 전 관절 0도에서 정기구학을 풀면 끝점이 `z = 0.904 m`,
`y = ±0.1535 m`에 옵니다. 토크를 끄고 팔을 놓아 두면 그게 0 자세라, 지그를 만들어 맞출 필요가
없었습니다.

절차는 리그를 다시 만졌거나 영점이 날아갔을 때를 위해 남깁니다.

🔴 **영점을 날리는 가장 흔한 방법이 이것입니다.**

**`connect()`를 호출하면 영점이 파괴됩니다.** 상류 라이브러리의 `connect()`가 내부에서
`set_zero_position`을 부르기 때문입니다. 그래서 우리 코드는 `connect_readonly()`만 씁니다.

즉 **모드를 바꾼다고 다시 연결하면 안 됩니다.** 그러면 지금 자세가 새 영점이 되고, 그 뒤의
모든 각도가 조용히 틀립니다 — 오류 메시지 없이.

### 4-1. 영점 잡기

#### 당신이 하는 일

1. 팔을 영점 자세로 손으로 맞춘다 (토크 OFF라 손으로 움직여집니다). 그냥 늘어뜨리면 그게
   0 자세입니다
2. 영점을 저장한다
3. 저장된 파일을 캡처 폴더에 복사한다

#### 검증

```bash
OPENARM_CALIBRATION_REAL_FIXTURE=~/openarm_captures/calib pytest tests/wp3b13 -q
```

이 검증은 **저장된 영점 파일의 체크섬을 다시 계산해서 대조**합니다. 빈 체크섬은 거부합니다 —
전에는 체크섬이 비어 있으면 검증을 건너뛰고 "검증됨" 도장을 찍었습니다.

### 4-2. 그리퍼 열림/닫힘 끝점 잡기 — **이 리그에는 해당 없음**

`fixed_spatula` 빌드라 `0x08`에 모터가 없습니다. 그리퍼를 달면 그때 이 단계가 열립니다 — 사람이
손으로 완전히 벌린 위치와 완전히 닫은 위치에 놓고 각도를 캡처합니다(`record.json` +
`expected.json`). 로드셀이 없어서 "완전히 열림"이 어디인지 기계가 알 방법이 없기 때문입니다.

```bash
OPENARM_GRIPPER_REAL_FIXTURE=~/openarm_captures/gripper pytest tests/wp2a08 -q
```

### 4-3. 홈 자세 확인

홈은 **J4 = π/2 (90도)**입니다. 전 관절 0도는 홈이 아닙니다 — 그건 J4가 기계적 끝에 닿은
자세라서 거부됩니다. (영점 자세와 홈 자세는 다른 것입니다: 0도는 "각도를 세는 기준"이고,
홈은 "여기서 시작한다"는 운영 자세입니다.)


지금 활성 홈 프로파일과 목표 자세를 찍어줍니다. 아무것도 실행하지 않습니다.

## 5. 4부 — 첫 토크 ON

**여기가 진짜 시작입니다.** 이 시점부터 팔이 스스로 힘을 냅니다.

### 5-1. 토크 ON 전 관문

```bash
python -m backend.torque_bringup.cli --manifest <시작-매니페스트.json>
```

이 명령이 **시작 매니페스트의 4가지 선행 조건**을 검사하고, 하나라도 안 되면 **0이 아닌 코드로
죽습니다.** 그중 하나가 `PG-SAFE-001` 통과 해시입니다. 토크를 켜지는 않습니다 — 문만 확인합니다.

> 조그 세션 쪽에는 **별도의 사전검사 5건**이 있습니다(`backend/preflight/gate.py`). 숫자가 다른
> 것은 서로 다른 관문이기 때문입니다 — 이쪽은 "시작해도 되는 빌드인가", 저쪽은 "지금 이 세션에서
> 토크를 인가해도 되는가"입니다.

### 5-2. 토크 ON 단계 전체를 한 세션으로

토크가 켜지는 단계는 **하나씩 따로 돌리지 마세요.** 훅마다 따로 치면 브레이크 없는 40 Nm 팔을
든 사람이 열두 번을 기다립니다. 그리고 그 사이사이 화면은 명령이 끝날 때까지 비어 있습니다
(맨 앞의 규칙).

```bash
./scripts/torque_session.sh --plan     # 각 단계가 당신에게 무엇을 요구하는지. 아무것도 안 돕니다
./scripts/torque_session.sh            # 선행조건만 검사하고 즉시 판정
./scripts/torque_session.sh --run      # 시각표를 찍고 워커를 떼어 보냅니다. 바로 프롬프트가 돌아옵니다
./scripts/torque_session.sh --status   # 워커가 지금까지 기록한 것을 읽습니다. 판정은 여기서 나옵니다
./scripts/torque_session.sh --run --step 3   # 3단계만 다시. 앞 캡처는 그대로 삽니다
```

`--run`은 **먼저 벽시계 시각표를 찍고 나서** 계측을 백그라운드로 보냅니다. 그래서 당신은 무엇이
언제 일어나는지 **시작 전에** 압니다. 첫 토크가 걸리기까지 30초의 여유가 들어 있습니다 — 시각표를
읽고, 두 손을 팔에 올리고, 자세를 잡는 시간입니다. 팔에 브레이크가 없어서 이 여유가 이 설계의
안전 그 자체입니다.

단계는 6개고, 각각 자기 캡처 폴더와 자기 훅을 가집니다:

| 단계 | 무엇 | 토크 | 훅 |
|---|---|---|---|
| 1 | 가드된 토크 ON — 현재 자세 홀드 | 🔴 **ON** | `OPENARM_TORQUE_BRINGUP_REAL_FIXTURE` → `tests/wp105` |
| 2 | 단일 관절 명령추종 스윕 (`PG-VEL-001`) | ON 유지 | `OPENARM_SAFETY_BRINGUP_REAL_FIXTURE` → `tests/wp106` |
| 3 | 충돌 임계값 보정 — 무충돌 잔차 수집 | ON 유지 | `OPENARM_THRESHOLD_CALIB_REAL_FIXTURE` → `tests/wp2c03` |
| 4 | 여기 궤적 주입 — **팔이 스스로 크게 움직이는 유일한 단계** | ON 유지 | `OPENARM_EXCITATION_REAL_FIXTURE` → `tests/wp2b06` |
| 5 | 마찰 식별 (`PG-FRIC-001` 증거) | ON 유지 | `OPENARM_FRICTION_REAL_FIXTURE` → `tests/wp2b07` |
| 6 | 실시간성·CAN 측정 (`PG-RT-001a`/`PG-CAN-001`) | 🔴 **OFF로 전환** — 받쳐 든 상태에서 천천히 내려놓으세요 | `OPENARM_RTBENCH_REAL_FIXTURE` → `tests/wp104` |

**판정은 종료 코드로 합니다** — `0` 통과 · `1` 거부 · `2` 아직 도는 중이거나 세션 기록 없음.
출력 꼬리를 눈으로 보고 판단하지 않습니다.

세션은 **스스로 토크를 걸지 않습니다.** 실모터 버스에 토크 프레임을 내보내는 결선이 아직 저장소에
없어서, 움직임이 필요한 단계는 **이름을 대고 거부**합니다. 지금 인자 없이 치면 이렇게 나옵니다:

```
  [통과] CAN 바인딩 — follower_left=can0, follower_right=can1
  [통과] 영점 캘리브레이션
  [통과] 장착 엔드이펙터 — fixed_spatula, 모터 7개: 0x01 0x02 0x03 0x04 0x05 0x06 0x07
  [통과] 토크-ON 선행조건 5건
  [거부] 토크 쓰기 경로 — 토크 쓰기 경로가 조립되어 있지 않다.
```

**이게 정상입니다.** 거부는 결선이 들어오는 날 저절로 풀립니다 — 세션이 자기 쓰기 경로를 새로
여는 것은 하지 않습니다. 단일 작성자 밖으로 나가는 토크 프레임은 8단계 안전 필터를 우회하고,
브레이크 없는 40 Nm 팔에서 그건 안전 거짓말이기 때문입니다.

거부가 나오는 동안에도 **위 네 줄은 진짜 검사**입니다 — 좌우 채널 대응, 영점 존재, 장착 도구가
정하는 모터 집합, 토크-ON 선행조건. 리그를 만진 뒤 이 명령 하나로 그게 다 확인됩니다.

### 5-3. 정지에 걸리는 시간(`PG-STOP-001`)은 재지 않습니다

이 자리에서 정지 지연을 재려고 왔다면 **잴 것이 없습니다.** 이유가 둘 겹칩니다.

1. **그 숫자가 없다고 못 만드는 기능이 없습니다.** 사용자 판정입니다.
2. **이 리그는 그 숫자를 정직하게 못 잽니다.** `ethtool -T can0`의 답이 이것입니다:

```
Hardware Transmit Timestamp Modes:
        off
PTP Hardware Clock: none
```

정지 시간은 **"데드맨을 놓은 순간"에서 "정지 프레임이 버스에 나간 순간"까지**입니다. 뒤쪽은
수신 하드웨어 타임스탬프로 찍히지만, **앞쪽을 같은 시계로 찍을 방법이 없습니다** — 이 어댑터는
송신에 시각을 못 찍고, 두 시계를 맞춰 줄 PTP 시계도 없습니다. 맞춰 놓지 않은 두 시계를 빼서 나온
숫자는 측정이 아니라 지어낸 값입니다. `docs/v1/plan/03-측정-게이트.md` §5.7.0이 그걸 금지합니다.
비교 대상인 20 ms 자체도 `[미확인]` 목표치이지 실측이 아닙니다.

**되살리려면** 셋 중 하나가 필요합니다: **송신 하드웨어 타임스탬프를 주는 CAN 어댑터**, 양쪽
시계를 맞춰 줄 **PTP 하드웨어 시계**, 또는 데드맨 릴리즈와 프레임 엣지를 **하나의 카운터로** 찍는
**별도 GPIO 마커 배선**. 그날 `PG-STOP-001`이 다시 판정 가능해집니다 — 소유는 `WP-1-05`고,
계획에서 사라진 게 아니라 잴 방법이 없어서 열리지 않는 것입니다.

**시계 없이도 남는 검사가 있고, 그건 지금 돕니다:**

```bash
python -m backend.stopbench.cli
```

인자를 받지 않습니다. 정지 경로의 **4단 형상**(하네스 이벤트 → 전송 → 스케줄러 → CAN)이 실제
코드 심볼에 묶여 있는지, 그리고 그 경로에 **`disable_torque`가 없는지**를 확인합니다. 어느 쪽이든
어긋나면 초록으로 보이는 산출물을 찍는 대신 **0이 아닌 코드로 죽습니다.**

정지 경로가 토크를 끊으면 안 되는 이유는 예산 이전의 문제입니다 — 브레이크가 없으니 **토크를
끊는 정지는 정지가 아니라 낙하**입니다. 이 판정에는 시계가 필요 없고, 그래서 지연 실측을 걷어내도
남습니다.

### 5-4. 데드맨(사람이 손을 떼면 정지)

```bash
OPENARM_DEADMAN_STOP_CAPTURE=~/openarm_captures/deadman/candump.txt pytest tests/wp2a02 -q
```

이건 **시간을 재는 게 아니라 순서를 봅니다** — 리스가 만료된 뒤 홀드 프레임이 실제로 버스에
나가는지, 만료 이후에 움직임 프레임이 하나도 없는지, 토크가 되살아나지 않는지. 시계 문제와
무관합니다.

## 8. 7부 — 카메라와 시간 동기

```bash
OPENARM_CAMERA_REAL_FIXTURE=~/openarm_captures/camera pytest tests/wp0b08 -q
OPENARM_DEPTH_REAL_FIXTURE=~/openarm_captures/depth pytest tests/wp3b03 -q
OPENARM_TIMESYNC_REAL_FIXTURE=~/openarm_captures/timesync pytest tests/wp3b04 -q
```

캡처 폴더 구조:

| 훅 | 폴더 안에 들어갈 것 |
|---|---|
| `OPENARM_CAMERA_REAL_FIXTURE` | `descriptors.json` (열거된 카메라 목록) + `capture_ts.*` |
| `OPENARM_DEPTH_REAL_FIXTURE` | `params.json` (`{device, depth_min, depth_max, shift, use_log}`) + `frames/*.npy` |

🔴 **`device`는 빼면 안 됩니다.** 없으면 훅이 캡처를 **거부**합니다. 이유가 있습니다 — 스테레오
카메라의 뎁스는 미터 단위 실수이고 매칭 안 된 픽셀에 `NaN`, 범위 밖에 `±inf`가 들어 있습니다.
그걸 확인 없이 uint16 밀리미터로 캐스팅하면 **1.5 m가 1 mm로 바뀌는데 채움률은 여전히 100%로
읽힙니다.** 어느 카메라에서 나온 값인지 적혀 있어야 그 변환을 거쳤는지 알 수 있습니다.

`frames/*.npy`는 `(H, W, 1)` uint16, 단위는 밀리미터, **0 = 측정 없음**입니다.

#### 이 리그의 뎁스는 아직 안 열립니다

달린 것은 **Stereolabs ZED Mini**입니다. RealSense가 아니고, 그래서 `pyrealsense2`가 아니라
**ZED SDK(`pyzed`)**가 필요한데 설치돼 있지 않습니다. 그리고 지금 USB 링크가
**풀스피드(12 Mbit/s)로 HID 인터페이스 하나만** 노출하고 있어서 영상 스트림 자체가 안 나옵니다.
`pyzed` 설치와 USB 링크, 둘 다 풀려야 이 항목이 시작됩니다.

훅은 카메라 종류와 무관하게 이미 서 있습니다 — 뎁스 계산기(채움률, 양자화 왕복)는 프레임 배열만
보므로, 실캡처가 들어오는 날 같은 코드가 그대로 돕니다.

## 10. 9부 — 실시간성 측정 (`PG-RT-001`)

캡처는 §5-2 세션의 **6단계**에서 나옵니다 — 그 단계는 토크를 끄고 읽기 전용으로 돕니다.
아래는 그 캡처를 판정하는 쪽입니다.

```bash
OPENARM_RTBENCH_REAL_FIXTURE=~/openarm_captures/rtbench pytest tests/wp104 -q
```

🔴 **주파수는 통과/실패 기준이 아닙니다.** 측정해서 보여줄 뿐입니다 — 사용자 판정이고, 코드가
그렇게 되어 있는지 정적 검사가 지킵니다.

**다만 예외가 하나 있습니다.** 충돌 감지 루프는 `K·dt < 2`를 만족해야 합니다. 이건 성능
기준이 아니라 **기능이 성립하는 조건**입니다 — 관측기가 전진 오일러라서, 이걸 어기면
잔차가 느려지는 게 아니라 **발산합니다.**

K = 90 기준으로:

| 루프 속도 | K·dt | 결과 |
|---|---|---|
| 1000 Hz | 0.09 | 수렴 |
| 100 Hz | 0.90 | 수렴 (**채택된 값**) |
| 50 Hz | 1.80 | 겨우 수렴 |
| 20 Hz | 4.50 | **발산** |
| 10 Hz | 9.00 | **발산** (45 → −315 → 2565 → −20475) |

즉 **감지 루프는 45 Hz를 넘어야 합니다** (K/2). 그래서 100 Hz로 정했습니다.

## 12. 🔴 절대 하면 안 되는 것

### 12-1. 페이로드를 매단 채 E-Stop을 시험하지 마라

`PG-SAFE-001`은 **무부하 구성에만** 유효합니다. 매단 순간 무효가 되고 다시 해야 합니다.
게이트로 검사하지는 않습니다(S-4는 뺐습니다) — S-5 직전 30초 눈확인에 들어 있습니다.

### 12-2. 복구 절차 없이 시작하지 마라

전원이 끊긴 뒤 어떻게 되살릴지가 **먼저** 정해져 있어야 합니다. E-Stop을 누르고 나서
"이제 어떻게 켜지?"를 고민하면 안 됩니다.

### 12-3. 시뮬레이션 결과를 물리 안전의 증거로 내지 마라

마찰 모델이 없는 상태의 시뮬레이션 출력은 **예측이 아니라 미검증 코드의 출력**입니다.
낙하 지점 예측이 특히 그렇습니다 — 마찰·접촉 파라미터가 아직 없습니다.

### 12-4. 리그를 바꾸고 이전 통과를 재활용하지 마라

로봇 위치나 카메라 마운트를 옮기면 그 배치에서 잰 값은 더 이상 지금 배치의 증거가 아닙니다.
캡처 폴더를 새로 만들고 다시 잽니다.

### 12-5. "건너뜀"을 통과로 읽지 마라

```
5 passed, 12 skipped
```

이 12개는 **아직 확인 안 된 것**입니다. 환경변수를 안 줬으니 검사가 안 돈 겁니다.
초록색이라고 통과가 아닙니다.

### 12-6. 모드를 바꾼다고 다시 연결하지 마라

`connect()`가 영점을 파괴합니다. 오류 없이, 조용히.

## 13. 통과했는지 어떻게 아나

### 한 단계씩

```bash
pytest tests/<해당-패키지> -q
```

- **초록 (`passed`)** = 통과
- **빨강 (`failed`)** = 실패. 메시지에 어느 값이 얼마나 벗어났는지 나옵니다
- **건너뜀 (`skipped`)** = **아직 확인 안 됨.** 통과가 아닙니다

### 전체

```bash
./scripts/gates.sh
```

13가지 검사를 전부 돌리고 마지막에 `ALL GATES GREEN` 또는 `FAILED: <이름>`을 찍습니다.
**판정은 종료 코드로 합니다** — 출력 꼬리를 눈으로 보고 판단하지 않습니다.

호스팅 CI는 없습니다(연구개발 단계라 제거했습니다). 그래서 **`scripts/gates.sh`에 없는
검사는 아무도 돌리지 않습니다.**

### 기록

각 단계의 캡처·사진·판정은 남깁니다. 나중에 "이 수치 어디서 나왔냐"에 답해야 하고,
리그를 바꾸면 이전 증거를 못 쓴다는 규칙이 있기 때문입니다.

건너뛰는 이유가 메시지에 적혀 있습니다 — 대개 "이 환경변수를 이런 폴더에 맞춰라"입니다.

## 14. 요약 — 순서만

```
0.  ./scripts/gates.sh 로 소프트웨어 확인          ← 지금 바로 가능
1.  준비물 확보 (E-Stop 실물 필수)                                          [있음]
2.  PG-SAFE-001:  S-1 전원(T-B) → S-5 E-Stop(자동 복전 아님)               [통과]
    (S-2·S-3·S-4 는 게이트에서 제외 — S-5 직전 30초 눈확인으로 남음)
3.  통신 확인:    USB → udev 이름고정 → CAN 링크 → 잠금 → RID 14모터 읽기   ← 지금 여기
4.  영점:         잔차 0.0109°, 전원 재인가 후에도 생존                     [끝남]
5.  첫 토크 ON:   ./scripts/torque_session.sh 한 세션 (6단계)
                  1 홀드 → 2 속도 스윕 → 3 임계값 → 4 여기궤적 → 5 마찰 → 6 실시간성
6.  움직임 안전:  속도 한계 도출 → 자산 점검 → (5의 3단계 캡처 판정)
7.  마찰 식별:    (5의 4·5단계 캡처 판정) — 여기 통과해야 충돌 감지가 켜진다
8.  카메라·시간 동기   ← pyzed 설치 + ZED Mini USB 링크가 먼저
9.  텔레오퍼레이션
10. 실시간성 측정 (5의 6단계 캡처 판정)
11. 데이터 수집 → 학습 → 평가

정지에 걸리는 시간과 반응에 걸리는 시간은 **재지 않는다** — 어댑터가 송신에 시각을 못 찍는다.
자세한 것은 §5-3.
```

**당신이 하는 건 손으로 하는 일과 캡처입니다. 판정·분석·기록은 제가 합니다.**
