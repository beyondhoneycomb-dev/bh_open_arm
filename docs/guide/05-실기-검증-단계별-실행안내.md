# 실기 검증 — 처음부터 끝까지, 한 단계씩

이 문서는 **당신이 실제로 손으로 무엇을 하는지**만 적는다. 왜 그렇게 설계했는지는
`docs/guide/02-실기-검증-무엇을-해야-하나.md`에 있고, 여기는 **순서와 명령과 판정**이다.

읽는 법: 위에서 아래로 그대로 따라간다. 각 단계는 세 부분이다.

- **당신이 하는 일** — 손으로 하는 것
- **명령** — 그대로 복사해서 붙여넣는 것
- **다음으로 넘어가는 조건** — 이게 안 되면 다음 단계로 가지 않는다

---

## 이 문서에서 쓰는 말

몇 개만 먼저 정한다. 나머지는 나올 때마다 그 자리에서 풀어 쓴다.

| 말 | 뜻 |
|---|---|
| **토크 OFF** | 모터에 전기는 들어가 있지만 **힘을 안 내는 상태**. 손으로 팔을 움직일 수 있다 |
| **토크 ON** | 모터가 자기 자리를 지키려고 **힘을 내는 상태**. 손으로 밀면 저항한다 |
| **영점(zero)** | "이 자세가 0도다"라고 모터에게 알려주는 것. 이게 틀리면 **모든 각도가 다 틀린다** |
| **캡처** | 로봇이 내놓은 데이터를 파일로 받아 적는 것. 이 프로젝트는 캡처 파일을 받아서 판정한다 |
| **게이트** | 통과 못 하면 다음으로 못 가는 관문. 이름이 `PG-`로 시작한다 |
| **E-Stop** | 비상 정지 버튼. 누르면 전원이 끊긴다 |
| **CAN** | 모터와 컴퓨터를 잇는 통신선. 자동차에서 쓰는 것과 같은 방식 |
| **잔차** | 실제 토크에서 "중력·마찰·관성으로 설명되는 몫"을 뺀 나머지. **충돌 감지는 이 값을 본다** |

## 0. 시작 전 — 5분

### 0-1. 소프트웨어가 준비됐는지 확인

```bash
cd ~/workspace/bh_open_arm
./scripts/gates.sh
```

맨 아래에 `ALL GATES GREEN`이 나와야 한다. 안 나오면 **로봇을 만지기 전에 그것부터 해결한다** —
그 상태로 실기에 들어가면 나중에 나온 이상한 값이 로봇 탓인지 코드 탓인지 구분이 안 된다.

**이 개발 PC는 이미 설치가 끝나 있다.** 아래는 *새 컴퓨터*에서 이 저장소를 처음 받았을 때만
필요하다.

```bash
uv sync --extra dev --extra robot     # 파이썬 쪽 (로봇을 움직이는 부분)
cd frontend && npm ci && cd ..        # 웹 화면 쪽
uv run oa-index                       # 계획 색인 생성 — 새 클론에는 없다
```

앞의 두 줄은 **남이 만든 패키지를 받는 것**이고, 셋째 줄은 **이 저장소가 자기 계획서에서 만들어내는
색인**이다. 성격이 달라서 도구도 다르다.

앞 두 줄이 나뉘어 있는 이유: 이 저장소는 **파이썬 덩어리와 웹 화면 덩어리**로 나뉘어 있고 패키지
관리 도구가 다르다. 파이썬은 `uv`가 `uv.lock`을 그대로 따르고, 웹 화면은 `npm`이
`frontend/package-lock.json`을 그대로 따른다(`npm install`이 아니라 `npm ci`인 이유가 이것이다 —
`install`은 잠금 파일을 고쳐 쓸 수 있고 `ci`는 그대로 따르거나 실패한다).

🔴 **셋째 줄을 빼면 위의 `./scripts/gates.sh`가 반드시 빨간불이 된다.** `registry indexes`가
"182 generated file(s) diverge"로, `pytest`가 `registry/build/gate_index.json` 없음으로 3건
실패한다. `registry/build/**`는 계획서에서 **생성되는 물건**이라 git에 넣지 않고(`.gitignore`의
`build/`) 각 기계에서 만든다. 로봇하고는 아무 상관이 없는데 게이트가 빨간불이면 실기에 들어갈
수 없으니, **클론 직후 한 번은 반드시 돌린다.** `uv sync` 뒤여야 한다 — `oa-index`가 그때 설치된다.

`frontend/node_modules/`는 git에 들어가지 않으므로 새 컴퓨터에서는 반드시 한 번 받아야 한다.
이미 있으면 다시 칠 필요 없다. `npm ci`는 `added 297 packages`라고 찍는다 — 최상위 디렉터리는
216개고 나머지는 그 안에 중첩된다. 두 숫자가 달라도 정상이다.

#### `npm ci`가 내는 경고 세 종류는 정상이다

새 컴퓨터에서 위 명령을 치면 경고가 쏟아진다. **오류가 아니다.** 무엇인지 미리 적어둔다.

| 출력 | 무엇 | 대응 |
|---|---|---|
| `EBADENGINE` | 그 기계의 Node가 요구 버전보다 낮다. 요구는 `^22.13.0 \|\| >=24` — 근거는 README §런타임 버전. 루트 패키지 1건 + eslint 계열 전이 의존 3건이 뜬다 | Node를 24로 올린다. 경고만 나고 설치는 성공하므로 급하지는 않다. Node 24면 **0건**이 된다 |
| `deprecated whatwg-encoding` | 테스트 환경(`jsdom`)의 전이 의존. 상류가 갈아끼울 일 | 없음 |
| `12 vulnerabilities` | 9건은 개발 도구 전용(eslint·vite·vitest 계열), 3건은 `react-router` | 아래 참조 |

🔴 **`npm audit fix`를 돌리지 마라.** 12건 중 **한 건도 줄지 않는다**(실측: 12 → 12). 잠금 파일
한 줄만 바뀌어서 `npm ci`가 재현하던 트리가 의미 없이 흔들린다. `--force`는 eslint 10 · vite 8 ·
vitest 4로 끌어올려 게이트를 통째로 깨뜨린다.

`react-router` 3건이 유일하게 프로덕션 번들에 들어가는 것이라 코드를 확인해 뒀다. 셋 다 이
저장소에서는 **도달 경로가 없다**: SSR 하이드레이션 취약점은 SSR을 안 쓰고(`BrowserRouter`
하나뿐, `renderToString`·`StaticRouter` 0건), 열린 리다이렉트 2건은 이동 대상이 전부
컴파일타임 상수다(`NotFound.tsx`의 `to="/"`, `Layout.tsx`의 `screen.paths[0]`·`VIEWPORT_PATH`).
그리고 6.x 라인에는 **패치 버전이 아예 없다** — 6.30.4가 6.x 마지막 릴리스이면서 취약 범위의
상한이고, 수정은 7.18.0부터라 메이저 상승이다.

> **이 개발 PC는 Node 18.19.1이라 `EBADENGINE`이 뜬다.** 18은 2025-04-30에 지원이 끝났다.
> 그래도 게이트는 초록이다 — `tsc`·`vitest`·`eslint`·`vite build` 전부 통과를 확인했고,
> 경고를 내는 패키지 3개는 전부 eslint 계열이며 **`scripts/gates.sh`는 eslint를 돌리지 않는다.**
> 즉 지금 실기 검증을 막는 요소가 아니다. Node 24로 올리는 것은 별건이다.

## 2. 1부 — 물리 안전 게이트 (`PG-SAFE-001`)

**이게 첫 관문이다.** 여기를 통과해야 나머지 물리 게이트 12개가 열린다. 그리고 이 게이트를
통과하기 전에는 **토크를 절대 켜지 않는다.**

S-2·S-3·S-4는 **연구개발 단계라 생략한다**(사용자 결정). 남은 것은 S-1과 S-5 둘이고,
S-1이 먼저다 — S-1이 "E-Stop을 누르면 무엇이 끊기는가"를 확정해야 S-5가 무엇을 보는지 정해진다.

```
S-1 전원 도메인  →  S-5 E-Stop 리셋
(S-2 구속물 · S-3 낙하영역 · S-4 무부하 = 연구개발 단계 생략)
```

---

### S-1 · 전원을 끊으면 CAN도 같이 끊기는가

**무엇을 알아내려는 건가.** E-Stop을 눌렀을 때 **모터 전원만 끊기는지, CAN 통신까지 같이 끊기는지**를
확인한다. 설계는 "둘 다 끊긴다"를 전제로 만들어져 있는데, **이 리그에서 실제로 그런지는 아무도 확인한
적이 없다.** 둘 중 어느 쪽이냐에 따라 전원 복구 절차가 달라진다.

#### 🔴 이 시험은 CAN이 살아 있어야 성립한다

**2026-07-29 1차 시도가 판정 불가로 끝났다.** `candump.txt`가 0바이트였는데, E-Stop이 CAN을 끊었기
때문이 **아니라 CAN 링크가 한 번도 올라간 적이 없었기 때문**이다. `linkshow.txt` 39샘플 전부에서
can0·can1이 `state DOWN` · `qdisc noop` · `can state STOPPED` · `mtu 16`(CAN-FD면 72)이었고,
`bitrate` 문자열이 파일 전체에 **0건**이었다. 링크가 내려가 있으면 아래 T-A와 T-B가 **구별되지 않는다.**

원인은 사람이 아니라 **이 안내서였다** — 링크를 올리는 단계(§3-3)가 **2부**, 즉 이 게이트를 통과한
*뒤*에 있었다. 안내서 자신의 순서가 S-1을 불가능하게 만들어 놨다. 아래 0단계가 그 수정이다.
**링크를 올리는 것은 토크와 무관하고 모터를 움직이지 않는다** — 그래서 안전 게이트 앞에 두어도 된다.

#### 1차 시도에서 이미 확정된 것 — 다시 재지 않는다

E-Stop을 실제로 눌렀고 모터 전원도 인가돼 있었음이 확인됐다. 그 39초 구간에서 중단조건 2건이 닫혔다:

| 중단조건 | 결과 |
|---|---|
| 버튼을 눌렀는데 **컴퓨터가 재부팅된다** | **해당 없음.** 1초 간격 39샘플이 공백 없이 연속 — 로직 전원은 살아 있다 |
| 어댑터가 모터 전원 도메인에 물려 있는가 | **아니다.** `parentdev 3-4:1.0`이 80개 인터페이스 블록 전부에 존재 — 어댑터는 호스트 전원을 쓴다 |

리그의 CAN 어댑터도 이때 확인됐다: PEAK PCAN-USB Pro FD(`0c72:0011`), `peak_usb` 드라이버,
2채널이 같은 USB 부모에 붙은 **1개 듀얼채널 장치**, `clock 80000000`. 이 80 MHz는 프로젝트 기준
코퍼스(`tests/wp0b02/fixtures/corpus/normal.txt`)가 가정하는 것과 같으므로 1M/5M 이 달성 가능하다.

#### 판별자는 프레임 유무가 아니라 오류 카운터다

T-A와 T-B는 **둘 다 모터 응답이 멈춘다.** 응답 침묵만으로는 구분이 안 된다. 갈리는 곳은 버스 상태다:

| | 팔쪽 트랜시버 | 호스트 송신 ACK | `can state` 귀결 |
|---|---|---|---|
| **T-B** 둘 다 끊김 | 전원 상실 | ACK 없음 → 오류 누적 | ERROR-ACTIVE → PASSIVE → **BUS-OFF** |
| **T-A** 전원만 끊김 | 별도 전원으로 생존 | 정상 ACK | **ERROR-ACTIVE 유지**, 카운터 0 |

그래서 **호스트가 계속 송신하고 있어야** 이 판별이 작동한다. 아무도 폴링하지 않으면 DM 모터는 먼저
송신하지 않으므로(`03-모터-설정.md:167`) 누르기 전 침묵과 누른 뒤 침묵이 똑같아진다. 아래 터미널 C가
그것이다. `linkshow`가 두 번째 계측기로 있는 이유도 이것이다 — 판정은 거기서 나온다.

#### 당신이 하는 일

1. 팔을 **전원 없는 상태**에서 손으로 rest 자세 근처에 두고 **잡고 있는다**
2. 그리퍼는 비운다. 팔 위에 아무것도 없어야 한다
3. 도달 범위 안에 사람이 없어야 한다
4. **0단계로 CAN 링크를 올리고, 기동을 확인한다**
5. **모터 전원을 인가한다 — 토크는 OFF다.** 전기는 들어가지만 힘은 안 낸다
6. 계측기 3개를 띄우고, **기준 트래픽에 응답이 오는지 먼저 확인한다**
7. **E-Stop 버튼을 누른다.** 5초 기다리고, **리셋한다**
8. **끝날 때까지 팔에서 손을 떼지 않는다**

#### 0단계 — CAN 링크 기동 `[당신이 직접]`

```bash
sudo ip link set can0 up type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can1 up type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can0 txqueuelen 1000
sudo ip link set can1 txqueuelen 1000
```

값은 발명한 게 아니다 — `backend/can/link/constants.py`의 `REQUIRED_BITRATE` ·
`REQUIRED_DBITRATE` · `RECOMMENDED_TXQUEUELEN`이고, 명령 형태는 `ops/systemd/can_link.py:42`가
렌더하는 것과 같다. **`restart-ms`는 0(커널 기본)으로 둔다** — 자동 재시작이 BUS-OFF 전이를
튕겨내며 지워버려서 T-B 신호를 가린다.

기동 확인:

```bash
ip -details link show can0
```

`mtu 72` · `state UP` · `can <FD,…> state ERROR-ACTIVE` · `bitrate 1000000 sample-point 0.750` ·
`dbitrate 5000000`이 다 보여야 한다. 🔴 **`mtu 16`이거나 `bitrate` 줄이 없으면 여기서 멈춘다** —
그대로 진행하면 1차 시도와 같은 판정 불가가 나온다.

#### 명령 — 계측기 3개 `[당신이 직접]`

터미널 A — CAN 프레임과 **오류 프레임**을 받아 적는다:
```bash
candump -ta -x -e any > ~/openarm_captures/s1_power/candump.txt
```

`-e`가 있어야 오류 프레임이 사람이 읽을 수 있게 찍힌다. 버스 상태 전이는 ms 단위라 **여기에만**
잡힌다. 시각은 `-ta`(시스템 시계)로 둔다 — 터미널 B의 `date -Ins`와 같은 시계라서 대조가 된다.

터미널 B — can 인터페이스만, **통계 포함**, 0.2초 간격:
```bash
while true; do
  echo "=== $(date -Ins)"
  ip -details -statistics link show can0
  ip -details -statistics link show can1
  sleep 0.2
done > ~/openarm_captures/s1_power/linkshow.txt
```

`-statistics`가 RX/TX 패킷·오류 수를 준다. 인터페이스를 2개로 좁히는 이유는 1차 시도에서 39초
캡처가 106KB였기 때문이다 — `lo`·`wlan`·`tailscale`을 매초 덤프한 잡음이었다.

터미널 C — **기준 트래픽.** 1차 시도에 없었던 것이고, 없으면 시험이 성립하지 않는다:
```bash
while true; do cansend can0 7FF#0100CC0000000000; sleep 0.05; done
```

`0x7FF` + 3번째 바이트 `CC` = **Refresh(상태 요청)**, J1(send ID 0x01) 대상이다
(`03-모터-설정.md:167`). **읽기 전용이다** — 플래시를 소모하는 파라미터 쓰기(`0x55`)도, 토크
인가(`0xFC`)도, 영점(`0xFE`)도 아니다. `NFR-MOT-003`의 감사 대상 목록에 `CC`가 없는 것이 그 확인이다.

#### 누르기 전 확인 — 이걸 안 하면 또 판정 불가가 된다

`candump`에 **J1 master ID(`0x11`) 응답 프레임이 돌아오는지** 본다.

🔴 **응답이 없으면 E-Stop을 누르지 않는다.** 누르기 전 침묵과 누른 뒤 침묵이 구별되지 않아
1차 시도와 같은 결과가 된다. 응답이 없으면 전원·배선·종단저항·모터 ID를 먼저 확인한다.

응답이 확인되면 E-Stop을 누르고, 5초 기다리고, 리셋한다. 그 다음 세 터미널을 `Ctrl+C`로 멈춘다.

#### 판정

세 파일을 저에게 주시면 제가 봅니다. 판정은 셋 중 하나다:

| 결과 | 뜻 | 다음 |
|---|---|---|
| **T-B** | 전원과 CAN이 **같이** 끊겼다. `can state`가 BUS-OFF 또는 ERROR-PASSIVE로 간다 | 설계 전제와 일치. **S-5로** |
| **T-A** | 모터 전원만 끊기고 CAN은 살아 있다. `can state`가 ERROR-ACTIVE에 머물고 오류 카운터가 0이다 | 복구 절차를 다시 정의해야 한다. 제가 처리 후 S-5로 |
| **그 외** | 부분 차단, 또는 아무 반응 없음 | **중단.** 회로가 제대로 연결 안 됐을 가능성 |

#### 즉시 멈춰야 하는 경우

- 버튼을 눌렀는데 **모터 응답 프레임이 계속 들어온다** → 차단이 아예 안 걸렸다
- 버튼을 눌렀는데 **컴퓨터가 재부팅된다** → 로직 전원까지 끊겼다는 뜻이고, 복구 절차가 성립 안 한다
  (1차 시도에서 **해당 없음으로 닫혔다** — 위 표 참조)
- 버튼을 눌렀는데 **아무 것도 변하지 않는다**(응답도 계속 오고 오류 카운터도 0) → 회로가 안 붙어 있다

#### 무효 캡처는 치운다

1차 시도 캡처는 증거가 아니다. 나중에 증거로 오인하지 않게 이름으로 못 박아 둔다:

```bash
mv ~/openarm_captures/s1_power ~/openarm_captures/s1_power_VOID_링크미기동
mkdir -p ~/openarm_captures/s1_power
```

### S-2 ~ S-4 — **연구개발 단계에서는 생략**

원래 여기에 세 단계가 있었다: 도달 포락 전체를 경계하는 하중등급 구속물 설치(S-2),

얻는 것보다 드는 품이 크다는 판단이다.

#### 다만 물리는 그대로다 — 30초짜리 확인

브레이크가 **없다.** 명세 `04-수동-동작.md:38`: *"각 관절에 기계적 스토퍼 존재.
**기계식 브레이크는 없다** — 토크를 끊으면 중력으로 낙하한다."* 그리고 바로 다음 단계인

엔드이펙터 위치에서 떨어진다.

게이트로 두지 않되, S-5 버튼을 누르기 직전 이것만 보면 된다:

- [ ] 팔을 **손으로 잡고 있다** (S-1에서 이미 하고 있는 것과 같다)
- [ ] 팔 **바로 아래**에 노트북·모니터·공구가 없다
- [ ] 그리퍼가 **비어 있다**

이건 절차가 아니라 눈으로 한 번 보는 것이다. 30초면 된다.

### S-5 · E-Stop을 풀면 어떻게 되는가

**무엇을 알아내려는 건가.** E-Stop을 해제했을 때 로봇이 **저절로 다시 움직이기 시작하는지**를 본다.
회로가 자동 복전이면, 소프트웨어가 아무리 조심해도 **회로가 먼저 재개시켜 버린다.**

#### 당신이 하는 일

실제로 전원을 끊는 시험이라 **팔을 잡고 있어야 한다.** 브레이크가 없어서 놓으면 떨어진다.

1. 팔을 **손으로 잡는다** (브레이크가 없어서 놓으면 떨어진다)
2. E-Stop을 누른다
3. **리셋한다**
4. 리셋 직후 팔이 **저절로 움직이는지** 본다 — 움직이면 안 된다
5. 촬영한다 (리셋 순간이 보이게)

#### 판정

| 결과 | 다음 |
|---|---|
| 리셋해도 팔이 **가만히 있다** | **`PG-SAFE-001` 통과.** 3부로 |
| 리셋하면 **저절로 움직인다** | **중단.** 회로가 자동 복전이라 소프트웨어로 못 막는다 |

"안전 게이트 없이는 토크를 못 켠다"가 말이 아니라 코드로 강제돼 있습니다.

### 3-5. 모터 16개를 읽는다 (`PG-RID-001`)

## 4. 3부 — 영점 잡기 (토크는 계속 OFF)

🔴 **이 프로젝트에서 가장 중요한 제약이 여기 있습니다.**

**`connect()`를 호출하면 영점이 파괴됩니다.** 상류 라이브러리의 `connect()`가 내부에서
`set_zero_position`을 부르기 때문입니다. 그래서 우리 코드는 `connect_readonly()`만 씁니다.

즉 **모드를 바꾼다고 다시 연결하면 안 됩니다.** 그러면 지금 자세가 새 영점이 되고, 그 뒤의
모든 각도가 조용히 틀립니다 — 오류 메시지 없이.

#### 당신이 하는 일

1. 팔을 영점 자세로 손으로 맞춘다 (토크 OFF라 손으로 움직여집니다)
2. 영점을 저장한다
3. 저장된 파일을 캡처 폴더에 복사한다

#### 검증

```bash

```

이 검증은 **저장된 영점 파일의 체크섬을 다시 계산해서 대조**합니다. 이번 세션에 고친 결함이
여기 있었습니다 — 체크섬이 비어 있으면 **검증을 건너뛰고 "검증됨" 도장을 찍고 있었습니다.**
지금은 빈 체크섬을 거부합니다.

## 5. 4부 — 첫 토크 ON, 그리고 정지 성능

**여기가 진짜 시작입니다.** 이 시점부터 팔이 스스로 힘을 냅니다.

### 5-1. 토크 ON 전 관문

```bash
python -m backend.torque_bringup.cli --manifest <시작-매니페스트.json>
```

이 명령이 4가지 선행 조건을 검사하고, 하나라도 안 되면 **0이 아닌 코드로 죽습니다.**
그중 하나가 `PG-SAFE-001` 통과 해시입니다.

### 5-2. 정지 성능 측정 (`PG-STOP-001`)

**목표는 20 ms 이내**인데, 이건 **아직 실측이 아니라 목표치**입니다.

🔴 **주의할 함정 하나.** 리그가 20 ms를 못 내면 "그럼 우리 예산을 늘리자"는 유혹이 생깁니다.
그건 하면 안 됩니다 — 그 순간 정지 기준이 **안전에서 나온 값이 아니라 우리 구현의 자백**이 됩니다.
**답은 예산을 늘리는 게 아니라 운영 속도를 낮추는 것**입니다.

#### 명령 `[당신이 직접]`

정지 시각은 **candump의 하드웨어 타임스탬프**로만 신뢰할 수 있습니다 (1 µs 분해능). 그러려면
**`-H`가 반드시 있어야 합니다:**

```bash
candump -ta -x -H any > ~/openarm_captures/stop/candump.txt
```

🔴 **`-ta`만 쓰면 시스템 타임스탬프가 나옵니다.** `candump --help`가 그렇게 적어 놨습니다 —
`-H (read hardware timestamps instead of system timestamps)`. `-t`의 인자(`a`/`d`/`z`/`A`)는
**형식**만 정하고 **시계 출처**는 정하지 않습니다. `-H` 없이 재면 이 문서가 스스로 "믿을 수 없다"고
한 시계로 20 ms 예산을 재게 됩니다. (S-1은 반대로 `-H`를 **쓰지 않습니다** — 거기서는 µs 정밀도가
필요 없고, `linkshow`의 `date -Ins`와 같은 시계여야 대조가 됩니다.)

**이 리그의 제약을 미리 확인해 뒀습니다** (`ethtool -T can0`): `hardware-receive` ✓ ·
`hardware-raw-clock` ✓ 이지만 `Hardware Transmit Timestamp Modes: off` · `PTP Hardware Clock: none`.
즉 **수신 방향만** 하드웨어 타임스탬프가 되고, PTP 동기가 없는 raw clock입니다. `03` §5.7.0의
`clockProvenance`가 단일 시계 도메인을 요구하므로, 송신측 경계 시각을 이 시계와 같은 도메인에 놓는
방법이 먼저 정해져야 합니다. 이건 아직 미해결이고, 정지 예산을 확정하기 전에 닫아야 합니다.

정지를 몇 번 걸고 멈춥니다. 그 다음:

```bash
python -m backend.stopbench.cli ~/openarm_captures/stop/capture.json
```

이 명령은 **판정을 내리지 않습니다** — 목표치가 아직 미확정이라 분해만 해서 보여줍니다.
그리고 정지 경로가 `disable_torque`를 쓰고 있거나 시계 출처를 못 믿으면 **초록으로 보이는
산출물을 찍는 대신 죽습니다.**

## 10. 9부 — 실시간성 측정 (`PG-RT-001`)

```bash
OPENARM_RTBENCH_REAL_FIXTURE=~/openarm_captures/rtbench pytest tests/wp104 -q
```

🔴 **주파수는 통과/실패 기준이 아닙니다.** 측정해서 보여줄 뿐입니다 — 이건 이번 세션에
사용자 판정으로 정해졌고, 코드가 그렇게 되어 있는지 정적 검사가 지킵니다.

**다만 예외가 하나 있습니다.** 충돌 감지 루프는 `K·dt < 2`를 만족해야 합니다. 이건 성능
기준이 아니라 **기능이 성립하는 조건**입니다 — 관측기가 전진 오일러라서, 이걸 어기면
잔차가 느려지는 게 아니라 **발산합니다.**

K = 90 기준으로:

| 루프 속도 | K·dt | 결과 |
|---|---|---|
| 1000 Hz | 0.09 | 수렴 |
| 100 Hz | 0.90 | 수렴 (**채택된 값**) |
| 50 Hz | 1.80 | 겨우 수렴 |
| 20 Hz | 4.50 | **발산** |
| 10 Hz | 9.00 | **발산** (45 → −315 → 2565 → −20475) |

즉 **감지 루프는 45 Hz를 넘어야 합니다** (K/2). 그래서 100 Hz로 정했습니다.

## 12. 🔴 절대 하면 안 되는 것

### 12-1. 페이로드를 매단 채 E-Stop을 시험하지 마라

`PG-SAFE-001`은 **무부하 구성에만** 유효합니다. 매단 순간 무효가 되고 다시 해야 합니다.

### 12-2. 복구 절차 없이 시작하지 마라

전원이 끊긴 뒤 어떻게 되살릴지가 **먼저** 정해져 있어야 합니다. E-Stop을 누르고 나서
"이제 어떻게 켜지?"를 고민하면 안 됩니다.

### 12-3. 시뮬레이션 결과를 물리 안전의 증거로 내지 마라

마찰 모델이 없는 상태의 시뮬레이션 출력은 **예측이 아니라 미검증 코드의 출력**입니다.
낙하 지점 예측이 특히 그렇습니다 — 마찰·접촉 파라미터가 아직 없습니다.

### 12-4. 리그를 바꾸고 이전 통과를 재활용하지 마라

로봇 위치나 카메라 마운트를 옮기면 그 배치에서 잰 값은 더 이상 지금 배치의 증거가 아닙니다.
캡처 폴더를 새로 만들고 다시 잽니다.

### 12-5. "건너뜀"을 통과로 읽지 마라

```
5 passed, 12 skipped
```

이 12개는 **아직 확인 안 된 것**입니다. 환경변수를 안 줬으니 검사가 안 돈 겁니다.
초록색이라고 통과가 아닙니다.

### 12-6. 모드를 바꾼다고 다시 연결하지 마라

`connect()`가 영점을 파괴합니다. 오류 없이, 조용히.

## 13. 통과했는지 어떻게 아나

### 한 단계씩

```bash
pytest tests/<해당-패키지> -q
```

- **초록 (`passed`)** = 통과
- **빨강 (`failed`)** = 실패. 메시지에 어느 값이 얼마나 벗어났는지 나옵니다
- **건너뜀 (`skipped`)** = **아직 확인 안 됨.** 통과가 아닙니다

### 전체

```bash
./scripts/gates.sh
```

13가지 검사를 전부 돌리고 마지막에 `ALL GATES GREEN` 또는 `FAILED: <이름>`을 찍습니다.
**판정은 종료 코드로 합니다** — 출력 꼬리를 눈으로 보고 판단하지 않습니다.

호스팅 CI는 없습니다(연구개발 단계라 제거했습니다). 그래서 **`scripts/gates.sh`에 없는
검사는 아무도 돌리지 않습니다.**

### 기록

각 단계의 캡처·사진·판정은 남깁니다. 나중에 "이 수치 어디서 나왔냐"에 답해야 하고,
리그를 바꾸면 이전 증거를 못 쓴다는 규칙이 있기 때문입니다.
