# 실기 검증 — 무엇을, 어떤 순서로, 누가 하나

이 문서는 **로봇 실물 앞에서 사람이 해야 하는 일**만 다룬다. 코드는 지금 오프라인으로 갈 수 있는
데까지 다 가 있고, 여기서부터는 **물건이 있어야 넘어간다.**

읽는 순서: 0장(지금 당장 막힌 것) → 1장(왜 당신이 해야 하나) → 2장(준비물) → 3장(순서) →
4장(항목별 상세) → 5장(하면 안 되는 것).

## 이 문서에서 쓰는 말

문서·코드에 이미 박혀 있는 말들이라 바꿀 수 없다. 뜻만 한 줄로 적어둔다.

| 말 | 뜻 |
|---|---|
| **게이트** | 통과 못 하면 그 아래 작업이 **코드 레벨에서 막히는** 검문소. 사람이 "됐다"고 넘길 수 없다. `PG-SAFE-001` 처럼 이름이 붙어 있다 |
| **리그(rig)** | 로봇 + 작업대 + 구속물 + 배선까지 합친 **실험 설비 한 벌**. "리그가 바뀌었다" = 그 중 뭐라도 옮겼다 |
| **페이로드** | 팔이 **들고 있는 물건**. 그리퍼에 잡힌 것, 손목에 붙인 것 전부 |
| **잔차** | 기대한 값과 실제로 잰 값의 **차이**. "잔차 ±0.5° 이내" = 오차가 0.5도를 넘지 않아야 한다 |
| **데드맨** | 사람이 **누르고 있는 동안만** 움직이게 하는 스위치. 손을 떼면 선다 |
| **오버런** | 제어 루프가 정해진 주기 안에 일을 **못 끝낸 횟수**. 500Hz면 2ms 안에 끝나야 하는데 넘긴 경우 |
| **p50 / p99** | 측정값을 줄 세웠을 때 **중간값 / 상위 1% 지점**. p99가 크면 "평소엔 빠른데 가끔 훅 느려진다"는 뜻 |
| **하드스톱** | 더 이상 안 돌아가게 **기계적으로 막아둔 끝지점** |
| **도달 포락(reach envelope)** | 팔이 **닿을 수 있는 공간 전체**. 구속물은 이 전체를 감싸야 한다 |
| **롤아웃** | 학습시킨 정책을 **실제 로봇에서 돌려보는 것** |
| **WP-… / FR-… / NFR-… / PG-… / CG-…** | 계획서·명세서의 **항목 번호**. WP=작업 단위, FR/NFR=요구사항, PG/CG=게이트 |

## 0. ✅ 전원 넣기 전에 고쳐야 했던 것 2가지 — 둘 다 끝났다

이 자리에 원래 "전원 넣기 전에는 시작하지 마라"는 항목 두 개가 있었다. **2026-07-28에 둘 다
닫혔다.** 기록으로 남긴다.

### 0-1. 좌우 팔이 뒤바뀌어 있었다 → 고쳤다 (`c73c2df`)

IK가 내놓는 16개 값(**모터 수가 아니라 동결된 액션 벡터의 폭**이다 — 팔당 8슬롯 × 2)은
`오른팔 8 + 왼팔 8` 순인데 우리 계약은 `왼팔 먼저`였고, 그 사이에 순서를
바꾸는 코드가 없었다. 결과적으로 안전 검사기가 **왼팔 값을 오른팔 한계로** 검사했고, 좌우 한계가
반대인 **2번 관절에서만 판정이 정확히 뒤집혔다.**

우리 코드를 전부 계약 순서(왼팔 먼저)로 통일하고, 상류 경계 **한 곳**에서만 변환한다
(`sim/ik/adapter.py`의 `_to_upstream_order`). 세 번째 순서를 만들지 않는 것이 요점이었다.
판별 테스트 `tests/wp0c09/test_arm_order_matches_the_action_contract.py`가 고치기 전 16/16 실패했다.

부수적으로 드러난 것: 재영점 위험을 재던 테스트가 고치기 전 **0 mm**를 재고 있었다(양팔 다 0).
고친 뒤 **43.2 mm**로 측정된다.

### 0-2. 뜻이 안 정해진 요구사항 13개 → 전부 판정하고 구현까지 끝냈다

사용자 판정을 원장(`docs/v1/plan/normalization/ledger.yaml`)에 `NORM-008`~`NORM-014` 7행으로
적재하고 해시를 재발행했다. 그 판정이 요구한 집행 9건도 코드로 들어갔다 —
자세한 것은 `docs/guide/04-판정에서-나온-구현-작업.md`와
`docs/v1/work_log/2026-07-28_판정-구현과-검사가-검사하지-않던-문제.md`.

판정 중 계산으로 잡은 모순 하나를 기록해 둔다: **관측기 이득 K=90과 감지 루프 10 Hz는 양립
불가능하다.** 관측기가 전진 오일러라 `K·dt < 2`에서만 수렴하는데 10 Hz면 `K·dt = 9`가 되어
잔차가 45 → −315 → 2565 → −20475로 발산한다. 감지 루프만 100 Hz(`K·dt = 0.9`)로 두는 안으로
해소했다. 이건 게이트가 아니라 **기능이 성립하는 조건**이다.

**즉 코드 쪽 선행 조건은 없다.** 지금 서 있는 자리는 §4-1(2부 통신·모터 확인)이다 — 1부 안전
게이트와 3부 영점은 이미 끝났다(§3, §4-2).

## 1. 왜 이건 당신이 해야 하나

**로봇은 이 PC에 붙어 있다.** 양팔 14개 모터가 CAN으로 응답하고, 영점이 잡혀 있고, E-Stop을 실제로
눌러 봤다. 그래서 이 장은 이제 "물건이 없다"가 아니라 **"물건은 있는데 사람 손이 있어야 하는 일"**의
목록이다.

리그 사실:

| 항목 | 실측 |
|---|---|
| CAN 어댑터 | PEAK PCAN-USB Pro FD(`0c72:0011`), `peak_usb` 드라이버, **2채널이 한 몸인 듀얼채널 장치 1개**, `clock 80000000` |
| 채널 ↔ 팔 | **`can0` = 왼팔, `can1` = 오른팔.** 이름을 믿은 게 아니라 실제로 움직여서 확인했다 |
| 모터 | **팔당 7개**(send id `0x01`~`0x07`), 양팔 14개. 그리퍼 자리(`0x08`)는 **응답 0/20** — 이 리그는 그리퍼가 없는 `fixed_spatula` 빌드다 |
| 영점 | 14개 전부 raw 32767. 잔차 **0.0109°** — 이건 오차가 아니라 **바닥값**이다(아래 §4-2) |
| E-Stop | 눌렀을 때 모터 전원과 CAN이 **같이** 끊긴다(T-B). 리셋해도 팔이 스스로 움직이지 않는다 |
| 뎁스 카메라 | Stereolabs **ZED Mini**. RealSense는 없다. 지금 USB 링크가 12 Mbit/s 풀스피드에 HID 인터페이스만 노출하고 있고, `pyzed`도 설치돼 있지 않다 |

여전히 사람이 해야 하는 것:

- **`ip link set`은 제가 못 칩니다.** 비밀번호 없는 sudo가 없어서 CAN 링크를 올리는 건 사람이
  칩니다. 안내서 05가 그런 명령에 `[당신이 직접]`을 붙여 표시한다. 같은 이유로 가상 CAN(vcan)도
  못 만든다.
- **어댑터가 1개라 채널이 2개다.** 계약 고정 이름은 4개(`oa_fl`/`oa_fr`/`oa_ll`/`oa_lr`)이고
  `FR-CON-005`는 **동일 VID/PID 어댑터 2개**를 전제한다. 팔로워 양팔에는 2채널로 충분하고,
  두 번째 어댑터는 텔레오퍼레이션(리더암) 단계에서 필요해진다.
- **udev 규칙의 어댑터 축은 USB 경로로 갈리지 않는다.** 두 채널이 같은 `ID_PATH`
  (`pci-0000:80:14.0-usb-0:10.3.1.2:1.0`)에 있어서, 둘을 구분하는 값은 **`dev_id`(`0x0` / `0x1`)**다.
  경로로 규칙을 쓰면 두 채널에 같은 이름이 붙는다.

RTX 5080이 있어서 **시뮬레이션·학습·AI는 여기서 다 검증됐다.** 남은 것은 팔을 실제로 움직이는
단계와 카메라다.

### 역할 분담

| 제가 하는 것 | 당신만 할 수 있는 것 |
|---|---|
| 검사 프로그램(하네스) 작성·실행 | **물리 E-Stop 버튼 누르기** |
| 캡처한 데이터 자동 판정 | **토크가 켜지는 동안 팔을 두 손으로 받쳐 들기** |
| 로그·증거 정리 | **전원 꺼진 팔을 손으로 잡아 자세 맞추기** |
| 수치 계산·통과/실패 판정 | **체커보드 들고 카메라 앞에서 움직이기** |
| 실패 시 원인 분석 | **`sudo`가 필요한 명령 치기** (`ip link set`) |
| — | **"이 자세가 안전한가" 최종 판단** |

계획 문서의 표현으로는 `Human-assisted-HW`(사람이 손을 대고 프로그램이 돈다)와
`Human-judgment`(최종 판정은 사람)다.

### 알아둘 것

- **팔에는 브레이크가 없다.** 명세 `docs/v1/spec/04-수동-동작.md:38` — *"기계식 브레이크는 없다 —
  토크를 끊으면 중력으로 낙하한다."* 전원이 끊기는 모든 단계에서 팔을 손으로 받쳐야 하는 이유가
  이 한 줄이다.
- **E-Stop 시험은 페이로드를 매단 채 하지 마라.** 이유는 5장에.
- 리그(작업대 배치, 마운트, E-Stop 배선)를 **바꾸면 안전 게이트를 처음부터 다시** 해야 한다.
- **버스에 없는 모터를 부르지 마라.** 없는 모터는 오류를 돌려주지 않고 그냥 침묵하고, 송신 오류
  카운터가 올라가 채널이 `ERROR-PASSIVE`로 떨어진다. 이 벤치에서 **16프레임 만에 양 채널이 전이**했다.
  그러면 실재하는 7관절까지 같이 열화된다 — 없는 그리퍼는 빠진 기능이 아니라 팔 전체의 고장 주입원이다.

## 3. 순서

순서를 바꾸면 안 된다. 이유는 각 부에 적어뒀다.

```
1부  물리 안전 게이트 (PG-SAFE-001)  ← 토크 켜기 전. 이거 통과 못 하면 아래 전부 차단   [끝남]
        ↓
2부  통신·모터 확인 (토크 계속 OFF)
        ↓
3부  영점 잡기 (토크 계속 OFF)                                                        [끝남]
        ↓
4부  첫 토크 ON
        ↓
5부  움직임 안전 (충돌·반응·마찰)
        ↓
6부  카메라·시간동기
        ↓
7부  텔레오퍼레이션
        ↓
8부  데이터 수집 → 학습 → 평가
```

### 1부 — 물리 안전 게이트: **이게 첫 관문이다**

프로젝트가 `PG-SAFE-001` 이라 부르는 것. 상세 절차는
`docs/v1/plan/04-리스크-및-안전-브링업-게이트.md` §4.3에 6요소(에이전트가 할 일 / 사람이 할 일 /
중단조건 / 안전 초기상태 / 산출증거 / 재개지점)로 다 적혀 있다. 여기서는 사람이 뭘 하는지만 정리한다.

**코드가 실제로 막고 있는 것과, 아직 확인 안 된 것을 구분해서 적는다.**

- 막고 있음(확인): 통과 기록이 없으면 토크 브링업이 **시작 자체를 거부**한다
  (`backend/torque_bringup/preconditions.py`). 5개 사전검사 중 하나라도 실패하면
  토크 인가가 거부된다(`backend/preflight/gate.py:49`).
- 🔴 **아직 확인 안 됨**: 이번 검토에서 *"검사기는 있는데 실제 실행 경로에 안 걸려 있는"* 사례가
  여러 건 나왔다. 예를 들어 충돌 래치를 갱신하는 함수가 **프로덕션에서 한 번도 호출되지 않아**
  충돌 판정이 항상 "충돌 없음"으로 고정돼 있다(미수정, 상세는 작업 로그 D-5).
  즉 **"게이트가 코드에 있다"와 "게이트가 실제 경로를 지킨다"는 다르다.**

→ 그래서 **소프트웨어 차단을 믿고 사람이 손을 떼면 안 된다.** 1부 전 단계에서 사람이 팔을
지지하는 이유가 이것이다. 진짜 안전장치는 물리 E-Stop 버튼과 구속물이다.

**들어가기 전 조건**: 정전·비상정지 후 복구 절차(RC-1~RC-5)가 **먼저 코드로 존재하고 검증돼야**
한다. 이유는 아래 5장에 있다.

**게이트 단계는 S-1과 S-5 둘이다.** 원래 다섯이었는데 S-2(하중 정격을 문서로 진술하는 구속물)·
S-3(낙하 구역 비우기)·S-4(무부하 확인)은 **사용자 결정으로 게이트에서 뺐다** — 연구개발 단계에
비해 무겁고, 얻는 것보다 드는 품이 크다는 판단이다. 셋은 **눈으로 확인하는 조언**으로 남는다
(아래 표 아래에 있다). 게이트로 되돌리지 않는다.

| 단계 | 사람이 하는 일 | 무엇을 알아내나 | 이 리그의 결과 |
|---|---|---|---|
| **S-1** 전원 도메인 | 팔을 **손으로 잡고**, 지시받은 시각에 E-Stop 버튼을 누른다. **손을 떼지 않는다** | E-Stop이 모터 전원과 CAN을 **같이** 끊는지 | **T-B — 같이 끊긴다.** 모터 응답 147/s가 **11.26초**에 0이 되고, 양 채널이 `ERROR-ACTIVE` → `ERROR-PASSIVE`로 걸어갔다. 호스트는 35초 연속 살아 있었고, 리셋 후 7/7 모터가 복귀했다 |
| **S-5** E-Stop 리셋 거동 | E-Stop을 작동시키고 리셋한다. 리셋 순간 팔이 스스로 움직이는지 본다 | 회로가 자동 복전인가 | **자동 복전이 아니다.** 리셋해도 팔이 스스로 움직이지 않는다 — `FR-SAF-057` 성립 |

**S-5 버튼을 누르기 직전 30초, 눈으로만 보는 것** (게이트 아님):

- 팔을 **손으로 잡고 있다**
- 팔 **바로 아래**에 노트북·모니터·공구가 없다
- 팔에 매달린 것이 없다

브레이크가 없어서 전원이 끊기면 팔은 그냥 떨어진다. 이건 절차가 아니라 한 번 둘러보는 것이다.

**다시 해야 하는 때**: 마운트·페이로드·E-Stop 배선·작업대 위치 중 **하나라도 바뀌면** 무조건
재실행. 위 결과는 지금 구성에만 유효하다.

### 4-0. 공통: 어떻게 돌리나

각 항목은 이미 **검사 프로그램이 다 짜여 있고, 데이터만 없어서 건너뛰기(skip) 상태**다.
실기에서 데이터를 캡처해 폴더에 넣고 환경변수로 그 폴더를 가리키면, 그 순간 검사가 실제로 돈다.

```bash
cd ~/workspace/bh_open_arm
source .venv/bin/activate

# 예: CAN 락 검증
export OPENARM_LOCK_REAL_FIXTURE=/경로/캡처폴더
pytest -q tests/wp0b01/test_reverify_hook.py
```

환경변수를 안 걸면 **"건너뜀 + 이유"** 로 표시된다. 이건 정상이다 — 가짜로 통과시키지 않는다는
뜻이다. 걸면 실제 판정이 나온다.

폴더에는 보통 **캡처한 원본 파일들 + `expected.json`**(기대값)을 넣는다. 항목마다 파일 이름이
다르고, 건너뛸 때 나오는 메시지에 **정확히 뭘 넣어야 하는지 적혀 있다.** 먼저 그 메시지를 읽어라:

```bash
pytest -q tests/wp0b01/test_reverify_hook.py -rs   # -rs = 건너뛴 이유 출력
```

🔴 **환경변수를 걸었는데 아무 검사도 안 열리는 훅이 일곱 개 있다.** 아래 표에 `[미연결]`로
표시해 뒀다. 그 일곱은 읽는 코드는 있는데 테스트가 그 값을 안 본다 — 걸면 pytest가 그냥 초록으로
끝나고, **그 초록에는 당신 캡처가 한 글자도 안 들어 있다.** 어느 훅이 지금 실제로 도는지는
**안내서 05 §13-1 대조표 한 곳**에만 있고, 그 표는 `tests/wp2c03/test_guide_hook_table.py`가
코드와 대조한다. 표가 코드보다 뒤처지면 게이트가 죽는다.

### 4-2. 3부 — 영점 잡기 (토크 계속 OFF)

**이 리그에서는 끝났다.** 14개 모터 전부 raw 32767, 잔차 **0.0109°**, 그리고 전원을 껐다 켜도
살아남았다. 절차는 리그를 다시 만졌을 때를 위해 아래에 남긴다.

🔴 **0.0109°는 오차가 아니라 바닥값이다.** 모터가 각도를 16비트로, ±12.5 rad 범위에 걸쳐 담기
때문에 한 눈금이 0.0219°다. 0.0109°는 정확히 그 **반 눈금** — 이보다 작은 값은 표현 자체가
안 된다. 다음 사람이 이걸 "고쳐야 할 오차"로 보고 다시 잡지 않게 여기 적어 둔다.

**매다는 자세가 곧 URDF 0도다.** 전 관절 0도에서 정기구학을 풀면 끝점이 `z = 0.904 m`,
`y = ±0.1535 m`에 온다. 즉 **토크를 끄고 그냥 늘어뜨리면 그게 0 자세다.** 지그를 만들어 맞출
필요가 없다.

프로젝트에서 `RESUME-1-02-ZERO` 라고 부르는 재개 지점이 이것이다.

**사람이 하는 일 (순서 고정):**

1. **전원이 꺼진 상태에서** 팔을 손으로 움직여 기준 자세(rest)에 맞춘다. 화면에 기준 자세 사진과
   3D 뷰가 뜬다.
2. 하드스톱(기계적 끝)에 살짝 붙여 기준면을 만들거나, 그냥 늘어뜨린다. 어느 방법을 썼는지
   기록된다(`zero_method`).
3. 화면에서 **명시적으로 "영점 설정"을 누른다.** 여기서만 0xFE(영점) 신호가 나간다.
4. 프로그램이 다시 읽어서(readback) 실제 각도와 기대 각도의 차이를 관절별로 계산한다.
   **관절당 ±0.5° 이내**여야 한다. 넘으면 다시 한다.
5. **전원을 껐다 켠 뒤 다시 연결**해서 영점이 살아남았는지 확인한다.
   - 살아남으면: 영점 영속성 확정 (**이 리그의 결과**)
   - 안 살아남으면: "매 전원 세션마다 영점 다시 잡기" 강제 플래그가 켜진다
   - **둘 다 유효한 결과다.** 안 살아남는다고 실패가 아니라, 그 사실을 확정하는 게 목적이다

| 환경변수 | 테스트 | 사람이 하는 일 |
|---|---|---|
| `OPENARM_CALIBRATION_REAL_FIXTURE` | `tests/wp3b13` | (카메라 보정과 공유 — 6부 참조) |
| `OPENARM_HOME_HARDSTOP_FIXTURE` | `tests/wp2d07` | 하드스톱 기준 홈 위치 캡처 |
| `OPENARM_GRIPPER_REAL_FIXTURE` | 없음 — 훅 직접 호출 | **이 리그에는 해당 없음** — 그리퍼가 없다. 아래 참조 |

> **그리퍼 끝점은 지금 잡을 수 없고, 잡을 필요도 없다.** 이 리그는 `fixed_spatula` 빌드라 `0x08`에

#### 🔴 정지에 걸리는 시간은 재지 않는다

**정지에 걸리는 시간(`PG-STOP-001`)은 이 리그에서 재지 않는다.** 이유가 둘 겹친다.

1. **그 숫자가 없다고 못 만드는 기능이 없다.** 사용자 판정이다.
2. **이 리그는 그 숫자를 정직하게 잴 수 없다.** `ethtool -T can0`이
   `Hardware Transmit Timestamp Modes: off` · `PTP Hardware Clock: none`이라고 답한다 —
   이 어댑터는 **보낸 프레임에 시각을 못 찍는다.** 정지 시간은 "데드맨을 놓은 순간"과 "정지
   프레임이 버스에 나간 순간"의 차이인데, 앞의 시각은 소프트웨어 시계에서만 나온다. 서로 맞춰
   놓지 않은 두 시계를 빼면 나오는 건 측정이 아니라 지어낸 숫자다.

**되살리려면** 셋 중 하나가 필요하다: 송신 하드웨어 타임스탬프를 주는 CAN 어댑터, 양쪽 시계를
맞춰 줄 PTP 하드웨어 시계, 또는 데드맨 릴리즈와 프레임 엣지를 **하나의 카운터로** 찍는 별도
GPIO 마커 배선. 그날 `PG-STOP-001`이 다시 판정 가능해진다.

남아 있는 것은 시계가 필요 없는 두 가지고, 둘 다 오프라인에서 돈다:

```bash
python -m backend.stopbench.cli        # 정지 경로 4단 형상 + disable_torque 부재 정적검사
```

정지 경로가 **토크를 끊고 있으면** 이게 죽는다. 브레이크가 없으니 토크를 끊는 정지는 정지가
아니라 낙하다 — 이 판정에는 시계가 필요 없고, 그래서 지연 실측을 걷어내도 남는다.

## 5. 🔴 절대 하면 안 되는 것

### 5-1. 페이로드를 매단 채 E-Stop을 시험하지 마라

`docs/v1/plan/04-리스크-및-안전-브링업-게이트.md` §4.4가 이것만으로 한 절을 쓴다.

무엇이 일어나는지 순서대로:

1. E-Stop → 모터 전원 차단 → **팔이 떨어진다** (여기까지는 시끄럽고 눈에 보인다)
2. 그다음 4~8단계는 **전부 조용하다** — 영점이 깨지고, 그 위에서 잡은 마찰 데이터가 오염되고,
   그 데이터로 만든 모델이 틀리고…
3. 그리고 오염은 **마찰 데이터를 뽑는 시점이 아니라 그걸 쓰는 시점**에 드러난다. 즉 몇 단계 뒤에.

→ S-5 직전 30초 눈확인에 "팔에 매달린 것이 없다"가 들어 있는 이유가 이것이다(3장). 게이트로
잡지 않을 뿐, 물리는 그대로다.

### 5-2. 복구 절차 없이 시작하지 마라

정전이나 E-Stop 이후 어떻게 복구하는지가 **먼저 코드로 존재하고 검증돼야** 안전 게이트를
시작할 수 있다. 핵심 5가지(`RC-1`~`RC-5`):

| | 요구 | 왜 |
|---|---|---|
| RC-1 | 전원 재인가 후 **모터를 켜기 전에** 전 관절 위치부터 읽는다 | 어디 있는지 모르고 켜면 안 된다 |
| RC-2 | 영점이 살아있는지 **기대값과 실측값의 차이**로 검사, 허용치를 넘으면 다시 잡으라고 요구 | |
| RC-3 | **떨어진 자세가 충돌 상태인지 3D로 판정.** 충돌이면 자동 복귀 금지, 사람이 손으로 푼다 | 충돌 상태에서 자동으로 움직이면 부순다 |
| RC-4 | E-Stop 해제 후 **자동으로 따라가기 재개 금지.** 첫 명령의 목표 위치는 **반드시 실측 각도** | 상류 라이브러리에 `q_des=0`을 풀 게인으로 1프레임 쏘는 버그가 있다(공개 이슈 #66) — 그대로 두면 팔이 튄다 |
| RC-5 | E-Stop 후 **논리 세션을 새로 열지 않는다.** 통신만 다시 여는 별도 연산(`reopen_transport()`)을 쓴다 | 다시 연결하면 자동 영점이 돌아 영점이 날아간다 |

### 5-3. 시뮬레이션 결과를 물리 안전의 증거로 내지 마라

마찰 모델이 식별 안 된 상태의 시뮬 출력은 예측이 아니라 **미검증 코드의 출력**이다. 낙하 지점
예측이 특히 그렇다 — 마찰·접촉 파라미터가 아직 없다. 시뮬은 시각화 보조다.

### 5-4. 리그를 바꾸고 이전 통과를 재활용하지 마라

마운트·페이로드·E-Stop 배선·작업대 위치 중 하나라도 바뀌면 안전 게이트 재실행이다.
어디부터 다시 하는지는 `docs/v1/plan/04-리스크-및-안전-브링업-게이트.md` §4.5
"재실행 진입점 규칙" 표에 있다.

### 5-5. 없는 모터를 부르지 마라

`0x08`(그리퍼)은 이 리그에 없다. 부르면 오류가 아니라 **침묵**이 돌아오고, 송신 오류 카운터가
올라가 채널이 `ERROR-PASSIVE`로 떨어진다 — 실측으로 16프레임이면 양 채널이 넘어간다. 그러면
멀쩡한 7관절까지 같이 열화된다. 폴링 대상의 정본은 장착된 도구가 정한다
(`backend/endeffector/tools.py`의 `EndEffectorProfile.motor_send_ids`), 등록부
(`backend/can/rid/layout.py`의 `ARM_SEND_IDS`)가 아니다.

## 6. 통과했는지 어떻게 아나

### 각 항목

```bash
export OPENARM_<항목>_REAL_FIXTURE=/캡처/폴더
pytest -q tests/<해당폴더> -rs
```

- 초록 = 실제 데이터로 검사가 돌아서 통과
- 빨강 = 실제로 실패. 메시지에 어느 값이 얼마나 벗어났는지 나온다
- 건너뜀(skip) = **아직 데이터가 없다.** 통과가 아니다

### 전체

```bash
./scripts/gates.sh        # 게이트 13종 전부. 판정은 종료 코드로 한다
```

호스팅 CI는 없다(연구개발 단계라 제거). **`scripts/gates.sh`의 목록이 곧 계약이다** —
거기 없는 검사는 아무도 돌리지 않는다.

### 기록

각 단계의 증거(로그·캡처·판정)는 남겨야 한다. 나중에 "이 수치 어디서 나왔냐"는 질문에 답할 수
있어야 하고, 리그를 바꾸면 이전 증거는 **못 쓴다**는 규칙이 있기 때문이다.
