*"포트를 동적으로 잡는 식으로 하라니까 또 고정식으로 했네"* — 카메라 슬롯 바인딩.

## 2. `--arm real` — 무엇이 이미 있었고 무엇이 없었나

`BiOaOpenArmFollower`(`openarm_follower_oa.py:1166`)가 이미 완성돼 있었다.
`connect_readonly(lock_manager)` · `get_observation()` · `disconnect()` 전부 있고,
`OaOpenArmFollower.__init__` 은 **`port` 를 생성자 인자로 받는다** — 그 독스트링이
`PORT_BY_SIDE` 를 *"a placeholder rather than an identification"* 이라고 명시한다.

없던 것 셋. 전부 결함이고 전부 이번에 닫았다.

### ① `get_observation()` 은 `GuardSample` 을 못 나른다

`ArmSession.tick` 이 요구하는 `ArmFrame` 은 `(각도, 토크, GuardSample)`(`session.py:58`)인데
`get_observation()` 은 평평한 채널 dict 다. 진짜 guard 를 만드는 `_poll_states()`(`:1018`)는
private 이고 `send_action` 에서만 불린다.

그대로 두면 실기 리더가 dummy 처럼 `GuardSample.healthy()` 를 박아야 한다. dummy 에선 그게
정직하다 — `arm.py` 가 이유를 적어놨다. 실기에선 **정반대**다: guard 의 네 필드
(`observation_present`·`bus_read_ok`·`lock_acquired`·`residual_exceeded`)가 전부 실제로
실패할 수 있는 것들이고, 데드맨과 래치가 그걸 읽는다. 없는 고장을 지어내는 것과
있는 고장을 숨기는 것은 같은 결함의 두 방향이다.

→ `OaOpenArmFollower.read_frame()` 신설. `_poll_states` 를 그대로 `Deg`/`Nm` 로 감싼다.
한 번 호출 = 한 번 왕복이므로 pose 와 torque 가 같은 순간을 말한다.

### ② 종료할 때 아무도 안 끊는다

`build_arm_session` 이 `robot.connect()` 만 하고 `disconnect()` 는 어디서도 안 불렸다.
dummy 는 무해하다. 실기는 Ctrl-C 로 서버를 내려도 모터 14개가 인에이블인 채 남는다.
통신두절 워치독이 결국 떨어뜨리지만 그건 **죽은 프로세스**를 위한 백스톱이지 내가 고른
종료를 위한 것이 아니다.

→ `build_arm_session` → `build_arm_backend`, 반환형이 `ArmBackend(session, close)`.
`serve_until_stopped` 가 틱을 세운 **뒤에** 닫는다. 순서가 assertion 이다 — 먼저 닫으면
리더가 사라진 소켓을 읽는다.

### ③ `serve.py` 의 시동 경고가 `real` 에서 거짓말이 된다

```python
print(f"arm backend {args.arm!r} — the state board carries synthetic readings, not an arm.")
```

`dummy` 뿐일 땐 참이었다. `real` 이 생기면 실제 팔을 읽으면서 합성값이라고 말한다.
`ARM_BACKENDS_ON_HARDWARE` 로 갈랐고, 실기 쪽 문안은 반대 사실을 말한다 — 버스가 열려
있고 모터가 통전됐다는 것.

### 통전은 숨기지 않는다

`connect_readonly` 의 독스트링이 이미 적어놓은 사실을 코드와 시동 문구가 되풀이한다:
`DamiaoMotorsBus.connect()` 의 핸드셰이크가 등록된 전 모터에 `CAN_CMD_ENABLE`(0xFC)를 보내고
응답을 요구한다. kp·kd·tau 가 0 이라 잡는 힘은 없지만 **한 프레임이면 움직인다.**

### 채널은 추측하지 않는다

`resolve_arm_channels()` 가 `can_binding.json` 을 읽고 지금 있는 채널에 맞춘다. 못 맞추면
거절하고 `canbind_session.sh` 를 이름으로 지목한다. "첫 번째 CAN 인터페이스"로 떨어지는
폴백은 팔이 움직이기 전까지 정답과 구분되지 않는다.

`BiOaOpenArmFollower` 에 `ports` 인자를 추가해 `_build_arm` 까지 내려보냈다. 팔을 주입하는
방식이 아니라 인자를 통과시키는 방식인 이유: 공유 `DropCounter` 조립이 `_build_arm` 에 있고,
주입하면 그게 호출자마다 복제된다.

## 3. 카메라 — 발견은 이미 동적이었고 배정만 고정이었다

`backend/camera/portpath.py` 는 전부 런타임 조회다 — `enumerate_capture_nodes`(`:139`)가
`/dev/video*` 를 전수 열고 `query_capture_node`(`:94`)가 `VIDIOC_QUERYCAP` 으로 `bus_info` 를
읽는다. 고정이던 건 `cli.py:88-94` 의 여섯 줄, **어느 포트가 왼손목인가**뿐이었다.

그 여섯 줄이 만드는 실패는 조용하다. 손목 두 대가 같은 시리얼
(`Arducam_202500915_0001`)을 보고하므로 좌우가 바뀌어도 영상에 안 보인다.

### 무엇이 됐나

| | |
|---|---|
| `backend/camera/rig.py` | `SlotProfile`(포맷·컨트롤, 슬롯의 성질) / `CameraBinding`(슬롯→포트, 이 벤치의 오늘) 분리. 원자적 저장·검증 로드·`resolve_slots` 거절 |
| `backend/camera/identify.py` | 렌즈를 가리면 어느 뷰가 어두워지나. `ops/hw/canbind/identify` 와 같은 모양 — 베이스라인 읽고, 운영자에게 시키고, 다시 읽고, 판정 |
| `v4l2_source.BrightnessProbe` | 식별 전용 열기. `open_frame_source` 를 안 탄다 — 그건 **슬롯의** 포맷을 강제하는데, 지금 알아내려는 게 슬롯이다 |
| `oa-camcap --bind` | 슬롯마다 한 라운드. 전부 풀려야 저장한다 |

판정은 한쪽으로만 기운다. 하나가 `COVERED_DROP_FRACTION`(0.4)을 넘고 **나머지 전부가**
`STEADY_DROP_FRACTION`(0.15) 안에 있어야 한다. 둘 다 어두워지면 손이 둘을 스쳤거나 방 조명이
바뀐 것이고, 큰 쪽을 고르는 게 이 모듈이 막으려는 유일한 실패다.

`COVERED_DROP_FRACTION` 이 0.5 가 아니라 0.4 인 이유: ZED-M 은 스테레오라 한쪽 렌즈만
가리면 평균이 절반 근처까지만 떨어진다.

## 5. 이번에 안 한 것, 그리고 왜

**버스 뮤텍스를 안 지었다.** `ArmSessionRunner` 스레드가 버스를 만지는 유일한 쪽이고
(`session_runner.py:13-16` 이 그 단일 writer 성질이 보드의 락 없는 publish 를 떠받친다고 적는다),
`STOP_HOLD_SENDER` 는 여전히 null 이라 명령 경로가 없다. 쓰는 쪽이 하나면 조율 기계는
`CLAUDE.md` §4b 가 짓지 말라는 것이다. **정지 루프가 붙는 회차에 이게 두 번째 writer 가 된다**
— 그때 명령은 이 루프를 통해서 가야지 옆에서 가면 안 된다. `RealSideReader` 의 스레딩 절에
적어뒀다.

**`node_by_port`(`portpath.py:196`)의 프로덕션 호출자가 0이 됐다.** 해소는 `rig.check_binding`
으로 옮겼다. 자기 테스트는 그대로 있다. 삭제 제안 안 함 — 사용자 확정(2026-08-24).
