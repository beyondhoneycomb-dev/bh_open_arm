# 2026-08-25 — 거절은 닫힘 코드로 도착하고 있었고, 브라우저가 그걸 버렸다

`STATUS.md` §8 의 1번(「`onError` 배선」)을 실행하려고 경로를 열었더니, 그 항목의 **전제가 틀려
있었다.** 고쳐야 할 결함은 있었지만 STATUS 가 지목한 자리에 있지 않았다. 이 문서는 무엇이
틀렸는지, 실제 결함이 무엇이었는지, 무엇을 고쳤는지를 적는다.

---

## 1. STATUS §8 1번이 틀린 두 곳

STATUS 원문:

> `wsClient.ts:362-364` 가 `onError` 를 부르는데 `ws/defaults.ts` 가 안 넘긴다.
> 백엔드 결함 프레임이 도착해서 **버려지고 있다.** 계약 변경 불필요.

### ① `ws/defaults.ts` 는 막고 있지 않다

`frontend/src/ws/defaults.ts:15-18` 의 `WsClientOverrides` 는
`Partial<Omit<WsClientOptions, "socketFactory" | "decoderPort">>` 이고, `onError` 는
`WsClientOptions` 의 멤버다(`wsClient.ts:83`). `createDefaultWsClient` 은 그 오버라이드를
`new WsClient({...})` 로 그대로 펼친다(`defaults.ts:40-46`). 즉 `onError` 는 **이미 통과한다.**

넘기는 쪽이 없을 뿐이다. `App.tsx:24` 가 `createDefaultWsClient` 을 **인자 없이** 부르고,
`RealtimeProvider` 의 `createClient` 는 `() => TClient` 라서 콜백을 놓을 자리가 없었다.
막힌 지점은 `defaults.ts` 가 아니라 셸이었다.

### ② 결함 프레임은 도착하지 않는다 — 그런 프레임이 없다

`CTR-WS@v2` 의 프레임은 열 종이고 그중 error 는 없다
(`contracts/ws/schema.py:223-338`). 백엔드는 이걸 문장으로도 적어 두었다:

> `CTR-WS@v2` declares no server-to-client error frame, so there is no envelope a refusal
> could travel in; adding one would put an eleventh frame type in a frozen contract.
> — `backend/ws/dispatch.py:28-31`

백엔드의 송신 경로는 전수로 둘뿐이다 — `backend/ws/sink.py:121` 의 `send_bytes`(카메라 프리뷰)와
`backend/ws/app.py:198` 의 `send_json(outcome.reply)`. 후자가 싣는 것은 `FRAME_TABLE` 의 응답
프레임(`lease_grant`·`lease_reject`·`rearm_*`)이다. `backend/ws/` 와 `contracts/ws/` 어디에도
`severity` 라는 낱말이 없다.

그러므로 `decoder.ts:34-41` 의 error 분기, `wsClient.ts:362-364` 의 `onError`,
`ws/errors.ts` 전체는 **생산자가 0인 소비자**다. 잇는다고 아무것도 흐르지 않는다.
`CG-G-03g` 가 성립 가능해지지도 않는다.

지우지는 않았다 — 사용자 확정(2026-08-24) 「도달 안 되는 코드 전부 유지」에 해당한다.

### ③ 이 주장이 어디서 왔나 — 맞는 판정을 틀린 쪽으로 뒤집었다

`2026-08-20_다크모드를-지웠다…md` §6b 다. 그 절의 제목이
「`NotificationCenter` 를 "데이터원 0" 으로 적었는데 **틀렸다. 원천은 이미 도착하고 있다**」이고,
STATUS §8 1번은 그 문장을 그대로 옮긴 것이다.

**원래 판정이 맞았다.** §6b 는 프런트 세 파일(`wsClient.ts`·`defaults.ts`·`App.tsx`)만 열고
`backend/ws/` 도 `contracts/ws/schema.py` 도 열지 않았다. 프런트에 소비자가 있다는 사실에서
생산자가 있다고 추론한 것이다.

출처는 같은 문서 §9 가 적어 두었다 — 늦게 도착한 정찰(ui) 에이전트 보고이고, 표에
「**`onError` 가 안 배선돼 결함 프레임이 버려진다**(§6b) — 내 "데이터원 0" 판정을 뒤집었다」로
올라 있다. 대조 없이 채택됐다. §9 의 교훈은 *"기다리지 말고 병행하되 버리지도 말라"* 였는데,
빠진 절반이 있다 — **회수한 보고도 소스로 대조해야 한다.** 백엔드 파일 두 개를 열었으면
그 자리에서 끝났을 일이다.

## 2. 실제 결함 — 서버는 닫힘으로 말하고 있었고 브라우저가 그걸 버렸다

`CTR-WS@v2` 에 error 프레임이 없으니 백엔드는 거절을 **WebSocket 닫힘**으로 답한다.
`backend/ws/constants.py:41-56` 이 그 코드를 소유하고, 아홉 종을 하나씩 나눠 놓았다:

```
4400 UNKNOWN_ROLE      4401 MISSING_SESSION    4402 MALFORMED_FRAME
4403 UNKNOWN_FRAME_TYPE 4404 UNAUTHORIZED_FRAME 4405 WRONG_DIRECTION
4406 REARM_NOT_ISSUED  4407 FORBIDDEN_ORIGIN   4408 COMMAND_UNROUTABLE
```

> One per refusal: a client that cannot tell a bad role from a malformed frame cannot fix
> either. — `constants.py:41-42`

백엔드는 이 채널을 **읽히게 하려고** 두 가지를 더 했다.

1. **`accept()` 다음에 닫는다**(`app.py:171-176`). accept 전에 거절하면 브라우저에는
   맨 HTTP 403 만 남고, 잘못된 role·빠진 세션·그냥 죽은 백엔드가 전부 같은 사건이 된다.
2. **사유를 123 바이트로 자른다**(`app.py:46-64`, `truncate_close_reason`). RFC 6455 §5.5.1 의
   닫힘 페이로드 한계를 넘기면 그 닫힘 프레임 자체가 프로토콜 오류가 되어 사유가 **아예** 도착하지
   않기 때문이다.

그리고 브라우저가 이렇게 받고 있었다:

```typescript
// frontend/src/ws/wsClient.ts:138 (수정 전)
socket.onclose = () => handlers.onClose();
```

코드도 사유도 여기서 소멸한다. 그 다음 `onSocketClose()`(`wsClient.ts:331-343`)는 **조건 없이**
`retryDelayMs` 뒤에 다시 연다.

### 결과 두 가지

**(a) 영구 거절이 1초 주기 무한 재접속이 된다.** 4407(허용 목록에 없는 origin)로 닫히면 브라우저는
같은 URL·같은 role 로 다시 붙고, 서버는 accept 후 다시 4407 로 닫는다. 페이지가 열려 있는 동안
끝나지 않는다. 4408 은 특히 확실하다 — `backend/ws/arm_channel.py:1-14` 가 그것을
*deployment 의 성질*(이 프로세스는 팔을 읽기만 하고 명령하지 않는다)이라고 못 박고, `--arm` 은
기동 인자라 프로세스 수명 동안 변하지 않는다(`backend/config/serve.py:351-357`).

**(b) 운영자에게 아무것도 안 보인다.** `onClose()` 하나가 「서버가 이 연결을 거절했고 재시도는
같은 원인을 다시 밟는다」와 「선이 잠깐 끊겼고 재시도가 답이다」를 동시에 뜻했다. 호출자는 둘을
구분할 수 없었다.

## 3. 고친 것

### 3.1 닫힘 코드를 분류한다 — `frontend/src/ws/closeCodes.ts` (신규)

분류가 **둘**이고, 둘째가 하중을 받는다.

1. **거절인가 transport 인가** — `isServerRefusal`, 범위 판정(4400–4499). 범위인 이유는 백엔드가
   내일 코드를 하나 더 넣어도 transport 집계로 사라지지 않게 하기 위해서다.
2. **재접속이 무의미한가** — `isHandshakeRefusal`, **열거** 판정(4400·4401·4407).

두 번째가 없으면 안 된다. 아홉 코드 중 **셋만 연결에 대한 판정**이다 — `handshake_session`
(`backend/ws/app.py`)이 프레임을 읽기 전에 role·session·Origin 으로 내리고, 그 셋은 클라이언트를
지을 때 URL 과 Origin 헤더로 고정되므로 다음 소켓도 똑같이 닫힌다.

나머지 여섯(4402·4403·4404·4405·4406·4408)은 **보낸 프레임 하나에 대한 판정**이다
(`backend/ws/dispatch.py`, `arm_channel.py`). 그 프레임을 안 보내는 새 소켓은 수용된다.

**이 소켓이 소프트 스톱을 나른다.** `FR-GUI-065` 는 정지를 제어권과 무관하게 손 닿는 곳에 두라고
하고, `backend/ws/arm_channel.py:13-15` 가 4408 에 대해 그것을 직접 적는다 — *"a deployment with no
send path still answers FR-GUI-065"*. 명령 하나가 거절됐다고 채널을 페이지 수명 내내 끊으면 그
보장이 깨진다. 그래서 방향을 코드마다 따로 도출했다:

| | 재접속하면 | 안 하면 |
|---|---|---|
| **핸드셰이크 거절 3종** | 같은 판정을 무한 반복 | 잃을 것 없음 — 소켓이 성립한 적 없어 정지도 실린 적 없다 → **끊는다** |
| **프레임 거절 6종** | 채널이 살아나고 정지가 다시 실린다 | 정지가 리로드까지 사라진다 → **재접속한다** |

두 번째 판정만 열거인 것도 의도다. 모르는 코드는 **재시도 쪽**으로 떨어져야 한다 — 반대로 두면
백엔드가 코드 하나를 새로 넣는 것만으로 그 코드를 만난 페이지 전부에서 정지가 사라진다.

이 코드들은 `CTR-ERR@v1` 이 아니다. `constants.py` 가 스스로 「RFC 6455 의 일부이지 계약의 일부가
아니다」라고 적어 두었고, 그래서 `ws/errors.ts`(CTR-ERR 미러) 옆의 **별도 파일**로 두었다.
닫힘 코드에서 `OA-*` 를 지어내지 않는다는 경계가 파일 경계로 보이는 편이 낫다.

표류 방지는 `closeCodes.contract.test.ts` 가 `backend/ws/constants.py` 를 직접 읽어 대조한다
(`errors.contract.test.ts` 가 `contracts/errors/error_registry.yaml` 을 읽는 것과 같은 방식).

### 3.2 코드와 사유를 끝까지 나른다

| 파일 | 변경 |
|---|---|
| `ws/types.ts:68` | `onClose(): void` → `onClose(code: number, reason: string): void` |
| `ws/wsClient.ts:146` | `socket.onclose = (event: CloseEvent) => handlers.onClose(event.code, event.reason)` |
| `ws/wsClient.ts` `onSocketClose` | 거절이면 `refusalCount` 를 올린다. **핸드셰이크** 거절이면 `dispose()` 로 정지시키고 `onLinkRefused` 를 부르고 재시도하지 않는다. 프레임 거절과 transport 닫힘은 종전대로 재시도 |
| `ws/wsClient.ts` `WsClientOptions` | `onLinkRefused?: (refusal: LinkRefusal) => void` 추가 |
| `ws/wsClient.ts` `WsClientStats` | `refusalCount` 추가. `socketErrorCount`(브라우저측 transport 오류)와 별개다 — 둘은 정반대의 대응을 요구한다 |
| `ws/synthetic.ts` | `FakeSocket.emitClose(code = 1006, reason = "")`. 코드를 안 적은 기존 호출은 전부 transport 를 뜻하게 되어 의미가 유지된다 |

### 3.3 셸까지 잇는다

`RealtimeProvider` 의 `createClient` 를 `() => TClient` 에서
`(hooks: RealtimeClientHooks) => TClient` 로 바꿨다. `RealtimeClientHooks` 는 `onLinkRefused`
하나를 담은 데이터 형상이다.

**콜백으로 넘긴 이유**: 거절은 한 번 일어나고 다시는 바뀌지 않는다. 클라이언트에 읽기 표면을 두면
그 한 번을 잡으려고 페이지 수명 내내 폴링해야 한다.

`createDefaultWsClient` 은 이미 `WsClientOverrides` 를 받으므로 **호출부 변경 없이** 그대로 맞는다.
`App.tsx:21` 의 프롭 타입만 정직해지도록 넓혔다 — 0-인자 함수는 1-인자 타입에 대입되므로 tsc 는
불평하지 않았겠지만, 그러면 타입이 거짓말을 한다.

거절이 오면 `status`가 `"unavailable"`, `reason` 이 `"4407: origin '…' is not on the
control-channel allowlist"` 가 된다. 코드와 사유를 **둘 다** 남기는 이유는, 사유는 사람이 조치할
것이고 코드는 서버 로그와 맞춰 볼 것이기 때문이다. 사유가 빈 문자열이면 코드만 낸다 — 없는 문장을
지어내면 운영자 손에 서버 로그의 무엇과도 대조되지 않는 문장이 쥐여진다.

**새 화면은 만들지 않았다.** `ControlLeaseHost`(`Layout.tsx:50`, 전 화면에 뜬다)가 이미
`status !== "open"` 일 때 `reason` 을 그린다(`ControlLeaseHost.tsx:47-54`).

### 3.4 알림 센터에는 붙이지 않았다 — 의도적

`Notification` 은 `OA-*` 코드와 `CTR-ERR` severity 를 요구한다(`global/notifications.ts:13-22`).
닫힘 코드 4404 는 `OA-*` 가 아니고, 지어내는 것은 이 저장소가 두 곳에서 명시적으로 금지한 행위다:

- `wsClient.ts:327-330` — *"never surfaced as a fabricated OA-* envelope"*
- `decoder.ts:4-6` — *"It fabricates no OA-* code on failure"*

그래서 거절은 **링크 상태**로 남겼다. `NotificationBadge` 는 여전히 고정 빈 배열
(`SafetyBarHost.tsx:50,87`)이고 `CG-G-03g` 는 여전히 성립하지 않는다 — 그건 `CTR-WS@v3` 가
error 프레임을 발행해야 열린다.

## 4. 이 변경이 나쁘게 만든 것

**프레임 거절을 재시도하는 대가**: 소켓마다 재현되는 버그 — 이를테면 서버와 브라우저가 role 을
다르게 아는 상태 — 를 가진 클라이언트는 페이지가 열려 있는 동안 `retryDelayMs` 마다 재접속한다.
그 루프는 조용하지 않다. `refusalCount` 가 그것을 센다. 정지 도달성과 맞바꾼 값이다.

**언제 뒤집히나**: 프레임 거절을 무한 재시도하는 것이 관측 가능한 부하를 만들 때 — 이를테면
`refusalCount` 가 한 세션에서 세 자리로 올라가는 것이 보일 때. 그때는 프레임 거절에 백오프나 횟수
상한을 두는 것이 맞고, 그래도 **0회로 내리지는 않는다**(0회가 정지를 뺏는 쪽이다).

`createClient` 가 인자를 받게 되면서, 클라이언트를 짓는 모든 호스트가 무시해도 되는 훅 객체를
받는다. **타입이 잡아주지 않는다** — 0-인자 함수는 1-인자 타입에 그대로 대입되므로, 훅을 안 읽는
팩토리는 컴파일이 통과하면서 거절 경로만 조용히 잃는다.

**언제 뒤집히나**: 셸이 들어야 할 것이 하나 더 생기고 그것이 반복 발생하는 사건일 때. 한 번뿐인
훅 둘까지는 생성자 인자가 맞고, 반복 발생하는 셋째가 붙는 순간 그건 인자 옷을 입은 이벤트 이미터다.
그때는 클라이언트에 구독 표면을 두는 편이 낫다.

## 7. 계약 세대 표류 — 수리를 시도했고, 어디까지 번지는지 재고 되돌렸다

**증상.** `CTR-ERR` 과 `CTR-CAL` 이 `@v2` 로 동결돼 있는데 파일 안에서는 `@v1` 이라 선언한다
(`contracts/errors/error_registry.yaml:1,11` · `backend/calibration/schema.py:39` ·
`schema.json:3`). 이 저장소가 발행한 세대 셋 중 **둘이 이 단계를 빠뜨렸고 `CTR-WS` 만 지켰다.**

`CI-09` 는 원리적으로 못 잡는다 — 선언된 id 가 **해시되는 바이트 안에** 있어서, 자기를 잘못
부르는 파일도 똑같이 깨끗하게 해시된다. 검사기가 없어서가 아니라 있는 검사기가 볼 수 없는 자리다.

### 7.1 발행은 성립한다

절차대로 세 세대를 실제로 발행했다. 기계가 순서를 강제한다 — 아티팩트만 고치고 freeze 를 부르면
*"declares no frozen glob content in the registry"* 로 거부한다(글롭 조회가 레지스트리의
`produces` 축을 탄다):

```
계획 문서 v2→v3 → ingest 재파종 → 아티팩트 선언 v3 → freeze → 코드 미러 → generate
```

`CTR-ERR@v3`(계획 24곳) · `CTR-CAL@v3`(16곳 + 정규화 원장, `--issue` 재발행) ·
`CTR-PRIM@v2`(50곳) 전부 장부에 올랐고, **177 은 안 움직였다** — 재파종 뒤에는 옛 세대를 소비하는
WP 가 0이라 freeze 가 트리거를 내지 않았고, 형상이 안 바뀌어 재검증할 것도 없었다.

### 7.2 그런데 멈추지 않는다

| 단계 | 왜 딸려 오는가 |
|---|---|
| `CTR-ERR@v3` | `contracts/prim/schema.json` 이 `consumed_contracts` 에 상류 세대를 **리터럴로** 적는다. 파이썬 쪽 `schema.py:72` 는 `CONSUMED_CONTRACTS = (ACTION_CONTRACT_ID, ERROR_CONTRACT_ID, …)` 로 **import 파생**이라 자동으로 맞는데, 손으로 유지하는 JSON 미러가 어긋나 `wp3a00` 미러 테스트가 깨진다 |
| → `CTR-PRIM@v2` | 그 JSON 이 `CTR-PRIM@v1` 의 동결 대상이라 고치려면 범프해야 한다 |
| → 3A 5종 | `CAM`·`CAP`·`TEL`·`WS`·`REC` 의 동결 본문과 reverify 가 `CTR-PRIM@v1` 을 문다 — **실측 12건 실패** |
| → 다시 `PRIM` | `prim/schema.py:20,275,351` 이 `CTR-WS@v1` 을 적는다. `WS` 를 올리면 `PRIM` 이 낡는다 |

**`prim ↔ ws` 순환이라 범프로는 만족 자체가 불가능하다.**

### 7.3 진짜 원인

라벨이 아니다. **동결 아티팩트가 상류의 세대(`@vN`)를 자기 바이트에 다시 적는 것**이다.
import 로 참조하면(`schema.py:72`) 범프를 자동으로 따라가고, 문자열로 박으면 유지할 수 없는
의존이 생기며 순환에서는 아예 만족 불가능해진다.

이 표류는 오늘 생긴 것이 아니다 — `prim/schema.py` 의 `CTR-WS@v1` 은 `CTR-WS` 가 8월에 `@v2` 로
간 뒤로 이미 낡아 있었다. 되돌린 지금도 그대로 있고, 아무도 검사하지 않아서 안 보일 뿐이다.

**같은 결함이 집행층에도 있다**: `registry/checks/ci_03d.py:19` 의
`PRIMITIVE_CONTRACT = "CTR-PRIM@v1"`, `tests/boot01/test_registry.py:239` 의 같은 리터럴.
계약이 올라가면 그 검사기가 **정당한 범프를 위반으로 읽는다** — 오늘 실제로 그렇게 됐다.
(세션 중에 둘 다 생산자의 `produces[]` 에서 파생하도록 고쳤으나, 계약 되돌림과 함께 원복했다.)

### 7.4 되돌린 이유와 남긴 것

카스케이드를 이 회차 안에 안전하게 닫을 수 없다고 판단해 **계약 범프 전부를 되돌렸다** — 빨간
트리를 남기지 않기 위해서다. 되돌린 범위: 장부·계약 인덱스·계획 문서·`contracts/**`·
`backend/calibration/**`·관련 테스트·`ci_03d`. 오늘의 독립 작업(§2·§3 닫힘 코드, §8 배지 규칙)은
남겼다.

`STATUS.md` §6 에 카스케이드 경로와 순환을 표로 박고 출구 셋을 적었다 — (a) 상류 세대 복창을
전부 import 참조로 (b) `@vN` 은 장부에만 두고 아티팩트는 상류 **이름**만 적는 규약 변경
(c) 표시만. (a)·(b) 둘 다 계약층 재발행이 붙는 **사용자 결정 사항**이다.

**이것은 땜빵이 아니라 미완이다.** 무엇이 왜 안 되는지는 추측이 아니라 실행해서 재봤고, 숫자와
파일:줄로 남겼다.

## 8. 배지를 잡는 것은 심각도가 아니라 「무엇이 멈췄나」다

`CG-G-03g` 는 *"ERROR 이상 알림이 ack 전까지 배지 유지"* 라고 적혀 있었고, 구현은 그걸
`severity >= Severity.ERROR` 로 옮겼다. 사용자 판정으로 이 형태를 폐기한다.

**"이상"은 한 줄로 세울 수 있는 순서를 전제한다. `OK/WARN/ERROR/STALE` 은 그런 줄이 아니다.**
`STALE` 은 "얼마나 나쁜가"가 아니라 **"물어봤는데 답이 없다"** 이고(`14:438` 이 ROS 2
`diagnostic_msgs` 의미론만 빌려온다고 적는다), 심각도 셋에 *모름* 하나를 끼워 0·1·2·3 을 매긴
다음 `>= 2` 로 자르면 **"모른다"가 "고장보다 나쁘다"로 계산된다.** 아무도 그렇게 정하지 않았고,
그건 배열 순서였다.

사용자 모델: **뭔가 나면 멈추고, 사람이 리셋을 눌러야 다시 돈다.** 그래서 판정 입력을 바꿨다.

| | 전 | 후 |
|---|---|---|
| 배지 유지 조건 | `severity >= ERROR` | `n.blocking && !n.acked` |
| `severity` 의 역할 | 판정 입력 | **화면에 찍히기만 한다. 분기 0건** |
| 삭제 | — | `BADGE_HOLD_MIN_SEVERITY` · `holdsBadgeUntilAck` |
| 추가 | — | `Notification.blocking` — "이것 때문에 뭔가 잡혀 있다" |

`blocking` 은 발행자가 채운다. 무엇이 실제로 멈췄는지는 발행자만 알기 때문이다.

**임계 자체를 없애지는 않았다.** 전부 잡으면 카메라 프레임 하나 떨어질 때마다 확인을 요구하게
되고, 그러면 운영자는 읽지 않고 누르게 되며 그 순간 이 장치가 죽는다. 바뀐 것은 **구분의 축**이다 —
얼마나 나쁜가에서, 무엇이 멈췄나로.

테스트가 이제 이렇게 단언한다: **아무것도 안 멈춘 `ERROR` 는 배지를 안 잡고, 뭔가 멈춘 `WARN` 은
잡는다.** 변이 2종(부등호 복원 / `blocking` 무시) 각각 4건 RED.
