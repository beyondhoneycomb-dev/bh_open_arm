## 🔴 라우터를 먼저 붙이면 안 된다

`oa-serve` 는 팔 세션을 만들지 않는다. 팔을 잡는 것은 `scripts/torque_session.py:1973` 과

장치는 없다 — `backend/actuation/`·`backend/deadman/`·`backend/ws/` 에서 flock·공유메모리·
소켓·FIFO 전수 검색 0건.

그래서 지금 라우터를 붙이면 이렇게 된다:

```
GUI 정지 → WS stop_hold → oa-serve 안의 SafetyLatch.engage()
                                    ↑ 이 래치를 읽는 팔이 없다
```

정지도 리스 만료도 재무장도 **전부 효과 없는 기계**가 된다. 그리고 `STOP_HOLD_SENDER` 까지

내린다 — 팔은 그대로인 채로. `backendLink.ts:1-5` 가 이름으로 막아둔 것이고(*"a control the
operator believes acted is worse than no control at all — NORM-007"*), **지금 없는 결함을 새로
만드는 일이다.**

올바른 순서는 **팔 세션(래치의 주인) → 라우터 → GUI** 다. 그래서 `serve.py:159`
`mount_websocket_router` 는 아직 `return False` 로 둔다.

## 그래도 남긴 배관 — 어느 순서에서든 필요한 것

### `mount_realtime_channel` 이 loopback 배치를 받는다

`admitted_origins`(`backend/ws/deployment.py:106`)는 두 배치 형태를 다 받도록 지어졌는데
**프로덕션 호출자가 0**이었다. 라우터가 `ControlChannelSecurity` 만 받고
`security.ws.origin_allowlist` 를 직접 읽고 있었기 때문이다. `LoopbackDeployment` 에는 `ws`
속성이 없으므로 `NORM-015` 가 서술한 배치는 **마운트 자체가 불가능했다.**

이제 `security: ControlChannelDeployment` 이고 `admitted_origins(security)` 를 읽는다.

### 명령을 못 보내는 호스트가 조용히 삼키지 않는다

`CommandSink` 가 `None` 을 반환하는 타입이라, 라우팅할 팔이 없는 호스트가 프레임을 받으면
**성공과 구별되지 않았다.** `dispatch.py:82-84` 주석이 그 위험을 이미 적어놨는데 반환 타입이
그것을 표현하지 못했다.

`CommandSink = Callable[..., WsClosure | None]` 로 바꿨다. 라우팅한 sink 는 `None` 을 돌려주고
동작이 전과 같다. 못 하는 sink 는 클라이언트가 받을 close 를 돌려준다 —
`WS_CLOSE_COMMAND_UNROUTABLE = 4408`, `UNAUTHORIZED`(4404)와 **일부러 다른 코드다**: 둘은
운영자에게 정반대를 지시하고, "권한 없음"으로 읽으면 이미 가진 권한을 찾으러 간다.

### 변이 검사가 구멍 하나를 짚었다

새 테스트 4개를 붙이고 변이 3종을 돌렸다.

| 변이 | 결과 |
|---|---|
| `admitted_origins(security)` → `security.ws.origin_allowlist` | 2건 실패 ✓ |
| sink 반환값 폐기(예전 동작) | **처음엔 안 잡혔다** |
| `WS_CLOSE_COMMAND_UNROUTABLE` → 4404 | 1건 실패 ✓ |

두 번째가 이 저장소가 반복하는 양식이다 — 거부 경로에 테스트가 없어서, 거부를 없애도 초록이었다.
명령 프레임을 실제로 보내고 close 코드를 확인하는 테스트를 붙이고 나서 잡혔다.
