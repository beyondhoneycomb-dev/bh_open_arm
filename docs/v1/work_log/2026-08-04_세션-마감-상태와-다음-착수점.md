## 환경 — 실기가 붙었고, 경계가 바뀌었다

옛 기록(“vcan·로봇HW 없음”)은 더 이상 사실이 아니다. 이 벤치에 붙어 있는 것:

| 장치 | 식별 | 상태 |
|---|---|---|
| PCAN-USB Pro FD | `0c72:0011` | 장치는 보이나 **`can0`/`can1` 이 `DOWN`/`STOPPED`** |
| Arducam B0495 ×2 | `04b4:4950` | `/dev/video2`(`usb-0:1.1.1`) · `/dev/video4`(`usb-0:1.1.3.4`) |
| ZED-M | `2b03:f681` HID + `f682` camera | 둘 다 존재 |

**무암호 sudo 가 없다. 그것 하나가 모터 실기 작업 전부를 막는다.** `lsusb` 가 PCAN 을 보여주는
것과 인터페이스가 기동된 것은 다른 사실이고, 진짜 답은 `ip -d link show can0` 의 `state` 다.

기동은 사용자가 직접 해야 한다 — `docs/guide/05-실기-검증-단계별-실행안내.md:289-292`:

```
sudo ip link set can0 up type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can1 up type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can0 txqueuelen 1000
sudo ip link set can1 txqueuelen 1000
```

**카메라는 안 막힌다.** `v4l2-ctl` 이 없고 설치도 못 하지만 `VIDIOC_QUERYCTRL`/`G_CTRL`/`S_CTRL`
을 ctypes+fcntl 로 직접 때리면 값·범위·기본값·`INACTIVE` 플래그를 전부 읽는다. 이번 세션의 카메라
판정이 그 경로로 나왔다. 하드웨어를 주장하는 상수를 검증할 때 이 길을 쓸 것.

통전은 여전히 확정을 받고 한다. `connect_readonly` 조차 핸드셰이크로 전 모터에 `0xFC` 를 보낸다.

## 아직 열려 있는 구조적 문제

**원장 검증기는 여전히 폐기된 인용문의 존재를 요구한다.** 이번엔 산문 주석으로 우회했으나, 다음
판정 이행자는 같은 벽을 만나고 같은 우회가 필요하다는 것을 모른다. 정면 해법은 원장 행에 이행
여부를 두고 검증기가 그에 따라 존재/부재를 검사하게 하는 것이며, `normalization_hash` 재발행이
딸린다(177개 WP 매니페스트의 착수 조건). 사용자 결정.

**NORM-006·007 의 `enforcement.status` 는 `planned` 로 남는다.** 실제 집행은 `pytest` 게이트가
하는데, `validator.py` 가 `active` 를 `registry/checks/ci_*.py` 파일로만 해석하고 `06` §5 는
`CI-01`~`CI-18` 만 선언한다. `active` 로 바꾸면 없는 로스터 항목을 주장하는 것이 된다. 푸는 데
`06` §5 개정이 필요하다.

## 이 기계에서 게이트를 돌릴 때

- `scripts/gates.sh` 의 판정은 **마지막 배너와 종료코드뿐**이다. `run()` 은 실패를 배열에 담고 다음
  섹션으로 넘어가므로, 섹션 헤더가 이어진 것은 앞 게이트가 통과했다는 뜻이 아니다.
- `=== pytest ===` 뒤에 `N passed` 요약줄이 없는 것은 **정상**이다. 통과한 런의 로그도 같다.
- **`pkill -f "_dummy_train"` 은 자기 자신을 죽인다.** 그 문자열이 실행 중인 셸의 명령줄에 들어
  있어 항상 매치된다. `pgrep -af "[_]dummy_train"` 처럼 대괄호로 끊을 것.
- `tests/wp4a01/_dummy_train.py --hold_at_step=3` 은 릴리스를 기다리며 영원히 도는 물건이라, 런이
  죽으면 고아로 남아 다음 런을 굶긴다. 게이트가 죽으면 이것부터 볼 것.
- 프론트 vitest 는 실제로 5.6 초면 끝난다. 백그라운드로 돌렸을 때 두 번 죽었고 포그라운드에서는
  한 번에 통과했다.
