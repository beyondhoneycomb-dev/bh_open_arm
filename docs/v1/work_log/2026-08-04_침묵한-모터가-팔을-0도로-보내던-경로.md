# 2026-08-04 — 침묵한 모터가 팔을 0도로 보내던 경로, 그리고 실기로 판정한 카메라 상수

같은 날 `2026-08-04_안 돌던-감지기를-결선하다.md` 의 후속. 그 세션이 미검증으로 남긴
`openarm_follower_oa.py:1032` 을 검증했고, 결함이었다. 그리고 실기가 붙어 있어서
`backend/camera/` 의 하드웨어 주장을 처음으로 실측과 대조했다.

## 맥락

앞 세션의 후속 목록 첫 줄: *"fail-closed 래치의 홀드 벡터가 「못 봤다」고 선언한 그 읽기에서
나와, 안 보인 관절이 0.0 으로 채워지면 래치가 홀드가 아니라 큰 이동 명령이 될 수 있다. 미검증."*

워크플로 19 에이전트(추적 3 · 훑기 4 · 적대검증 12)를 돌렸고, 독립 세 에이전트가 같은 사슬로
수렴했다. 사슬의 전 구간을 직접 열어 확인했다.

## 결과 ① — 🔴 침묵한 모터가 팔을 0도로 보낸다

| 홉 | 파일:줄 | 하는 일 |
|---|---|---|
| 1 | `damiao.py:138-148` | 모터별 상태 캐시를 `position: 0.0` 으로 초기화 |
| 2 | `damiao.py:695-702` | 응답이 없으면 `Packet drop:` 만 남기고 캐시는 건드리지 않는다 |
| 3 | `damiao.py:668-674` | `sync_read_all_states` 가 요청한 전 모터의 캐시를 무조건 복사해 돌려준다 |
| 4 | `openarm_follower_oa.py:1032` | 그 0.0 이 `widened` 로 |
| 5 | `openarm_follower_oa.py:705` | `present` 가 된다 |
| 6 | 같은 드롭이 `:1024` `bus_read_ok=False` | 가드가 fail-closed 래치 |
| 7 | `enforcement.py:268` | `_reject` 가 `accepted=present` — 그 0.0 |
| 8 | `assembly.py:105-115` → `decider.py:105-109` → `scheduler.py:258` | CAN 에 쓰인다 |

**0.0 을 만드는 조건과 거부를 만드는 조건이 같다.** 정상일 때는 나타나지 않고 고장났을 때만
발동한다. URDF 영점에 매달린 팔에서 0도는 수평이다.

영점 확립 경로도 같은 결함을 탄다. `:592` 가 `_read_joint_deg()` 로 잔차를 재는데, 응답 없는
모터는 0.0 으로 읽히고 잔차 0.0 은 허용 범위 안이다 — **말하지 않는 모터의 영점이 성립한다.**

### 고칠 코드는 이미 저장소에 있었다

리그 경로가 세 조각을 다 갖고 있다:

- `_is_cache_initialiser` — 응답이 채우는 전 필드가 0 이면 캐시 초기값. 통전된 DM 모터는
  MOS·로터 온도를 섭씨로 보고하므로 실온만 있어도 0 이 아니다. **값만 보고 판별한다.**
- 드롭 로그 기록자와 함께 걸러내기
- `read_present_pose_deg` 가 대입 대신 거부. 사유까지 적혀 있다 —
  *"a substituted zero is the horizontal on an arm hanging at the URDF zero"*

**팔로워 경로는 하나도 물려받지 않았다.** 적대 검증이 이유까지 찾아냈다: 보호를 가진
`RigArmBus` 는 `rig_session.py:545` 에서 engage bus 용으로만 만들어지고 `arms[side].bus` 에
되돌아가지 않는다. 팔로워의 명령별 읽기는 그것을 볼 일이 없다.

### 수리

방향은 연산에서 도출했다 — 관절 위치 명령은 되돌릴 수 없고(팔이 이미 움직였다) 폭발반경이
넓다(브레이크 없는 7축). **거부한다.**

`is_cache_initialiser` 와 `ANSWERED_STATE_FIELDS` 를 `backend/actuation/bus_writer.py` 로
옮겼다 — 드롭 검출의 나머지 절반(`DropCounter`)이 이미 거기 있고, 두 판정이 "무엇이 응답인가"에
대해 서로 다른 답을 갖게 두면 안 된다. 리그와 팔로워가 같은 함수를 쓴다.

`_poll_states` 는 장착 모터의 상태가 없거나 캐시 초기값이면 `BusReadRefusedError` 를 던진다.
장착되지 않은 슬롯의 0.0 은 그대로 둔다 — 뒤에 모터가 없으므로 그 0 은 사실이다.

**새 기구는 짓지 않았다.** 거부하면 명령이 안 나가고, 메일박스가 `FRESHNESS_WINDOW_SEC`(0.05초)
뒤에 낡으면 스케줄러가 `_hold_batch` 로 홀드한다 — 마지막으로 정당하게 명령된 자세. "마지막
정상값"은 이미 있었고 그것이 옳은 자리다.

## 결과 ② — 가짜 셋이 존재할 수 없는 장치를 흉내내고 있었다

수리를 넣자 21건이 빨개졌다. 결함이 아니라 **가짜가 틀렸다는 신호**였다.

`damiao.py:139-148` 의 실제 상태 dict 는 5필드(`position`·`velocity`·`torque`·`temp_mos`·
`temp_rotor`)인데 `tests/wp102/conftest.py`·`tests/wp103/conftest.py`·
`tests/wp105/test_rig_engage.py` 의 doubles 는 앞 3개만 돌려줬다. 통전된 모터가 두 온도 센서
모두 0 °C 를 보고하는 일은 없다. 셋 다 실제 응답 모양으로 고쳤다 —
`scripts/torque_session_tests/rig_doubles.py` 가 이미 하던 그대로다.

`tests/wp103/test_guard_polled.py` 는 다섯 건이 `omit_motors`(응답이 짧게 오는 모양)로 래치를
검사하고 있었는데, **벤더 버스는 짧은 응답을 내지 않는다.** `conftest.py` 주석이 이미 그렇게
적어놨다 — *"only the second one happens on hardware"*. 실기 케이스(`drop_motors`)로 옮기고,
새 거부는 따로 고정했다.

`REST_POSE_DEG` 를 0.0 → 3.0 으로 바꿨다. 0 은 캐시가 보고하는 값이라, 픽스처가 거기 쉬면
**측정된 홀드와 지어낸 홀드가 같은 튜플**이 되고 그 사이의 모든 단언이 아무것도 검사하지 않는다.

## 결과 ③ — 카메라 상수를 실기로 판정했다

`v4l2-ctl` 이 없고 무암호 sudo 도 없어서 `VIDIOC_QUERYCTRL`/`G_CTRL`/`S_CTRL` 을 ioctl 로 직접
읽었다. Arducam B0495 두 대(`/dev/video2`, `/dev/video4`) 와 ZED-M(`/dev/video0`).

| 저장소 주장 | 실측 |
|---|---|
| 범위 밖 정수는 조용히 최근접 합법값으로 (9999→660) | ✅ `9999 → 660`, `gain 1 → 168`, 에러 없음 |
| 자동 모드가 가드하는 컨트롤에 쓰면 **에러 없이 버려진다** | ❌ `EACCES errno=13`, 값 불변 |
| 선언 없이 열면 `exposure=660`·`gain=1600` 최대라 순백 클리핑 | ❌ `exposure=5`·`gain=168`, 양쪽 **최소**이자 기본값 |
| `AUTO_EXPOSURE_APERTURE_PRIORITY = 3` = 켜질 때의 자동 모드 | ❌ 메뉴가 `{0: Auto Mode, 1: Manual Mode}` 뿐. 켜질 때 0. 3 은 `EINVAL errno=22` |
| `ARDUCAM_..._TEMPERATURE_MINIMUM = 2800` ("미측정") | ❌ Arducam 2300. **2800 은 ZED-M 값이었다** |
| `ARDUCAM_EXPOSURE_TIME_MINIMUM = 5` · `GAIN_MINIMUM = 168` | ✅ |

가장 무거운 것은 두 번째다. "쓰기는 에러를 내지 않는다"고 적혀 있으면 이 모듈 위에 쓰기 경로를
짓는 사람은 **`EACCES`/`EINVAL` 분기를 아예 만들지 않는다.** 없는 실패 모드를 문서가 지웠다.

가짜(`fixtures.py`)도 같은 믿음대로 쓰여 있었다 — 게이트가 닫힌 쓰기를 조용히 `return` 하고,
메뉴 범위를 클램프했다. 셋 다 실제 답(클램프 / `EACCES` / `EINVAL`)으로 고쳤다. `ControlRange`
에 `legal_values` 를 더했다: 메뉴의 경계는 그 항목을 열거하지 않으므로(0..3 인데 답하는 것은
0 과 1) 범위에서 유도할 수 없다.

가짜의 ZED 백밸런스 기본값이 **선언값 4000 과 같았다** — 픽스처가 이미 설정된 채로 켜지면 그
아래 모든 케이스가 아무것도 증명하지 않는다. 실측 4600 으로 바꾸고, 그 불변식을 값 목록이 아니라
"선언값과 다르다"로 단언하게 고쳤다.

## 검증

```
./scripts/gates.sh   →  ALL GATES GREEN, 종료코드 0
프론트               →  868/868 (162 파일)
변이 검사            →  카메라 4/5 · 팔로워 4/5
```

변이는 `str.replace` 결과가 원본과 다른지 **먼저 단언하고** 돌렸다. 앞 세션이 배운 것:
적용되지 않은 변이는 살아남은 변이와 출력이 완전히 같다.

살아남은 변이 하나는 동어반복이라 예상된 것이다. `observation_present=not unanswered` 를
`True` 로 바꿔도 위 거부가 걸러낸 뒤라 구조상 같은 값이고, 어떤 테스트도 구별할 수 없다.

## 워크플로가 반증한 것

내가 처음 "증폭"이라고 부른 두 건은 **오진이었고 적대 검증이 잡았다**:

- `assembly.py:105-115` 가 `GateResult.rejected` 를 안 읽는 것은 사실이나, 거부의
  `accepted` 는 팔의 실제 present 이고 `_as_hold_frame`(`scheduler.py:45-58`)이 토크를
  벗긴다. 홀드 지점이 팔이 실제로 있는 자리를 따라가는 것은 브레이크 없는 팔에서 **옳다.**
  `tests/wp103/test_gateway_write_path_assembly.py:238-250` 이 이미 그것을 의도로 고정한다.
  남는 것은 텔레메트리뿐 — 틱 기록이 통과와 거부를 구별하지 못한다.
- 충돌 래치가 `engage_safety_latch` 에 닿지 않는 것도 사실이나, `guard.py:204` 가 콜백
  **이전에** `_latched` 를 세우고 `enforcement.py:207` 이 그 플래그를 인-밴드로 읽는다.
  콜백은 집행 경로가 아니다.
- "마지막 정상 자세가 어디에도 없다"도 반증됐다. `ActuationScheduler._hold_batch` 가 그것이고
  `tests/wp0a01/test_hold_frame.py:48-58` 이 고정한다.
