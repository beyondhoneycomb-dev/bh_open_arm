# 2026-08-05 — 충돌 가드 래치는 아직 닿지 않는다: 급하다고 판정했다가 취소한 근거

## Context

CAN 링크를 올리기 직전에 충돌 가드 래치 경로를 추적했다. 처음 판정은 **"실기 붙는 순간 터진다"**
였고, 그것을 사용자에게 그렇게 보고했다. 더 파보니 **틀렸다.** 이 문서는 그 정정과 근거다.

정정을 남기는 이유: 근거가 사라지면 다음 세션이 같은 체인을 보고 같은 결론에 도달하고,
같은 순서 오판을 반복한다.

## Files changed

없다. 이 문서는 판정 기록이다. 같은 날의 구현은 다른 두 편에 있다.

## Why

### 체인은 실재한다

```
openarm_follower_oa.py:717    angles, guard_sample = self._poll_states()      ← send_action 안
openarm_follower_oa.py:1058   bus_read_ok = drop_counter.count == drops_before  ← 드롭 1회면 False
enforcement.py:188            self._guard.poll(guard_sample)
guard.py:196-197              not bus_read_ok  ⇒  GuardCause.BUS_READ_FAILED
guard.py:204                  _latched = True                     ← 디바운스 없음
enforcement.py:207            collision_latched = guard.is_latched
safety.py:485-486             ⇒ 모든 명령 정지 (COLLISION_LATCH)
guard.py:165                  False 로 되돌리는 유일한 곳 = guard.acknowledge()
openarm_follower_oa.py:892    유일한 호출자 = acknowledge_collision_latch()  ← 프로덕션 호출자 0개
```

가드 자기 주석이 결과를 적어놨다 (`guard.py:160-162`):
*"one dropped CAN reply stops the arm until the process restarts."*

### 그런데 그 경로에 아직 아무도 안 들어간다

가드 폴링은 **`send_action` 안에서만** 일어난다(`_poll_states`가 `GuardSample`을 만든다).
`send_action`의 프로덕션 호출자를 전수 조회하면:

| 호출자 | 살아 있나 |
|---|---|
| `backend/recorder/embed/loop.py:192` | 데이터 수집 루프 — 실행 중 아님 |
| `backend/inference/adapter/remote.py:158` | 추론 — 실행 중 아님 |
| `backend/torque_bringup/rig.py:427` | 토크 브링업 |
| `openarm_follower_oa.py:1375` | 양팔 위임 |

**그리고 `scripts/torque_session.py`·`rig_session.py`는 `send_action`을 부르지 않는다** —
docstring에만 나온다. 그 세션은 토크를 걸고 `maintain_hold`(`rig.py:531` = `spine.tick()`)로
홀드만 유지한다. 홀드 경로는 가드를 보지 않는다.

**귀결**: 가이드 `05` 5부(토크 ON)까지 가는 동안 래치는 걸리지 않는다. 걸리는 것은 데이터 수집·
추론·토크 브링업 경로이고, 셋 다 지금 실행 중이 아니다. **오늘의 실기 작업을 막지 않는다.**

### 그리고 예외를 던지는 것은 답이 아니었다

`send_action`이 거부분을 수락분과 같은 모양으로 반환하는 것(`accepted=present`,
`enforcement.py:264-268`)을 보고 예외를 던질 생각을 했다. 틀렸다 —
`backend/feedback/__init__.py:12`가 이유를 적어놨다:

> "It never stops the command loop. Stopping the stream drops the arm (RID-9 watchdog)."

호출자 루프를 끊으면 명령 스트림이 끊기고 그것이 인에이블 이탈이고 낙하다. 거부가 홀드로 계속
흐르는 것은 **설계이고 옳다**(`openarm_follower_oa.py:683-688`이 그렇게 적었다).
고칠 것은 반환 형태가 아니라 **읽는 경로의 부재**다.

### 정보는 네 곳에 기록되고 네 곳 모두 안 읽힌다

| 기록되는 곳 | 프로덕션 읽기 |
|---|---|
| `GateResult.override.latched` (`enforcement.py:273`) | 0 |
| `_last_gate_result` (`openarm_follower_oa.py:723`) | 0 |
| `_last_latch_reason` (`:357`, `:901`) | 0 |
| `AuditRecord.latched` (`audit/record.py:72`) | `from_decision` 프로덕션 호출자 0 |

읽는 사람 없는 접근자를 다섯 번째로 추가하는 것은 이 결함을 반복하는 것이므로 **하지 않았다.**

## Follow-ups

- **순서**: 래치 출구와 거부 가시성은 **데이터 수집 경로가 살아날 때** 필요하다
  (`recorder/embed/loop.py:192`). 그 전에 붙이면 호출자 없는 설비를 또 만드는 것이다.
- **이원화 방지 근거는 이미 있다.** `backend/freedrive/session.py:252-260`의 `LatchTarget`
  어댑터가 프로덕션에서 `guard.acknowledge()` + `latch.acknowledge()` 를 **함께** 한다.
  `DeadmanController`의 프로덕션 생성 지점은 `freedrive/session.py:233` 하나뿐이고 그것이
  이 어댑터를 넘긴다. 🔴 **위험은 미래에 있다** — `ActuationScheduler.acknowledge_latch`
  (`scheduler.py:207`)는 `SafetyLatch`만 해제하고 가드를 모른다. WS 서버가 스케줄러를 맨몸으로
  `latch_target`에 넘기면 재무장이 스케줄러 래치만 풀고 가드는 걸린 채 남는다 —
  `freedrive/session.py:255-258`이 그 실패를 문장으로 적어놨다. **정적 검사로 못박을 자리다.**
- `AuditRecord.from_decision`은 `executed`(MIT 배치)와 `chain`(캘리브 변환)을 요구하므로
  `send_action`이 아니라 **쓰기 틱**이 만들 기록이다. `SPINE §6`이 방출 4종 전부를 감사 채널에
  기록하라고 하는데 그것을 만드는 코드가 없다 — 별도 항목.
- 이 세션에서 같은 양식을 다섯 번 만났다: `PreviewSink`(구현체 0), `acknowledge_collision_latch`
  (호출자 0), `AuditRecord.from_decision`(호출자 0), `identify_moved_channel`(진입점 0),
  `last_latch_reason`(읽기 0). **순수한 코어는 짓고 껍데기는 안 짓는다.** 코어가 테스트로
  검증되니 게이트는 초록이고, "안 연결됨"을 묻는 검사가 없다.
  → [[openarm-tests-check-shape-not-value]] 와 같은 뿌리. CLAUDE.md 승격 후보.
