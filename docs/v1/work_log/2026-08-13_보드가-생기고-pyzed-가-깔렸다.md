# 2026-08-13 — 상태 보드가 생겼다, 그리고 pyzed 설치가 게이트를 빨갛게 만들었다

## Context

사용자 지시 둘: `pyzed` 설치, 남은 것 계속 진행.

정찰(에이전트 2명이 각각 확인)이 확정한 것 — **트리 전체에 상태 보드가 없다.** 제어 경로에서
프로즌 객체를 원자적으로 교체해 여러 읽는이에게 주는 물건이 하나도 없다. `TargetMailbox` 는
명령이 **들어가는** 쪽이고, `EventRingBuffer` 는 사후 텔레메트리 링이며, `_poll_states()` 는
`send_action` 마다 팔별로 버스를 다시 읽는다 — 그게 두 번째 버스 소유자이고 pose·torque 시간
어긋남의 출처다.

## Why

### 1. 보드 — 락 없이, 프로즌 객체 하나를 바꿔 끼운다

```
버스 소유자:  전 모터 1회 읽기 → publish(ArmState)     한 명이 쓴다, 틱당 한 번
읽는이:       board.view()                            속성 읽기 하나, 락 없음
```

`publish` 는 속성 저장 하나다. CPython 이 그 저장을 원자적으로 하므로 읽는이는 이전 상태 전체나
새 상태 전체를 보고 반쪽 섞인 것을 못 본다 — **그것이 락이 없는 이유의 전부이고, `ArmState` 가
프로즌이어야만 성립한다.** 가변 페이로드를 넣으면 락만 없어지고 찢김은 돌아온다.

`joint_deg` 와 `torque_nm` 이 **같은 프레임**에서 나온다. 따로 읽으면 서로 다른 순간을 서술하고,
그 틈을 가로질러 계산한 잔차는 아무도 못 믿는 충돌 신호가 된다.

보드는 팔을 소유한 쪽이 갖고 **모듈 전역이 아니다.** 한 프로세스의 팔로워 둘이나 테스트 둘이
서로의 팔을 판정하게 된다.

### 2. 🔴 신선도는 사실이 **둘** 필요하다 — 하나면 놀고 있는 팔을 세운다

뻔한 규칙 *"판독이 N초보다 낡으면 정지"* 는 **틀렸다.** 운영자 조작 사이에 붙어만 있는 GUI 는
읽지도 몰지도 않으므로, 그 규칙은 **가만히 있다는 이유로 팔을 세운다.** 옆 Indy7 리그의 스위트가
한 번 돌자마자 그걸 말했고 테스트 4개가 떨어졌다.

조건은 더 좁다. 아무도 안 읽고 아무도 안 모는 팔은 **놀고 있는 것**이고, 판독이 멈춘 뒤에도
**계속 명령받는** 팔이 눈 감고 도는 루프다. 후자만 실패다. 그래서 보드가 프레임이 마지막으로
나간 시각도 들고(`mark_commanded`), `is_driving_blind` 가 둘 다 요구한다:

```python
return self.commanded_since_read and self.age_s > max_age_s
```

건강한 루프는 읽고 나서 보내므로 마지막 명령이 마지막 판독보다 항상 최대 한 주기 새롭다 —
그래서 무장 조건이 **"명령이 자기 판독보다 오래 살아남았다"** 이지 단순히 "명령이 있었다" 가
아니다.

### 3. pyzed 설치가 게이트를 빨갛게 만들었고, 그게 옳았다

ZED SDK 는 `/usr/local/zed` 에 **이미 있었다**(5.4.1). 가이드의 *"없음"* 서술이 낡은 것이다.
`get_python_api.py` 가 venv 에 pip 이 없어 실패했고, 받아둔 휠을 `uv pip install` 로 넣었다.
sudo 안 썼다.

그 직후 게이트가 2건 빨간불이 됐다:

```
FAILED tests/wp3b03/test_reverify_hook.py::test_the_zed_is_unavailable_for_three_separate_reasons
FAILED tests/wp3b03/test_reverify_hook.py::test_a_superspeed_zed_clears_the_cabling_blocker_and_only_that_one
```

**결함이 아니라 테스트가 사실을 정확히 지킨 것이다.** 세 사유 중 하나(SDK 부재)를 내가 없앴다.

다만 그 두 테스트에 진짜 결함이 하나 있었다 — **환경 의존.** 합성 sysfs 트리로 USB 링크는
가짜로 만들면서 SDK 검사는 진짜 인터프리터(`importlib.util.find_spec`)를 읽는다. 즉 누가 패키지를
깔면 아무도 안 건드린 트리에서 판정이 뒤집힌다. docstring 이 지키려던 성질은 *"사유가 서로
독립"* 이지 *"사유가 셋"* 이 아니므로, SDK 유무를 `monkeypatch` 로 고정하고 양방향을 따로
못박았다(`test_the_sdk_blocker_is_reported_exactly_when_the_sdk_is_absent` — 조건문이 아니라
쌍조건이라 SDK 가 있든 없든 문다).

실기에서 지금 남은 ZED 차단 사유는 **하나뿐**이다:

```
stereolabs_zed  supported=False  the installed LeRobot has no camera class for 'stereolabs_zed'
```

## Follow-ups

- **보드는 아직 호출자가 0이다.** 다음 단계가 그것을 채운다 — 틱당 1회 14모터 batch 읽기를
  버스 소유자에 넣고 `publish` 로 흘린다. 그 전까지 이 파일은 이 저장소가 반복해 만드는
  "호출자 없는 코어" 이고, **그 상태로 두면 안 된다.**
- ZED 를 실제로 쓰려면 **LeRobot 에 ZED 카메라 클래스가 없다**는 사유가 남는다. 우리가 짓거나
  `pyzed` 를 직접 소비하는 경로를 두거나 둘 중 하나다.
- 세션 중 하드웨어가 통째로 빠졌다가 ZED 만 돌아왔다. **Arducam 2대와 PCAN(can0/can1)은 아직
  없다** — 카메라 3대 측정과 실기 제어 루프 확인은 그것이 돌아와야 한다.
