## 🔴 `connect_readonly` 는 읽기 전용이 아니다

이 세션 최대 발견이다.

`.venv/…/lerobot/motors/damiao/damiao.py:204-247` 의 `_handshake()` 가 **등록된 모든 모터에**
`CAN_CMD_ENABLE` 을 보내고 응답을 요구한다. 그리고 `tables.py:200` 에서
**`CAN_CMD_ENABLE = 0xFC`** — 토크 인에이블이다.

그래서 `packages/lerobot_robot_openarm/openarm_follower_oa.py:435` 의 `connect_readonly()` 는
독스트링이 *"Never calls `enable_torque`… after this returns, torque is OFF (02 FR-CON-062,
12 FR-SAF-075)"* 라고 약속하지만, **한 층 아래에서 전 모터를 활성화한다.**

뒤따르는 MIT 명령이 없으면 kp=kd=tau=0 이라 토크가 걸리지 않는다(그래서 팔이 움직이지 않았다).
하지만 "활성화된 채 감쇠 0" 은 FR-MOT-058 ③ 이 금지하는 상태이고, 모터는 다음 프레임에 즉시
반응하는 상태로 남는다.

**그리고 이미 일어난 뒤였다.** 위 두 거부 모두, 그리퍼에서 실패하기 *전에* 왼팔 `joint_1`~
`joint_7` 에 0xFC 가 나가 있었다. *"거부됐으니 아무 일도 없었다"* 는 추론이 틀렸다.

수습: LeRobot 을 거치지 않고 원시 CAN 으로 `0xFD` 를 양 채널 7개씩 보내 알려진 OFF 상태로
되돌렸다(14개 전부 응답). `connect()` 재호출로는 확인할 수 없다 — **확인 자체가 통전이다.**

게이트(`assert_torque_on_allowed`)는 매니페스트가 **선언한** 주기를 RID-9 천장과 비교하는데,
루프는 `RID9_NO_SEND_MARGIN_SEC / HOLD_REFRESH_DIVISOR` 로 **자기가 다시 계산**한 값을 썼다.
두 값이 우연히 같아서 지금은 문제가 없지만, 검사받은 값과 실행되는 값이 다른 변수였다.

`HoldMaintainer(rig_session.rig, manifest.rid9_send_period_sec)` 로 바꿨다. 이로써 죽은
`HOLD_REFRESH_DIVISOR` 를 함께 제거했다 — 제 변경이 만든 고아이므로 제가 치웠다.

## 낡은 경고가 깨끗한 세션을 물들였다

`_record_step` 이 상태 파일에 **키로 병합**하므로, 도달하지 못한 단계에는 이전 세션의 판정이
남는다. 실측: `engage`/`release` 는 00:53 세션 것인데 `torque_state` 는 `finished_at=None` —
00:29 실패 세션의 잔재. 결과로 **깨끗하게 끝난 세션이 종료코드 1** 을 내고 *"팔이 아직 통전돼
있을 수 있다"* 고 거짓 경고했다.

이런 거짓 경보는 정작 진짜일 때 무시하게 만든다.

수리 — 세션 시작에 단계 기록을 비우되 **토크 경고만 이월**하고, 릴리스가 실제 통과할 때
회수한다. 경고는 *실행*이 아니라 *팔*에 대한 주장이므로, 승인에서 거부된 세션(팔을 건드린 적
없음)이 그것을 지울 자격은 없다. 변이 3종 각각이 해당 테스트만 죽인다.

## 세션 테스트 3건이 실기를 타고 있었다

`_admit_everything` 이 *"CAN 채널을 건드리지 않고"* 라고 적혀 있었지만 `admit` 만 스텁하고 단계
수행부는 그대로 돌았다. "릴리스 실패" 라는 전제를 **그리퍼 핸드셰이크 실패가 우연히**
충족시키고 있었고, 그게 고쳐지자 릴리스가 진짜로 성공해 테스트가 깨졌다.

# 카메라

## 손목 쌍은 시리얼이 같다 — udev 로는 구분 불가

실측:

```
$ ls /dev/v4l/by-id/
usb-Arducam_…_Arducam_202500915_0001-video-index0 -> ../../video2
usb-Arducam_…_Arducam_202500915_0001-video-index1 -> ../../video3
usb-Technologies__Inc._ZED-M-video-index0         -> ../../video4
```

**Arducam 항목이 하나뿐이다.** 시리얼이 같아서 udev 가 하나만 만들었고 `/dev/video0` 짜리
카메라는 안정된 이름이 **아예 없다.**

명세가 이걸 이미 알고 있었다. `06` FR-CAM-085 — *"Cell 참조 하드웨어: 출하 시 시리얼 동일 →
굽지 않으면 심링크가 임의 카메라에 붙음"* — 이고 우선순위 **C**, **[선택]**, *"정본 계약이
아니므로 기본값·필수 단계가 아니다"*.

## 커널의 `bus_info` 로 구분한다


재부팅·재연결에 불변, 시리얼이 같아도 구분, **udev 규칙이 하나도 필요 없다.** 플러그를 옮기면
바뀐다 — CAN 채널 바인딩의 `ID_PATH` 와 같은 성질이고 같은 실패 양식이다.

캡처 노드인지는 이름으로 추측하지 않고 **노드별 `device_caps`** 를 읽는다. 장치 전체
`capabilities` 를 읽으면 UVC 의 메타데이터 노드(`video1`/`3`/`5`)까지 카메라로 세어 대수가 두
배가 된다 — 변이 검사로 확인.

## 지정은 GUI 안에서 — 설정파일에 묶지 않는다

**처음에 CLI 바인딩 도구(`scripts/camera_bind.py`)로 만들었는데 요구를 잘못 읽었다.** 요구는
화면 안에서 동적으로 프리뷰를 보고 고르는 것이었다. 되돌리고 S-06 카메라 화면의 동작으로 옮겼다.

`frontend/src/screens/S-06/DeviceAssignmentPanel.tsx` — 각 행이 셋을 함께 싣는다:

1. **프리뷰** — 어느 팔을 보고 있는지 말해주는 유일한 것
2. **포트** — 지정의 키이자, 이 하드웨어에서 유일하게 구분되는 텍스트
3. **슬롯** — 지금 채우고 있는 것

행 집합은 상수가 아니라 마지막 스캔에서 답한 장치들이다(CG-G-S06a 와 같은 규칙). 고를 수 있는
슬롯도 `deriveTiles` 로 등록된 집합에서 나오므로 로봇에 없는 슬롯을 제시하지 않는다.

판정은 순수 함수(`assign.ts`)로 분리했다 — 다른 장치가 쓰는 슬롯 · 사라진 장치 · 포트를 보고하지
않는 장치를 거부하고, **이미 그 슬롯인 장치의 재지정은 통과**시킨다(무동작을 충돌이라 부르면
운영자가 진짜 경고를 넘겨 읽는다).

## ZED

`2b03:f682`, 1344×376 = 672×376 스테레오 쌍. **LeRobot 의 `OpenCVCamera` 로 추가 설치 없이
읽힌다** — 일반 UVC 장치다. 확인:

```python
cam = OpenCVCamera(OpenCVCameraConfig(index_or_path=Path("/dev/video4")))
cam.connect(warmup=True); cam.read()   # (376, 1344, 3) uint8
```

**깊이는 별개다.** `/usr/local/zed` 없음(SDK 미설치), `pyzed` 없음, LeRobot 카메라 클래스는
`opencv`/`realsense`/`reachy2_camera`/`zmq` 뿐이다.
