## CAN 결합이 해석되지 않았다

어댑터를 다시 꽂으면서 USB 포트 경로가 `10.3.1.2` → `7.1.2` 로 바뀌었다. 지속 결합은
`ID_PATH` + `dev_id` 로 키를 잡으므로 경로가 바뀌면 해석되지 않는다 — 설계된 실패다.

어댑터의 두 소켓은 그대로이므로 `dev_id` 별 역할을 보존한 채 새 경로로 다시 키를 잡았다
(사용자 결정: 물리 재식별 대신 재키잉). 결과 `~/.config/openarm/can_binding.json`:

```json
{"roles": {"follower_left":  "pci-0000:80:14.0-usb-0:7.1.2:1.0/dev_id:0x0",
           "follower_right": "pci-0000:80:14.0-usb-0:7.1.2:1.0/dev_id:0x1"}, "version": 1}
```

`check_binding` 이 `follower_left→can0`, `follower_right→can1` 로 해석하고 missing 은 없다.

## 🔴 ZED 오진 — 상수 하나가 세 번의 잘못된 조언을 만들었다

**이 항목은 내가 틀린 기록이다.** 사용자가 바로잡았고 그 지적이 맞았다.

ZED Mini 는 USB 기능이 **둘**이다:

| 기능 | 제품 id | 링크 | 인터페이스 | manufacturer |
|---|---|---|---|---|
| 카메라 | `2b03:f682` | 5000 Mbps | 비디오 클래스 `0e` × 2, `uvcvideo` | `Technologies, Inc.` |
| IMU/HID | `2b03:f681` | **12 Mbps (설계상 전속)** | HID 클래스 `03` × 1 | `STEREOLABS` |

`backend/sensing/depth/constants.py` 의 `ZED_MINI_USB_PRODUCT_ID` 가 **`f681`** — IMU/HID
동반 기능을 가리키고 있었다. 그래서 정상 카메라가 붙어 있는데도 코드가 이렇게 출력했다:

> *the 2b03:f681 camera is on a 12 Mbit/s link publishing interface class 03 and no video class
> 0e, so it carries no stream to open — **move it to a USB 3.0 port***

나는 이 출력을 믿고 "고속 협상 실패 → 케이블/포트 문제" 라고 진단했고, 조작자에게 포트를 세 번
바꾸게 했다. 카메라가 실제로 붙은 뒤에도 같은 말을 계속했다.

내 19:48 측정 자체가 `f682`(5000)와 `f681`(12)이 **동시에 존재**함을 이미 보여주고 있었는데도
읽지 못했다. 사용자가 *"zed 가 뭐 신호 같은거 주기 전에는 기본 12로 하는거 아니야?"* 라고 짚은
것이 정확했다 — 12 Mbps 는 별개 기능의 정상값이지 협상 실패가 아니다.

**올바른 판별자는 링크 속도가 아니라 `f682` 의 존재다.** 상수를 고치고
`ZED_MINI_USB_HID_PRODUCT_ID = "f681"` 을 별도로 두었다. 그러자 배선 차단 사유가 사라지고
실제 남은 둘만 남는다: `pyzed` 미설치, LeRobot 에 `stereolabs_zed` 카메라 클래스 없음.

### 교훈

코드가 출력한 진단을 근거로 하드웨어를 의심했는데, 그 진단의 전제(어느 장치를 보는가)가 틀려
있었다. **진단 메시지는 그것을 만든 상수보다 신뢰도가 높을 수 없다.**

## 거짓 초록 셋 — 전부 실기 데이터가 생기면서 드러났다

오프라인에서는 스킵이거나 공허하게 참이던 것들이, 실제 캡처가 들어오자 실패해야 할 자리에서
초록을 냈다.

### ① `dev_id_distinguishes_channels` — 크기 1 집합에서 공허하게 참

수용의 내용이 *"한 어댑터의 두 채널을 `dev_id` 가 구분한다"* 인데, 채널이 하나면 구분을 보일 수
없다 — 없는 것도 없고 충돌도 없으니 통과한다.

형제 함수 `serial_shared_per_adapter`(`ops/hw/udev/measurement.py:111-118`)는 `saw_shared` 로 같은 것을 이미 막고 있었고
전용 테스트까지 있었다. 한쪽만 고쳐져 있었던 것이다.

어댑터별 가드로 맞췄다. **인터페이스 개수를 세는 수정으로는 안 된다** — 서로 다른 어댑터 두
개가 각각 한 채널씩 담긴 캡처도 통과하므로, 그 변종까지 테스트로 못박았다
(`test_two_adapters_of_one_channel_each_do_not_prove_dev_id_separation`).

변이 검사: 가드 삭제 → 2 RED, 어댑터별 대신 전체 인터페이스 개수 → 1 RED.

### ② wp2a09 실기 교차검사가 한 팔 캡처를 통과

`wp0b07` 에는 팔 커버리지를 붙였는데 여기엔 안 붙였다. 같은 거부(`assert_every_arm_answered`)를
배선했다.

### ③ wp3b03 의 USB 신원 수용이 **실패할 수 없었다**

탐색기가 `manufacturer` 문자열이 `"STEREOLABS"` 인 장치를 찾는데, 실측하면 카메라 기능은
`"Technologies, Inc."` 를 보고하고 `"STEREOLABS"` 는 HID 쪽이다. 즉 **이 탐색기로는 카메라를
절대 못 찾았고**, 통과는 항상 스킵이거나 HID 를 잡은 결과였다.

벤더 id + 비디오 클래스 인터페이스로 찾게 했다. 벤더 id 는 시험 대상이 아니고 제품 id 만
시험하므로 순환이 아니다. 변이 검사: `f681` → 1 RED, `f683` → 1 RED, `f682` → 76 passed.

## 반쪽 읽은 리그가 "장착 모터 전량" 수용을 통과했다

같은 병의 또 다른 형태 — **세는 것이 식별하는 것을 대신했다.**

실측: `can0.json` 하나만 둔 디렉터리(14개 중 7모터)가 양팔 정상 캡처와 구별되지 않고 **95건 전부
통과**했다. 각 덤프가 따로 판정되므로 담긴 일곱 개의 모든 판정이 통과하고, 나머지 팔은 읽히지
않은 채 "장착 모터 전량 읽음" 수용이 초록이 된다.

`can0` 을 두 이름으로 복사한 캡처도 "팔당 하나" 가드를 통과했다 — 가드가 파일 개수를 세고
`iface` 필드를 안 봤다.

`backend/can/rid/reverify.py::assert_every_arm_answered` 가 둘을 가른다. **인터페이스 이름은
검사하지 않는다** — 지속 결합은 `ID_PATH`·`dev_id` 로 키를 잡고 `canN` 이름은 살아있는 채널에서
해석되므로 다른 날 찍은 캡처로는 알 수 없다. 오프라인에서 검사 가능한 것은 리그의 팔 수만큼
서로 다른 인터페이스가 답했고 같은 것이 두 번 답하지 않았다는 것이다.
